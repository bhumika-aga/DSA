OOP & Collections Deep Dive

"First, learn the rules. Then break them intelligently. OOP gives you the rules for building scalable systems."

🌍
Why does this topic matter?
Object-Oriented Programming (OOP) is how engineers manage complexity. A single FAANG backend service can have millions of lines of code written by hundreds of engineers. Without OOP principles, that codebase collapses under its own weight. Encapsulation, Inheritance, Polymorphism, and Abstraction are the four tools that keep large systems maintainable — and they appear directly in interview questions like "Design a Parking Lot" or "Design an LRU Cache."
By the end of this lecture you can
  • Understand interfaces, abstract classes, generics
  • Master Java Collections Framework: ArrayList, LinkedList, Stack, Queue, Deque, PriorityQueue
  • Learn HashMap, TreeMap, LinkedHashMap and when to use each
  • Understand Comparable vs Comparator for custom sorting
  • Learn Iterator pattern and for-each internals
🧠
The picture to keep in your head: Cookie cutters, job descriptions, and containers. A class is a cookie cutter and each object is a cookie made with it. An interface is a job description — “anyone who can drive” — that many different people can fill. The collections are containers with different rules: a list is a numbered shelf, a set is a guest list where no name appears twice, and a map is a coat check, where a ticket gets you straight to a coat.

📖 Before We Start — The Big Picture

In the real world, we manage complexity by grouping related things. A class is a blueprint (the architect's drawing of a house). An object is the actual thing built from that blueprint (a real house). Every Toyota car on the road is a different object, but they all share the same class (blueprint). OOP is just this idea — applied to code.

You already used objects in Lecture 5 when you read about the String class, ArrayList, and the JVM's heap. Every single one of those is a class. This lecture teaches you how to design your own classes and how to make them work together elegantly.

🔗
How it connects: Lecture 5 explained memory — every object you new up goes on the heap. This lecture teaches you what those objects are. Lecture 7 (Java 8+) extends this with lambdas and functional interfaces, which are just anonymous object implementations behind the scenes.

1. Encapsulation

☕ Java · BankAccount
class BankAccount {
    private double balance;  // hidden — cannot access directly
    BankAccount(double init) { balance = init; }

    public void deposit(double amt) {
        if (amt <= 0) throw new IllegalArgumentException("Amount must be positive");
        balance += amt;
    }
    public double getBalance() { return balance; } // read-only access
}
// Cannot do: account.balance = -1000; (compile error!)
// Must go through deposit/withdraw which enforce business rules

2. Inheritance

☕ Java · Inheritance Chain
abstract class Shape {
    abstract double area();
    void print() { System.out.println("Area: " + area()); } // inherited
}

class Circle extends Shape {
    double r;
    Circle(double r) { this.r = r; }
    @Override double area() { return Math.PI * r * r; }
}

class Rectangle extends Shape {
    double w, h;
    Rectangle(double w, double h) { this.w=w; this.h=h; }
    @Override double area() { return w * h; }
}

// Polymorphism in action:
Shape[] shapes = {new Circle(5), new Rectangle(3,4)};
for (Shape s : shapes) s.print(); // calls correct area() per type

📊 Comparable vs Comparator

☕ Java · Both Patterns
class Employee implements Comparable<Employee> {
    String name; int salary;
    @Override
    public int compareTo(Employee o) {
        return Integer.compare(this.salary, o.salary); // natural order = by salary
    }
}

// Comparable: used when ONE natural ordering makes sense
// TreeSet<Employee> automatically uses compareTo()

// Comparator: used when you need MULTIPLE orderings or can't modify class
Comparator<Employee> byName = Comparator.comparing(e -> e.name);
Comparator<Employee> bySalaryDesc = (a,b) -> b.salary - a.salary;

// Chaining comparators (sort by salary desc, then by name asc)
Comparator<Employee> combined =
    Comparator.comparingInt((Employee e) -> e.salary).reversed()
              .thenComparing(e -> e.name);

list.sort(combined);
Arrays.sort(arr, combined);
new PriorityQueue<>(combined); // custom-ordered heap

🧬 Generics Deep Dive

☕ Java · Generic Methods & Bounded Wildcards 
// Generic method — works for any Comparable type
public static <T extends Comparable<T>> T findMax(List<T> list) {
    T max = list.get(0);
    for (T item : list) if (item.compareTo(max) > 0) max = item;
    return max;
}

// Bounded wildcards
// ? extends T — can READ (covariant): upper bound
double sumOfList(List<? extends Number> list) {
    double sum = 0;
    for (Number n : list) sum += n.doubleValue();
    return sum;
} // works for List<Integer>, List<Double>, List<Long>

// ? super T — can WRITE (contravariant): lower bound
void addNumbers(List<? super Integer> list) {
    for (int i = 1; i <= 10; i++) list.add(i);
} // works for List<Integer>, List<Number>, List<Object>

// PECS: Producer Extends, Consumer Super

📋 ArrayList Internals

📌
ArrayList is backed by a plain Object[] array. When you call new ArrayList<>() it creates an Object[10] internally. When full, it allocates a NEW array of size 1.5× and copies everything over. This copy is O(n) but happens rarely, so add() is O(1) amortised.
☕ Java · ArrayList resize simulation 
// Pseudocode approximation of ArrayList internals
class SimpleArrayList<T> {
    Object[] data = new Object[10]; // default capacity
    int size = 0;

    void add(T item) {
        if (size == data.length) {               // capacity hit
            int newCap = (size * 3) / 2 + 1;      // ~1.5× growth
            data = Arrays.copyOf(data, newCap);   // O(n) copy!
        }
        data[size++] = item;                      // O(1)
    }

    void remove(int idx) {                       // O(n) — shifts elements left
        System.arraycopy(data, idx+1, data, idx, size-idx-1);
        data[--size] = null;                   // prevent memory leak
    }
}
// Tip: new ArrayList<>(expectedSize) avoids all resizing overhead

⚠️ Complexity & Classic Bugs

The costs worth quoting in an interview first, then the mistakes that most often break code that looks correct. Every row in the second table is a bug someone has shipped.

Operation Cost Note
ArrayList get O(1), add at end O(1) amortised, contains/remove O(n) The default list
LinkedList get O(n), add/remove at ends O(1) Rarely the right choice
HashMap / HashSet O(1) average for everything No order
TreeMap / TreeSet O(log n) for everything Keeps keys sorted
PriorityQueue peek O(1), add/poll O(log n), contains O(n) Smallest element first
ArrayDeque O(1) at both ends The best stack and queue
Bug Symptom Fix
Overriding equals but not hashCode A HashSet holds two “equal” objects Always override both together
Using a mutable object as a map key The entry vanishes after the key changes Use immutable keys
list.remove(3) on a List<Integer> Removes index 3, not the value 3 list.remove(Integer.valueOf(3))
Comparator written as a - b Wrong order for large or negative values Integer.compare(a, b)
LinkedList.get(i) in a loop O(n²) where O(n) was expected Use ArrayList for index access
Printing a PriorityQueue The output is not sorted poll() repeatedly to get sorted order
Adding to Arrays.asList(...) UnsupportedOperationException Wrap it: new ArrayList<>(Arrays.asList(...))
Raw types without generics ClassCastException at run time Always write the type parameter

💪 In-Lecture Practice Problems

Problem 01 · Class Design
Design a Stack With Increment Operation
🔗 LC 1381 - Design a Stack With Increment Operation
Medium Encapsulated State Amazon · Microsoft
›
Problem

Design a stack with a maximum size supporting push, pop (return -1 when empty) and increment(k, val), which adds val to the bottom k elements.

CustomStack(3): push 1, push 2, pop → 2, push 2, push 3, push 4 (ignored), increment(5, 100), increment(2, 100), pop → 103
Hints
▶Hint 1 — a nudge

Start simple: an array plus a size index, with increment looping over the bottom k elements.

▶Hint 2 — the key idea

To make increment O(1), record it lazily: inc[min(k, size) - 1] += val. When you pop index i, add inc[i] to the value and pass it down to inc[i - 1].

Solution

This is encapsulation doing real work. Callers see only push, pop and increment; the class decides how state is stored. Because the fields are private, you can replace the O(k) increment with the lazy O(1) version without touching a single caller — exactly the argument for hiding fields behind methods.

▶Full solution
☕ Java · Array + Lazy Increment 
class CustomStack {
    private final int[] stack, inc;
    private int size = 0;

    CustomStack(int maxSize) {
        stack = new int[maxSize];
        inc = new int[maxSize];
    }

    void push(int x) {
        if (size < stack.length) stack[size++] = x;
    }

    int pop() {
        if (size == 0) return -1;
        int i = --size;
        int result = stack[i] + inc[i];
        if (i > 0) inc[i - 1] += inc[i];   // hand the pending increment down
        inc[i] = 0;
        return result;
    }

    void increment(int k, int val) {
        int i = Math.min(k, size) - 1;
        if (i >= 0) inc[i] += val;         // applied later, on pop
    }
}
TimeO(1) per operation
SpaceO(maxSize)
Problem 02 · Sorting
Sort Employees by Salary then Name
MediumConcept · no LeetCode equivalent Microsoft · Amazon · Goldman SachsComparator Chain
›
Problem

Sort a list of Employee objects: primary by salary descending, secondary by name ascending. Do not modify the Employee class.

Hints
▶Hint 1 — a nudge

You need two sort keys with different priorities, not one.

▶Hint 2 — the key idea

Comparator.comparingDouble(Employee::getSalary).reversed().thenComparing(Employee::getName). thenComparing only breaks ties.

Solution
▶Full solution
☕ Java
List<Employee> employees = ...;
employees.sort(
    Comparator.comparingInt((Employee e) -> e.salary).reversed()
              .thenComparing(e -> e.name)
);

// Or with lambda:
employees.sort((a,b) -> {
    if (a.salary != b.salary) return b.salary - a.salary; // desc salary
    return a.name.compareTo(b.name);              // asc name
});
TimeO(n log n)
SpaceO(1)
Problem 03 · Composition + HashMap
Design Underground System
🔗 LC 1396 - Design Underground System
Medium Objects as Map Values Amazon · Bloomberg · Uber
›
Problem

Design a subway system with checkIn(id, station, t), checkOut(id, station, t) and getAverageTime(start, end), the average travel time over all completed trips between two stations.

checkIn(1, "A", 3) · checkOut(1, "B", 8) · checkIn(2, "A", 10) · checkOut(2, "B", 16) · getAverageTime("A", "B") → 5.5
Hints
▶Hint 1 — a nudge

What has to be remembered between a check-in and the matching check-out?

▶Hint 2 — the key idea

Two maps: id → (station, time) for trips in progress, and "start,end" → (total, count) for finished trips. Small classes make the values self-describing.

Solution

Model the domain before writing methods: a CheckIn holds a station and a time, and a Route accumulates a total and a count. The service composes two HashMaps of those objects and keeps them private. A record is perfect for the immutable pair; a small mutable class suits the running totals. Every operation is O(1).

▶Full solution
☕ Java · Two Maps of Small Objects 
class UndergroundSystem {
    private record CheckIn(String station, int time) {}
    private static class Route { long total; int count; }

    private final Map<Integer, CheckIn> active = new HashMap<>();
    private final Map<String, Route> routes = new HashMap<>();

    void checkIn(int id, String station, int t) {
        active.put(id, new CheckIn(station, t));
    }

    void checkOut(int id, String station, int t) {
        CheckIn in = active.remove(id);
        Route r = routes.computeIfAbsent(in.station() + "," + station, k -> new Route());
        r.total += t - in.time();
        r.count++;
    }

    double getAverageTime(String start, String end) {
        Route r = routes.get(start + "," + end);
        return (double) r.total / r.count;
    }
}
TimeO(1) per operation
SpaceO(riders + routes)
Problem 04 · Encapsulated State
Design an Ordered Stream
🔗 LC 1656 - Design an Ordered Stream
Easy Class Design Bloomberg · Amazon
›
Problem

An ordered stream receives (idKey, value) pairs for ids 1..n in any order. Each insert returns the longest run of values that can now be emitted in id order, starting from the current pointer.

OrderedStream(5): insert(3, "c") → [] · insert(1, "a") → ["a"] · insert(2, "b") → ["b", "c"]
Hints
▶Hint 1 — a nudge

What must the object remember between two calls?

▶Hint 2 — the key idea

A String[] of size n + 1 and a private pointer starting at 1. After storing the value, collect values while the slot at the pointer is filled, moving the pointer forward.

Solution

The pointer is the object's hidden state, which is precisely why it is private — no caller can push it out of step with the array. Each id is emitted exactly once, so although a single insert can return many values, the total work across all inserts is O(n): amortised O(1) each.

▶Full solution
☕ Java · Array + Pointer 
class OrderedStream {
    private final String[] values;
    private int ptr = 1;

    OrderedStream(int n) { values = new String[n + 1]; }

    List<String> insert(int idKey, String value) {
        values[idKey] = value;
        List<String> chunk = new ArrayList<>();
        while (ptr < values.length && values[ptr] != null) {
            chunk.add(values[ptr++]);
        }
        return chunk;
    }
}
TimeO(n) total
SpaceO(n)
Problem 05 · Polymorphism
Peeking Iterator
🔗 LC 284 - Peeking Iterator
Medium Iterator / Decorator Google · Apple · Amazon
›
Problem

Wrap an existing Iterator<Integer> so that it also offers peek() — the next element without consuming it — alongside next() and hasNext().

over [1, 2, 3]: next → 1 · peek → 2 · next → 2 · next → 3 · hasNext → false
Hints
▶Hint 1 — a nudge

You cannot push a value back into the inner iterator, so what do you do with the one you read early?

▶Hint 2 — the key idea

Cache one element ahead: a nextVal field and a hasPeeked flag. peek fills the cache, next returns the cache if it is filled and otherwise delegates.

Solution

This is the decorator pattern. PeekingIterator implements Iterator<T> and wraps another one, so it can stand anywhere an iterator is expected — that substitutability is polymorphism in practice. Making it generic costs nothing and lets it wrap any element type, which is the whole argument for generics over raw types.

▶Full solution
☕ Java · Cache One Ahead 
class PeekingIterator<T> implements Iterator<T> {
    private final Iterator<T> inner;
    private T nextVal;
    private boolean hasPeeked = false;

    PeekingIterator(Iterator<T> iterator) { this.inner = iterator; }

    public T peek() {
        if (!hasPeeked) {
            nextVal = inner.next();
            hasPeeked = true;
        }
        return nextVal;
    }

    @Override
    public T next() {
        if (hasPeeked) {
            hasPeeked = false;
            return nextVal;
        }
        return inner.next();
    }

    @Override
    public boolean hasNext() {
        return hasPeeked || inner.hasNext();
    }
}
TimeO(1) per call
SpaceO(1)
