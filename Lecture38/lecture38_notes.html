Square Root Decomposition & Mo’s Algorithm

“When a tree is too much: split into blocks, or change the order of the questions.”

📚 Lecture 38 of 45 Phase 5 — Advanced Structures ⏱ 3 days 🎯 12 problems 💼 Google · Amazon · Meta · Microsoft
🌍
Why does this topic matter?
Lecture 37 gave you trees that answer range questions in O(log n). This short lecture gives you two simpler ideas that are sometimes the better tool. Square root decomposition splits an array into √n blocks and keeps a summary per block — slower than a tree, but written in minutes. Mo’s algorithm answers a whole batch of range questions by choosing a clever order to answer them in, which handles questions like “how many distinct values?” that no tree combines neatly.
By the end of this lecture you can
  • Split an array into √n blocks and answer range queries in O(√n)
  • Explain why √n is the right block size, from the balancing argument
  • Separate heavy and light values to bound the work per query
  • Order offline queries with Mo’s algorithm and slide a window between them
  • Track distinct counts and most-frequent values under add and remove
🧠
The picture to keep in your head: a book with chapters. To count the words from page 37 to page 912, nobody counts every page. You count the loose pages at each end, and for every complete chapter in between you read the total off a list. That is square root decomposition: whole blocks answered from a stored total, only the two ragged ends done by hand. Mo’s algorithm is a delivery driver who sorts the day’s stops by neighbourhood instead of driving them in the order they were booked — same deliveries, far less driving.
🎯
How often will you need this? Honestly: rarely in an interview, often in programming contests. A Fenwick or segment tree (Lecture 37) is usually the expected answer. This lecture is short because the two ideas in it — split into blocks and answer queries in a clever order — are worth knowing on their own, and because some questions (“how many distinct values in this range?”) are genuinely easier with them than with any tree.

🧱 Square Root Decomposition

Split an array of n items into blocks of about √n items each, and store one summary per block — its sum, its minimum, whatever the question needs. For n = 10,000 that is 100 blocks of 100. A range query then has three parts: the partial block at the left end, the whole blocks in the middle, and the partial block at the right end.

📐 Pseudocode · Build, Query, Update 
B ← floor(sqrt(n))                      // block size
blockSum ← array of (n ÷ B + 1) zeros
for i from 0 to n - 1:
    blockSum[i ÷ B] ← blockSum[i ÷ B] + a[i]

function query(l, r):                   // sum of a[l..r]
    total ← 0
    while l ≤ r and l mod B ≠ 0:        // ragged left end
        total ← total + a[l];  l ← l + 1
    while l + B - 1 ≤ r:                // whole blocks
        total ← total + blockSum[l ÷ B];  l ← l + B
    while l ≤ r:                        // ragged right end
        total ← total + a[l];  l ← l + 1
    return total

function update(i, value):              // point update in O(1)
    blockSum[i ÷ B] ← blockSum[i ÷ B] + (value - a[i])
    a[i] ← value
Structure Range query Point update Code size
Plain array O(n) O(1) Trivial
Prefix sums O(1) O(n) Tiny
Square root blocks O(√n) O(1) Small
Fenwick / segment tree O(log n) O(log n) Medium

Why √n, exactly?

With blocks of size B, a query touches at most n ÷ B whole blocks plus up to 2B loose items. Make B small and there are too many blocks; make it large and the ragged ends get long. The total, n ÷ B + 2B, is smallest when the two terms are about equal — which happens at B ≈ √n. That balancing argument is the whole idea, and it applies well beyond sums.

⚖️ Heavy and Light Elements

The same balancing trick works on values instead of positions. In an array of n items, at most √n different values can each appear more than √n times — there simply is not room for more. Call those values heavy. You can afford to precompute something for every heavy value (such as a prefix count), and handle every light value by brute force, because a light value never appears more than √n times. The worked example on Online Majority Element uses this split — with the cut-off at √n/2, for a reason the example explains.

🚚 Mo’s Algorithm

Some range questions are awkward for any tree: “how many distinct numbers are in a[l..r]?” does not combine neatly from two halves. But if you already know the answer for one range, you can get the answer for a neighbouring range cheaply — add one element on the right, or remove one on the left, updating a count table as you go. Mo’s algorithm makes that cheap-step idea fast by answering the queries in a smart order.

The order: group queries by which √n-block their left end falls in, and within a group sort by right end. Then walk a window from query to query. Inside one group the right end only moves forward, and the left end only wobbles within one block — so the total movement is about (n + q)√n steps instead of n × q.

📐 Pseudocode · Mo’s Algorithm — Count Distinct Values in Each Query Range 
B ← floor(sqrt(n))
order ← query indices sorted by (l ÷ B, then r)
count ← array of zeros;  distinct ← 0
curL ← 0;  curR ← -1                  // the current window is empty

function add(i):
    count[a[i]] ← count[a[i]] + 1
    if count[a[i]] = 1: distinct ← distinct + 1
function remove(i):
    count[a[i]] ← count[a[i]] - 1
    if count[a[i]] = 0: distinct ← distinct - 1

for q in order:
    (l, r) ← queries[q]
    while curR < r: curR ← curR + 1;  add(curR)       // grow right
    while curL > l: curL ← curL - 1;  add(curL)       // grow left
    while curR > r: remove(curR);  curR ← curR - 1    // shrink right
    while curL < l: remove(curL);  curL ← curL + 1    // shrink left
    answer[q] ← distinct

return answer                          // in the ORIGINAL query order
💡
Offline means you see every question first. Mo’s algorithm only works when all the queries are known before you answer any of them, so you can reorder them. That is called answering offline. If each query depends on the answer to the previous one, you are online, and Mo’s is off the table.

Frequency of Frequencies

Counting distinct values needs one table. Tracking the most frequent value as the window moves needs two: count[v] (how often value v appears) and howMany[f] (how many values currently appear exactly f times). When you remove an element, the maximum frequency can only drop by one, and howMany tells you instantly whether it did. This is the trick behind most “mode in a range” questions.

🧩 Choosing a Tool

The situation Reach for Why
Range sums, array never changes Prefix sums O(1) per query
Range sums with updates Fenwick tree (Lecture 37) O(log n) both, very little code
Range min/max with updates Segment tree (Lecture 37) Min and max are not invertible
Updates, and a tree feels like too much code Square root blocks O(√n), written in five minutes
Distinct count or mode in many ranges, all known upfront Mo’s algorithm Answers do not merge, but they slide
Values in a small range (say −50 to 50) Counting buckets Scan 101 buckets instead of sorting

⚠️ Complexity & Classic Bugs

Operation Cost Note
Build the blocks O(n)
Block range query O(√n) Two ragged ends plus whole blocks
Block point update O(1) Update the item and its block
Mo’s algorithm, q queries O((n + q)√n) Plus O(q log q) to sort the queries
Heavy/light precompute O(n√n) worst case Prefix counts for at most √n heavy values
Bug Symptom Fix
Block size of 0 when n is tiny Division by zero Use max(1, floor(sqrt(n)))
Returning Mo’s answers in sorted order Answers attached to the wrong queries Store each answer at its original index
Shrinking before growing the window Removing an element that was never added; negative counts Grow first (curR up, curL down), then shrink
Off-by-one on the whole-block loop Double-counts or skips the last full block Loop while l + B − 1 ≤ r
Forgetting to update the block summary Queries ignore the update Update both the item and its block
Using Mo’s on online queries Impossible to reorder Use a tree, or rethink the problem
A count array sized by value on huge values Out of memory Compress the values first
🔍
How to spot it. A pile of range queries, all given up front, asking something that does not split into halves — distinct count, mode, pairs of equal values. Or a constraint around 10⁵ where you would like a simpler alternative to a tree. And if the values are small, try buckets before anything clever.

Problem 01 · The Add/Remove Primitive
Count the Number of Good Subarrays
🔗 LC 2537 - Count the Number of Good Subarrays
Medium Window with a running pair count Amazon · Google
›
Problem

Count the subarrays that contain at least k pairs of equal elements (i < j with nums[i] = nums[j]).

nums = [3,1,4,3,2,2,4], k = 2 → 4
Hints
▶Hint 1 — a nudge

When one more copy of a value x enters a window that already holds c copies, how many new equal pairs appear?

▶Hint 2 — the key idea

Exactly c. And removing a copy removes c − 1 pairs. So the pair count updates in O(1) per step — exactly the cheap add/remove step Mo’s algorithm is built on.

Solution

The whole trick is the O(1) update: adding a value that already appears c times creates c new pairs, removing one destroys (c − 1). With that, a sliding window works. For each right end, shrink the left end while the window still has at least k pairs; then every start position before the current left end gives a good subarray. This add/remove bookkeeping is the same primitive Mo’s algorithm uses — here the queries happen to arrive in a convenient order already.

▶Full solution
📐 Pseudocode · Pairs Change by the Current Count 
function countGood(nums, k):
    count ← empty map;  pairs ← 0;  left ← 0;  result ← 0
    for right from 0 to length(nums) - 1:
        x ← nums[right]
        pairs ← pairs + count[x]            // x pairs with every copy already here
        count[x] ← count[x] + 1
        while pairs ≥ k:                    // window [left..right] is good
            y ← nums[left]
            count[y] ← count[y] - 1
            pairs ← pairs - count[y]        // lost pairs with the copies that remain
            left ← left + 1
        result ← result + left              // starts 0..left-1 all give good subarrays
    return result
TimeO(n)
SpaceO(n)
Problem 02 · Small Values → Buckets
Sliding Subarray Beauty
🔗 LC 2653 - Sliding Subarray Beauty
Medium Counting buckets in a window Amazon · Google
›
Problem

For every window of length k, report its beauty: the x-th smallest negative number in the window, or 0 if there are fewer than x negatives.

nums = [1,-1,-3,-2,3], k = 3, x = 2 → [-1,-2,-2]
Hints
▶Hint 1 — a nudge

Sorting every window costs O(k log k) each time. Look at the constraints on the values — how many different values can there be?

▶Hint 2 — the key idea

Values lie between −50 and 50. Keep a count for each of the 50 negative values; the x-th smallest is found by walking those 50 buckets.

Solution

When the values are small, bucket them. A window update is O(1) — add one count, remove one count — and a query walks at most 50 buckets from −50 upwards until x negatives have been passed. That makes the whole thing O(n × 50), independent of k. It is the same “fixed-size summary per block” idea as square root decomposition, applied to the value range instead of the positions.

▶Full solution
📐 Pseudocode · 50 Buckets per Window 
function getSubarrayBeauty(nums, k, x):
    count ← array of 51 zeros               // count[v] for v = -50..-1, stored at index -v
    result ← empty list
    for i from 0 to length(nums) - 1:
        if nums[i] < 0: count[-nums[i]] ← count[-nums[i]] + 1
        if i ≥ k and nums[i - k] < 0:       // the element leaving the window
            count[-nums[i - k]] ← count[-nums[i - k]] - 1
        if i ≥ k - 1:
            seen ← 0;  beauty ← 0
            for v from 50 down to 1:        // -50, -49, ... smallest first
                seen ← seen + count[v]
                if seen ≥ x: beauty ← -v;  break
            result.append(beauty)
    return result
TimeO(n · 50)
SpaceO(1)
Problem 03 · Reorder the Queries
Count Zero Request Servers
🔗 LC 2747 - Count Zero Request Servers
Medium Offline queries + sliding window Amazon · Google
›
Problem

Given server logs [serverId, time] and queries asking about the interval [q − x, q], return, for each query, how many of the n servers received no requests in that interval.

n = 3, logs = [[1,3],[2,6],[1,5]], x = 5, queries = [10,11] → [1,2]
Hints
▶Hint 1 — a nudge

Answering each query by scanning every log is O(logs × queries). What if you answered the queries in increasing order of time instead of the order given?

▶Hint 2 — the key idea

Sort the logs by time and the queries by time. The window [q − x, q] then only ever moves forward: add logs entering on the right, remove logs leaving on the left, and keep a count of servers with at least one request.

Solution

This is the core of Mo’s algorithm in its simplest form: answer the queries in a different order from the one they were asked in, so that each step reuses the previous answer. Once queries are sorted by time, both window ends only move forward, so every log is added once and removed once. The only extra care is to remember each query’s original position and write its answer there.

▶Full solution
📐 Pseudocode · Sort Queries, Slide Once 
function countServers(n, logs, x, queries):
    sort logs by time
    order ← query indices sorted by queries[i]
    count ← array of n + 1 zeros;  active ← 0     // servers with ≥ 1 request
    lo ← 0;  hi ← 0;  answer ← array of length(queries)
    for qi in order:
        q ← queries[qi]
        while hi < length(logs) and logs[hi].time ≤ q:          // entering
            s ← logs[hi].server
            if count[s] = 0: active ← active + 1
            count[s] ← count[s] + 1;  hi ← hi + 1
        while lo < hi and logs[lo].time < q - x:                // leaving
            s ← logs[lo].server
            count[s] ← count[s] - 1
            if count[s] = 0: active ← active - 1
            lo ← lo + 1
        answer[qi] ← n - active                                  // original position
    return answer
TimeO(L log L + Q log Q)
SpaceO(n + Q)
Problem 04 · Heavy and Light
Online Majority Element In Subarray
🔗 LC 1157 - Online Majority Element In Subarray
Hard Square root split by frequency Google · Amazon
›
Problem

Build a structure over an array that answers query(left, right, threshold): the element appearing at least threshold times in arr[left..right], or −1. It is guaranteed that 2 × threshold > right − left + 1, so the answer is a strict majority.

arr = [1,1,2,2,1,1]; query(0,5,4) → 1, query(0,3,3) → −1, query(2,3,2) → 2
Hints
▶Hint 1 — a nudge

Short ranges are easy: a single Boyer-Moore pass finds the majority candidate. What about long ranges — which values could possibly be a majority of a long range?

▶Hint 2 — the key idea

A range longer than √n needs more than √n/2 copies of its majority, so only values appearing more than √n/2 times in the whole array can win it — and there are at most 2√n of those. Give each such heavy value a prefix-count array; handle short ranges (length ≤ √n) by brute force.

Solution

The split is by frequency, and the threshold is √n. A range longer than √n needs a majority of more than √n/2 copies, so its answer must appear more than √n/2 times in the whole array — and at most 2√n values do, each checked in O(1) with prefix counts. (Setting the cut-off at √n instead is a tempting bug: a value with, say, 0.7√n copies can still be the majority of a range just over √n long.) A range of length at most √n is scanned directly with Boyer-Moore voting. Every query is therefore O(√n). Binary search on each value’s positions, or a segment tree of Boyer-Moore votes, also work — but the heavy/light split is the square-root idea in its purest form.

▶Full solution
📐 Pseudocode · Prefix Counts for Heavy Values, Brute Force for Short Ranges 
function MajorityChecker(arr):
    n ← length(arr);  S ← floor(sqrt(n))
    heavy ← values appearing more than S ÷ 2 times in arr    // at most 2S of them
    for each v in heavy:
        pref[v] ← prefix counts of v over arr                 // pref[v][i] = copies in arr[0..i-1]

function query(left, right, threshold):
    if right - left + 1 ≤ S:                                  // short range: vote directly
        cand ← Boyer-Moore majority candidate of arr[left..right]
        return cand if count of cand in arr[left..right] ≥ threshold else -1
    for each v in heavy:                                      // long range: only heavy values qualify
        if pref[v][right + 1] - pref[v][left] ≥ threshold:
            return v
    return -1
TimeO(√n) per query
SpaceO(n√n)
