Attacking an Unseen Problem

“You do not need to see the answer. You need a routine for when you don’t.”

📚 Lecture 2 of 45 Phase 1 — Foundations ⏱ 3 days 🎯 15 problems 💼 Google · Amazon · Meta · Microsoft
🌍
Why does this topic matter?
Knowing fifty algorithms does not help if you freeze in front of a problem you have never seen — and in an interview, every problem is one you have never seen. This lecture gives you a routine for that moment: six steps that take you from a blank page to a correct answer, and then to a fast one. It is the most reusable thing in the course; every later lecture is really just more material for Step 5.
By the end of this lecture you can
  • Restate a problem and check it with your own worked example
  • Turn the input size into a target Big-O before designing anything
  • State a brute force and find the work it repeats
  • Use five concrete moves when you are stuck
  • Explain your thinking out loud the way an interviewer wants to hear it
☕
Still no Java — still on purpose. Everything here happens before you write a line of code, so it works in any language. Solve the practice problems on paper; you will code them after Lecture 4.

🧭 The Six Steps

Good problem-solvers are not people who see the answer instantly. They are people who have a routine for when they don’t. Here is the routine this whole course uses. Each step has one job, and skipping one is how most wrong answers happen.

Step The question you ask What you write down
1. Understand What exactly goes in, and what must come out? The problem in your own words, plus two worked examples
2. Size it up How big can the input be? The target Big-O, from Lecture 1’s table
3. Brute force What is the dumbest thing that is definitely correct? That solution and its Big-O
4. Find the waste Which work is repeated, or unnecessary? The bottleneck, in one sentence
5. Match a pattern Have I seen a problem shaped like this? The tool you will use
6. Test on paper Does it work on the awkward inputs? Three edge cases, traced by hand
🧠
It is how a doctor works. A good doctor does not guess a diagnosis from the waiting room. They listen to the symptoms (understand), take measurements (size it up), rule out the obvious (brute force), look for what does not fit (find the waste), match it to conditions they know (pattern), and check before prescribing (test). You are doing the same thing, with code as the prescription.

📖 Step 1 — Understand the Problem

Most failed interviews fail here, silently. The candidate solves a slightly different problem from the one that was asked. The cure is cheap: before anything else, restate the problem and work two examples by hand.

Ask this Because
Can the input be empty? Your loop may never run, or crash on a[0]
Can there be duplicates? “Find the number” changes meaning if it appears twice
Can values be negative or zero? Many tricks only work for positive numbers
Is the input sorted? Sorted input unlocks faster tools
What should I return if there is no answer? −1, an empty list, false — they are different programs
Does order in the output matter? Sometimes any valid answer is accepted
💡
Work an example nobody gave you. The examples in a problem are chosen to be friendly. Make up one of your own — a little bigger, a little stranger — and solve it by hand. If you cannot do it by hand, you are not ready to tell a computer how.

🎯 Step 2 — Size It Up

Read the constraints and turn them into a target, exactly as in Lecture 1. If n can be 100,000, you know before thinking about the method that you need roughly O(n log n) or better. That one fact rules out whole families of ideas and tells you where to look.

🔨 Step 3 — Say the Brute Force Out Loud

Always state the simplest correct solution first, even if it is far too slow. It proves you understood the problem, it gives you something to test the clever version against, and — surprisingly often — it is already fast enough.

📐 Pseudocode · A Brute Force for "Find Two Numbers That Add to a Target" 
function findPair(a, target):
    for i from 0 to length(a) - 1:
        for j from i + 1 to length(a) - 1:      // every pair, once
            if a[i] + a[j] = target:
                return (i, j)
    return none

// Correct, obviously so, and O(n²). Now we have something to improve.

🔍 Step 4 — Find the Waste

Look at the brute force and ask: what is it doing more than once? In the pair search, for each a[i] the inner loop is really asking one question — “is target − a[i] somewhere in the list?” — and answers it by scanning, every single time. That repeated scan is the bottleneck.

🔍
Name the bottleneck in one sentence. “For every item I rescan the whole list to look something up.” Once you can say that, the fix is usually obvious: make the lookup fast. A structure that answers “is this value present?” instantly turns O(n²) into O(n). That structure is a hash set, and it gets its own lecture (16).

🧩 Step 5 — Match a Pattern

After enough problems you start to recognise shapes. This course teaches about twenty of them. You do not know them yet — but it helps to see now that the signals are learnable, and where each one is taught.

If the problem says… Reach for… Taught in
“is this value present?” many times A hash set or hash map Lecture 16
The input is sorted Binary search or two pointers Lectures 13, 25
“a contiguous piece” / subarray / substring Sliding window or prefix sums Lectures 25, 26
“the k largest” / “top k” A heap Lecture 20
“all combinations” / “every arrangement” Backtracking Lecture 24
“shortest path” on a grid or network Breadth-first search Lecture 21
“count the ways” / “minimum cost” with choices Dynamic programming Lecture 32
The locally best choice looks safe Greedy Lecture 29

🧪 Step 6 — Test on Paper

Before running anything, trace your solution on three awkward inputs: the smallest possible (often empty or one item), one where every value is the same, and one at the extreme end of the constraints. Lecture 3 turns this into a full checklist.

🚶 A Full Walkthrough

Here are all six steps on the pair problem from Step 3, the way you would say them out loud in an interview.

Step What you say
Understand “I return the positions of two different numbers that add to the target. Can the same position be used twice? No. Is there always an answer? I’ll assume so, but return none otherwise.”
Size it up “Up to 10,000 numbers. Every pair is 50 million checks — borderline. I’d like O(n log n) or better.”
Brute force “Check every pair: O(n²), O(1) space. Correct, but slow.”
Find the waste “For each number I rescan for its partner. The rescan is the waste.”
Match a pattern “Fast lookup means a hash map from value to position. One pass: before storing a number, ask whether its partner is already stored.”
Test “[3, 3], target 6: first 3 is stored, second 3 finds it — returns (0, 1), not (0, 0). Good.”
📐 Pseudocode · The Improved Version 
function findPair(a, target):
    seen ← empty map                    // value → position
    for i from 0 to length(a) - 1:
        need ← target - a[i]
        if need in seen:                // is the partner already here?
            return (seen[need], i)
        seen[a[i]] ← i                  // store AFTER checking: never pairs with itself
    return none

// O(n) time, O(n) space. The trade: memory for speed.

🤔 When You Are Stuck

Everyone gets stuck. The difference is having moves to make instead of staring. Try these in order.

Move Why it works
Solve a tiny example completely by hand Your hands often find the method before your head does
Draw it Arrays as boxes, pointers as arrows — pictures reveal structure
Make the problem easier Sorted input? Only positive numbers? Solve that, then add the difficulty back
Look at the answer’s shape If the answer is a single number, maybe it has a formula
Work backwards from the end What must be true just before the answer is known?
Say what you would do with unlimited time That is your brute force — improve it one bottleneck at a time

🗣️ Talking While You Work

In an interview, a correct answer reached in silence scores lower than a nearly-correct one explained well. The interviewer is grading how you think. Say what you are about to try and why, say when you notice a problem, and say the Big-O of every version you propose.

💡
Silence is the only wrong answer. “I don’t see the fast version yet, so let me write the brute force and look for repeated work” is a strong sentence. It shows a method, and it buys you time.

⚠️ Complexity & Classic Mistakes

These are mistakes of process. Every one of them is common, and every one is prevented by one of the six steps.

Mistake What happens The step that prevents it
Coding immediately You solve a slightly different problem 1 — Understand
Ignoring the constraints A correct O(n²) solution times out 2 — Size it up
Skipping the brute force No baseline, nothing to test against 3 — Brute force
Optimising the wrong part Clever code, same Big-O 4 — Find the waste
Forcing a favourite technique Sliding window on a problem that is not contiguous 5 — Match honestly
Testing only the given examples Passes the samples, fails on empty input 6 — Test on paper
Going silent when stuck The interviewer cannot give credit or hints Talk while you work

💪 In-Lecture Practice Problems

Four problems, each solved by one of the moves in this lecture rather than by a data structure. For each one, try the steps yourself before opening the hints.

Problem 01 · All Six Steps
Maximum Nesting Depth of the Parentheses
🔗 LC 1614 - Maximum Nesting Depth of the Parentheses
Easy Running counter Amazon · Google
›
Problem

Given a valid expression with parentheses, return how deeply the parentheses are nested at their deepest point.

s = "(1+(2*3)+((8)/4))+1" → 3
Hints
▶Hint 1 — a nudge

Step 1: solve the example by hand. How did you know the depth was 3 — what did you keep track of as your eyes moved right?

▶Hint 2 — the key idea

You counted: up one at every "(", down one at every ")". The deepest you ever got is the answer. No stack or recursion needed.

Solution

A small problem, but walk all six steps. Understand: the string is always valid, other characters are irrelevant. Size: up to 100 characters — anything works. Brute force: for every position, count the unmatched openings before it — O(n²). Waste: each count redoes the previous one plus a single character. Pattern: keep a running counter instead. Test: a string with no parentheses returns 0. The whole solution came from noticing what your own hand did.

▶Full solution
📐 Pseudocode · One Counter, One Pass 
function maxDepth(s):
    depth ← 0;  best ← 0
    for each ch in s:
        if ch = '(':
            depth ← depth + 1
            best ← max(best, depth)
        else if ch = ')':
            depth ← depth - 1
    return best
TimeO(n)
SpaceO(1)
Problem 02 · Solve It by Hand
Partitioning Into Minimum Number Of Deci-Binary Numbers
🔗 LC 1689 - Partitioning Into Minimum Number Of Deci-Binary Numbers
Medium Look at the answer’s shape Amazon · Google
›
Problem

A deci-binary number uses only the digits 0 and 1 (like 101 or 1100). What is the fewest deci-binary numbers that add up to the given number n?

n = "32" → 3   (10 + 11 + 11)   |   n = "82734" → 8
Hints
▶Hint 1 — a nudge

Forget algorithms. Break 32 into deci-binary numbers by hand, then 82734. What limits how few you can use?

▶Hint 2 — the key idea

Each deci-binary number adds at most 1 to each digit position. A digit of 8 needs at least 8 of them — and 8 is always enough.

Solution

This is the “look at the answer’s shape” move from the stuck-list. The answer is one number, and the examples (32 → 3, 82734 → 8) give it away once you work them by hand: it is the largest digit. The reasoning: every deci-binary number contributes at most 1 to each column, so a column with digit d needs at least d numbers; and d numbers are enough, because each one can put a 1 wherever that column still needs it. A problem labelled Medium, solved by one pass and no data structures — because the thinking happened on paper.

▶Full solution
📐 Pseudocode · The Answer Is the Largest Digit 
function minPartitions(n):
    best ← 0
    for each ch in n:
        best ← max(best, digit value of ch)
        if best = 9: return 9           // cannot do better than 9
    return best
TimeO(n)
SpaceO(1)
Problem 03 · Small Examples First
Maximum Number of Coins You Can Get
🔗 LC 1561 - Maximum Number of Coins You Can Get
Medium Sort, then a greedy choice found by hand Amazon · Google
›
Problem

There are 3n piles of coins. Each round you pick any 3 piles; Alice takes the largest, you take the next, Bob takes the smallest. Maximise the coins you collect.

piles = [2,4,1,2,7,8] → 9   (you get 7 + 2)
Hints
▶Hint 1 — a nudge

Try every grouping for the six-pile example by hand. Which piles should Bob always get?

▶Hint 2 — the key idea

Give Bob the smallest piles — he takes the minimum anyway. Then from what is left, Alice takes the biggest and you take the second biggest, round after round.

Solution

Steps 3 and 4 in action. The brute force tries every way to form triples — exponential, hopeless for 10⁵ piles. Working the example by hand shows the structure: Bob’s pile is wasted, so it should be as small as possible, and you always sit just below Alice. After sorting, that means Bob takes the bottom third and you take every second pile from the top. Sorting dominates, so the whole thing is O(n log n) — which Step 2 said was the target.

▶Full solution
📐 Pseudocode · Sort, Then Take Every Second From the Top 
function maxCoins(piles):
    sort(piles)                         // smallest first
    n ← length(piles) ÷ 3
    total ← 0
    i ← length(piles) - 2               // second largest
    repeat n times:
        total ← total + piles[i]        // your pile
        i ← i - 2                       // skip Alice's next pile
    return total
// Bob silently gets piles[0 .. n-1], the smallest third.
TimeO(n log n)
SpaceO(1)
Problem 04 · Draw It
Number of Laser Beams in a Bank
🔗 LC 2125 - Number of Laser Beams in a Bank
Medium Draw it, then count Amazon
›
Problem

A bank floor plan is a grid of rows; "1" marks a security device. A beam joins every device on one row to every device on the next non-empty row. Count the beams.

bank = ["011001","000000","010100","001000"] → 8
Hints
▶Hint 1 — a nudge

Draw the grid and draw the beams. Do empty rows affect anything?

▶Hint 2 — the key idea

Beams only connect consecutive non-empty rows. Between a row with a devices and the next with b, there are a × b beams.

Solution

The picture does the work. Once drawn, empty rows vanish (beams pass straight through them) and each pair of neighbouring non-empty rows contributes the product of their device counts. The brute force would compare every device with every other device — O((rows × cols)²) — but the drawing shows that only the count per row matters, so one pass is enough.

▶Full solution
📐 Pseudocode · Multiply Neighbouring Counts 
function numberOfBeams(bank):
    prev ← 0;  total ← 0
    for each row in bank:
        c ← count of '1' in row
        if c > 0:                        // empty rows are skipped
            total ← total + prev × c
            prev ← c
    return total
TimeO(rows × cols)
SpaceO(1)
