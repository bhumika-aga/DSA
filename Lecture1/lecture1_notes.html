How Fast Is It? — Complexity Analysis

“Not how long it takes — how the time grows.”

📚 Lecture 1 of 45 Phase 1 — Foundations ⏱ 4 days 🎯 20 problems 💼 Google · Amazon · Meta · Microsoft
🌍
Why does this topic matter?
Two solutions can give the same answer and still be completely different: one finishes before you blink, the other would still be running next year. The difference is almost never the computer — it is how the amount of work grows as the input gets bigger. This lecture gives you a vocabulary for that growth, called Big-O, and a handful of rules for reading it straight off a piece of code. Every later lecture assumes you can do this, and every interviewer will ask.
📖
Unfamiliar word? Every term used in this course is defined in plain English in the Glossary, with a link to the lecture that teaches it.
By the end of this lecture you can
  • Read the course's pseudocode notation fluently
  • Say what O(1), O(log n), O(n), O(n log n), O(n²) and O(2ⁿ) mean in plain words
  • Work out the Big-O of a piece of code from its loops alone
  • Tell time from space, and worst case from amortised
  • Read a problem's size limit and name the speed your solution needs
☕
No Java yet — that is on purpose. The first three lectures teach you how to think about a problem before you learn the language you will solve it in. Every example here is written in plain pseudocode, and every exercise can be done with a pencil. You write your first Java in Lecture 4; come back to these assignments then and code them.

📖 Reading the Pseudocode

Every algorithm in this course is written in the same small notation. It is not a real programming language — it is a way of writing steps precisely enough that nothing is ambiguous. Ten symbols cover almost all of it.

You will see It means
x ← 5 Put the value 5 into a box called x. (Read the arrow as “becomes”.)
a[i] The item at position i in the list a. Positions start at 0.
length(a) How many items the list a holds.
for i from 0 to n - 1: Repeat the indented lines with i = 0, 1, 2, … up to and including n − 1.
while x > 1: Keep repeating the indented lines as long as the condition is true.
if … : … else: … Do one thing or the other depending on the condition.
function f(n): … return r A named, reusable set of steps that takes n in and hands r back.
÷ and mod Whole-number division (7 ÷ 2 = 3) and the remainder left over (7 mod 2 = 1).
≤ ≥ ≠ At most, at least, not equal.
// like this A comment: a note for the human reader. The computer ignores it.
💡
Indentation is meaning. Lines pushed further right belong to the line above them. That is how you tell what is inside a loop and what comes after it.

⏱️ Counting Steps, Not Seconds

How long does a program take? Measuring with a stopwatch sounds natural, but it answers the wrong question: a laptop and a phone give different times for the same code, and so does the same laptop on a busy day. What stays the same everywhere is how many steps the program takes — and, more usefully, how that number grows when the input gets bigger.

📐 Pseudocode · Find the Largest Number 
function largest(a):
    best ← a[0]
    for i from 1 to length(a) - 1:     // look at every other item once
        if a[i] > best:
            best ← a[i]
    return best

// A list of 10 items: about 10 steps. A list of 1,000: about 1,000.
// Double the list, double the work. That is the entire idea of growth.
🧠
Think of it like a party. One recipe says “bake one cake per guest”: double the guests and you double the baking. Another says “every guest shakes hands with every other guest”: double the guests and the handshakes quadruple. Both are fine at a dinner for six. Only one of them survives a wedding for six hundred. Complexity analysis is just the habit of asking which kind of recipe you wrote.

📈 Big-O in Plain Words

Big-O is a short label for the shape of that growth. You say “O(n)” out loud as “order n”, and it means: when the input doubles, the work roughly doubles. The letter n is always “the size of the input” — how many items are in the list, how many characters are in the string.

The Growth Ladder

There are only seven labels you will meet regularly. Learn this table and you can predict whether any solution will finish in time.

Big-O Name n = 10 n = 1,000 n = 1,000,000 Typical example
O(1) constant 1 1 1 Read a[5]
O(log n) logarithmic 3 10 20 Halve the search space each step
O(n) linear 10 1,000 1,000,000 Look at each item once
O(n log n) n-log-n 33 10,000 20,000,000 A good sort
O(n²) quadratic 100 1,000,000 10¹² — hours Compare every pair
O(2ⁿ) exponential 1,024 more than atoms in the universe — Try every subset
O(n!) factorial 3,628,800 — — Try every ordering
🔍
The one number to remember. A computer does roughly 100 million (10⁸) simple steps per second. Put your step count next to that and you know immediately whether something takes a millisecond, a second, or a lifetime.

🔎 Reading Cost From Code

You do not need to run anything to find the Big-O. Four rules, applied to the structure of the code, get you there.

📐 Pseudocode · Rule 1 — Steps One After Another Add 
for i from 0 to n - 1: print(a[i])      // n steps
for i from 0 to n - 1: print(a[i])      // n more steps

// Total: n + n = 2n  →  O(n). Two separate passes are still "linear".
📐 Pseudocode · Rule 2 — A Loop Inside a Loop Multiplies 
for i from 0 to n - 1:
    for j from 0 to n - 1:              // runs n times for EACH i
        compare(a[i], a[j])

// Total: n × n = n²  →  O(n²). This is the handshake recipe.
📐 Pseudocode · Rule 3 — Halving Gives log n 
while n > 1:
    n ← n ÷ 2                           // 1000 → 500 → 250 → … → 1

// How many halvings until you reach 1? About log₂(n): 10 for a thousand,
// 20 for a million. That is why O(log n) feels almost free.
📐 Pseudocode · Rule 4 — A Fixed-Size Loop Is Constant 
for c from 'a' to 'z':                  // always 26 times, whatever n is
    count[c] ← 0

// 26 does not grow with the input, so this is O(1).
⚠️
The trap: an inner loop that starts later. for j from i + 1 to n - 1 looks cheaper than a full inner loop — and it is, by half. But half of n² is still n² growth. Rule 5 below explains why the half disappears.

The Simplification Rules

Rule Example Why
Drop constant multipliers 3n → O(n) Doubling n still doubles 3n; the 3 does not change the shape.
Keep only the biggest term n² + n + 100 → O(n²) At n = 1,000,000 the n² term is a million times larger than n.
Different inputs keep different letters two lists: O(n + m), not O(n) If one list is huge and the other tiny, a single letter hides that.
Nested loops over different inputs multiply O(n · m) Every row of one against every item of the other.

💾 Space: How Much Memory

Time is not the only cost. Space complexity counts the extra memory an algorithm needs as the input grows. Interviewers usually mean auxiliary space — memory beyond the input you were given.

📐 Pseudocode · Same Answer, Different Space 
function reverseCopy(a):             // O(n) extra space
    b ← new list of length(a)
    for i from 0 to length(a) - 1:
        b[i] ← a[length(a) - 1 - i]
    return b

function reverseInPlace(a):          // O(1) extra space
    left ← 0;  right ← length(a) - 1
    while left < right:
        swap a[left] and a[right]
        left ← left + 1;  right ← right - 1
💡
Recursion uses space too. Every call that has not finished yet is waiting in memory. A function that calls itself n levels deep uses O(n) space even if it never creates a list. You will see why in Lecture 8.

🌳 Recursion: Count the Calls

When a function calls itself, draw the calls as a tree. The total cost is simply how many calls there are × the work inside each call. You will learn to write recursion in Lecture 8; for now, only learn to count it.

Shape of the calls Number of calls Cost Example
One call, input shrinks by 1 n O(n) Factorial
One call, input halves log n O(log n) Binary search
Two calls, input halves, O(n) work to combine log n levels × n per level O(n log n) Merge sort
Two calls, input shrinks by 1 about 2ⁿ O(2ⁿ) Naive Fibonacci

The last row is why some innocent-looking code never finishes: two calls per level doubles the work at every level. Lecture 8 shows how remembering answers you have already computed turns that 2ⁿ back into n.

📦 Amortised Cost

Some operations are usually cheap and occasionally expensive. A growable list is the classic case: adding an item is instant — until the list is full, at which point it copies everything into a space twice as big.

🧠
Like moving house. Most years you do not move at all. When you do, it is a huge job. But if you move once every ten years, the effort averaged over the years is small. Because the list doubles each time, the copies add up to at most about 2n work over n additions — so each addition is O(1) amortised, even though a single one can cost O(n).

🎲 Best, Average and Worst Case

The same code can be fast or slow depending on the input. Searching a list for a value finds it instantly if it is first (best case), or looks at everything if it is last or missing (worst case).

Case Linear search When people mean it
Best O(1) — it was first Almost never worth quoting
Average O(n) — about half the list When inputs are random
Worst O(n) — last or missing The default in interviews unless you are told otherwise

🎯 Constraints Tell You the Target

Every interview problem states how big the input can be. Combined with the 10⁸-steps-per-second rule, that number tells you which Big-O you need before you have any idea how to solve it. This is the single most useful habit in this lecture.

If n is at most… You can afford… Which usually means
10–11 O(n!) Try every ordering
20–25 O(2ⁿ) Try every subset
100–500 O(n³) Three nested loops
1,000–5,000 O(n²) Check every pair
100,000–1,000,000 O(n log n) or O(n) Sort once, or a single pass
1,000,000,000 or more O(log n) or O(1) Halving, or a formula
🔍
Try it now. A problem says the list can hold up to 100,000 numbers. Checking every pair is 10¹⁰ steps — about 100 seconds. So the pair-checking solution is out before you write it, and you already know to look for something n log n or better.

⚠️ Complexity & Classic Bugs

The mistakes below are mistakes in analysis, not in code. Each one makes you promise a speed your solution does not have.

Mistake What it looks like Fix
Hidden loops inside one line if x in list inside a loop looks O(1) but scans the list: O(n²) overall Ask what every built-in call costs
Forgetting that sorting costs “Sort, then one pass — O(n)” The sort alone is O(n log n)
Keeping constants “O(2n)”, “O(n/2)” Both are O(n)
Adding nested loops Two nested loops called O(2n) Nested multiplies: O(n²)
One letter for two inputs Two lists of different sizes called O(n) Use n and m: O(n + m) or O(n · m)
Ignoring recursion space A recursive solution called O(1) space Count the depth of the calls
Confusing amortised with worst case “Every append is O(1)” O(1) amortised; one append can be O(n)
Mixing up halving and stepping A loop doing i ← i + 2 called O(log n) Adding a constant is still O(n); only multiplying or dividing gives log

💪 In-Lecture Practice Problems

Five problems, each teaching a different way to read cost. You do not need to write code yet — for each one, read the problem, state the obvious solution and its Big-O, then read the solution and compare.

Problem 01 · Reading Nested Loops
Count Good Triplets
🔗 LC 1534 - Count Good Triplets
Easy Brute force, counted exactly Amazon · Google
›
Problem

Count the triplets i < j < k where every pair of the three values differs by at most given limits a, b and c.

arr = [3,0,1,1,9,7], a = 7, b = 2, c = 3 → 4
Hints
▶Hint 1 — a nudge

Write the obvious solution: three loops. Now count — how many times does the innermost line run for a list of length n?

▶Hint 2 — the key idea

Roughly n × n × n ÷ 6, which is O(n³). The problem says n ≤ 100, so that is about 170,000 steps — perfectly fast. The slow solution is the right one here.

Solution

This is the lecture’s most important lesson in disguise: read the constraint before you optimise. With n ≤ 100, O(n³) is roughly a million steps at worst — a hundredth of a second. A cleverer solution would take longer to write and could hide bugs, for no benefit. Three nested loops multiply (Rule 2), and starting each loop after the previous one only divides by a constant, which Big-O ignores.

▶Full solution
📐 Pseudocode · Three Loops, and That Is Fine 
function countGoodTriplets(arr, a, b, c):
    n ← length(arr);  count ← 0
    for i from 0 to n - 1:
        for j from i + 1 to n - 1:
            for k from j + 1 to n - 1:          // innermost line runs ≈ n³ ÷ 6 times
                if |arr[i] - arr[j]| ≤ a and |arr[j] - arr[k]| ≤ b and |arr[i] - arr[k]| ≤ c:
                    count ← count + 1
    return count

// n ≤ 100  →  at most ~166,000 checks. Done in well under a millisecond.
TimeO(n³)
SpaceO(1)
Problem 02 · Simulate, Then Think
Count of Matches in Tournament
🔗 LC 1688 - Count of Matches in Tournament
Easy Simulation → formula Amazon · Google
›
Problem

In a knockout tournament of n teams, each round pairs teams up and the losers leave (an odd team out advances for free). How many matches are played in total?

n = 7 → 6   |   n = 14 → 13
Hints
▶Hint 1 — a nudge

Simulate the rounds: each round roughly halves the teams. How many rounds is that, and what does each round cost?

▶Hint 2 — the key idea

Now look at the answers: 7 → 6, 14 → 13. Every match knocks out exactly one team, and all but one team must be knocked out.

Solution

Two correct answers with very different costs. The simulation halves the number of teams each round, so it runs about log₂ n rounds — O(log n), already fast. But one sentence of reasoning beats it: each match eliminates exactly one team, and n − 1 teams must be eliminated, so the answer is n − 1 in O(1). Whenever a loop produces a suspiciously simple pattern, stop and ask whether there is a reason behind it.

▶Full solution
📐 Pseudocode · Halving Loop vs One Line 
function numberOfMatchesSimulated(n):     // O(log n): teams halve each round
    matches ← 0
    while n > 1:
        matches ← matches + n ÷ 2
        n ← (n + 1) ÷ 2                     // winners, plus the free pass if odd
    return matches

function numberOfMatches(n):              // O(1)
    return n - 1                          // every match removes exactly one team
TimeO(1)
SpaceO(1)
Problem 03 · Same Answer, Different Cost
Count Operations to Obtain Zero
🔗 LC 2169 - Count Operations to Obtain Zero
Easy Repeated subtraction → division Amazon
›
Problem

Given two numbers, repeatedly subtract the smaller from the larger until one of them is zero. Return how many subtractions that takes.

num1 = 2, num2 = 3 → 3   (2,3 → 2,1 → 1,1 → 0,1)
Hints
▶Hint 1 — a nudge

Following the rules literally works. What happens with num1 = 1,000,000,000 and num2 = 1?

▶Hint 2 — the key idea

A billion subtractions of the same number is just one division. Replace "subtract b from a, over and over" with "a ÷ b subtractions happen at once, leaving a mod b".

Solution

The literal simulation is O(max(num1, num2)) — fine for small numbers, a billion steps for large ones. Batching the repeated subtractions into a single division makes each step shrink the numbers dramatically, and the loop becomes the Euclidean algorithm for greatest common divisor, which runs in O(log n). Same output, same idea, a completely different speed. Whenever a loop repeats the same operation many times in a row, ask whether arithmetic can do them all at once.

▶Full solution
📐 Pseudocode · Batch the Subtractions 
function countOperations(a, b):          // O(log n)
    ops ← 0
    while a > 0 and b > 0:
        if a ≥ b:
            ops ← ops + a ÷ b              // all those subtractions at once
            a ← a mod b
        else:
            ops ← ops + b ÷ a
            b ← b mod a
    return ops

// The one-at-a-time version would loop a ÷ b times per step instead of once.
TimeO(log(min(a, b)))
SpaceO(1)
Problem 04 · Remove the Repeated Work
Sum of Absolute Differences in a Sorted Array
🔗 LC 1685 - Sum of Absolute Differences in a Sorted Array
Medium O(n²) → O(n) with running totals Amazon · Google
›
Problem

For each position i in a sorted array, return the sum of |nums[i] − nums[j]| over every other position j.

nums = [2, 3, 5] → [4, 3, 5]
Hints
▶Hint 1 — a nudge

The direct solution compares every pair: O(n²). With n up to 100,000, how many steps is that?

▶Hint 2 — the key idea

10¹⁰ — far too many. Because the array is sorted, every number to the left of i is smaller and every number to the right is larger. You only need the total of each side, not each number separately.

Solution

This is the pattern you will use for the rest of the course: find the work that is being repeated and do it once. The pair-by-pair version recomputes the same partial sums over and over. Since the array is sorted, the left side contributes nums[i] × (count left) − (sum left) and the right side contributes (sum right) − nums[i] × (count right). Keep a running total as you walk, and each position costs O(1). The technique has a name — prefix sums — and gets its own lecture (26); here, only notice how the constraint forced you to find it.

▶Full solution
📐 Pseudocode · Running Totals Instead of Pairs 
function getSumAbsoluteDifferences(nums):
    n ← length(nums);  total ← sum of nums
    left ← 0                                  // sum of everything before i
    result ← new list of length n
    for i from 0 to n - 1:
        right ← total - left - nums[i]        // sum of everything after i
        result[i] ← nums[i] × i - left        // left side: nums[i] is bigger
                  + right - nums[i] × (n - 1 - i)   // right side: nums[i] is smaller
        left ← left + nums[i]
    return result
TimeO(n)
SpaceO(1) extra
Problem 05 · Think Before You Loop
Strictly Palindromic Number
🔗 LC 2396 - Strictly Palindromic Number
Medium Reasoning → O(1) Google · Amazon
›
Problem

A number n is strictly palindromic if it reads the same forwards and backwards when written in every base from 2 up to n − 2. Decide whether n is.

n = 9 → false   |   n = 4 → false
Hints
▶Hint 1 — a nudge

The obvious plan converts n into every base and checks each one — roughly O(n log n). Before writing it, try base n − 2 by hand for a few values of n.

▶Hint 2 — the key idea

For n ≥ 5, n written in base n − 2 is always "12" — which is not a palindrome. So the answer is always false.

Solution

The fastest code is code you do not have to run. Writing n in base n − 2 gives one lot of (n − 2) plus a remainder of 2 — the digits “12” — for every n ≥ 5, and the small cases fail too. So no number qualifies, and the answer is O(1). Problems like this are rare in interviews, but the habit they teach is not: try small cases by hand before you design anything. Lecture 2 turns that habit into a method.

▶Full solution
📐 Pseudocode · The Answer Is a Constant 
function isStrictlyPalindromic(n):
    return false

// Why: in base (n - 2), n = 1 × (n - 2) + 2, so its digits are "12"
// for every n ≥ 5 — never a palindrome. Checking by hand saved all the code.
TimeO(1)
SpaceO(1)
