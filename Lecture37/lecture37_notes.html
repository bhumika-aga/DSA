Segment Trees & Fenwick Trees

“Prefix sums are fast until someone changes one number.”

📚 Lecture 37 of 45 Phase 5 — Advanced Structures ⏱ 6 days 🎯 22 problems 💼 Google · Amazon · Microsoft
🌍
Why does this topic matter?
Every structure so far has been good at one thing. A prefix-sum array answers range queries instantly but has to be rebuilt after any change; a plain array updates instantly but has to be scanned for every query. Segment trees and Fenwick trees refuse that trade-off: both operations become O(log n). They are also the point where interviews stop asking you to recall a structure and start asking you to design one, which is why they appear in senior loops far more often than their LeetCode frequency suggests.
By the end of this lecture you can
  • Say exactly when a prefix-sum array stops being the answer
  • Build a segment tree and write query and point update
  • Add lazy propagation for range updates
  • Write a Fenwick tree from memory and explain the low-bit trick
  • Use a BIT over values to count, not just to sum
🧠
The picture to keep in your head: Sales reports in a company. Head office knows total sales, each region knows its subtotal, and each store knows its own. To total a run of stores, you combine a few regional subtotals instead of phoning every store. When one store’s figure changes, only its chain of managers updates their numbers. That hierarchy of subtotals is a segment tree.

⚖️ Why Prefix Sums Break

Consider q operations on an array of n numbers, mixing “sum of [l, r]” with “set a[i] to v”. Two obvious designs each fail on one half of the workload.

Design Query Update Total for n = q = 10⁵
Plain array, scan the range O(n) O(1) 10¹⁰ — far too slow
Prefix-sum array O(1) O(n) rebuild 10¹⁰ — equally hopeless
Square-root blocks O(√n) O(1) ~3 × 10⁸ — borderline
Segment tree / Fenwick tree O(log n) O(log n) ~4 × 10⁷ — comfortable
🧠
The idea behind all three fixes is the same: store the answer for blocks of the array instead of for every prefix. A prefix sum uses one block per prefix, so a change touches almost all of them. Square-root decomposition uses √n blocks; a segment tree uses a hierarchy of halves, so a change touches only the log n blocks on one root-to-leaf path. Lecture 38 comes back to the √n version, which is easier to write under pressure and often fast enough.

🌳 The Segment Tree

Node 1 covers the whole array. Its children cover the two halves, theirs cover the quarters, and the leaves are single elements. Each node stores the answer for its own range, so a query assembles its answer from at most 2 log n nodes, and an update repairs one path.

📐 Pseudocode · Layout 
// Array of size 4n, no pointers. For node i covering [lo, hi]:
//     left child  = 2i,     covering [lo, mid]
//     right child = 2i + 1, covering [mid + 1, hi]
//     mid = lo + (hi - lo) ÷ 2
//
// a = [2, 5, 1, 4]
//
//              [0..3] = 12
//             /            //        [0..1] = 7      [2..3] = 5
//        /      \         /      //      2         5       1        4
//
// Why 4n and not 2n? Because the tree is only perfect when n is a power of
// two; 4n is the safe bound for every n, and it costs nothing to allocate.

Build

📐 Pseudocode · Build in O(n) 
function build(node, lo, hi):
    if lo = hi:
        tree[node] ← a[lo]                  // a leaf is its element
        return

    mid ← lo + (hi - lo) ÷ 2
    build(2·node,     lo,      mid)
    build(2·node + 1, mid + 1, hi)
    tree[node] ← tree[2·node] + tree[2·node + 1]   // pull up

// Every node is written exactly once → O(n), not O(n log n).
// Replace + with min, max, gcd or OR and nothing else changes: the operation
// only has to be associative.

Query & Update

The query is a three-way decision at every node: my range is outside yours (contribute nothing), my range is inside yours (return my stored answer), or we overlap partially (ask both children).

📐 Pseudocode · Range Query, Point Update 
function query(node, lo, hi, l, r):        // sum of [l, r]
    if r < lo or hi < l: return 0        // 1. no overlap
    if l ≤ lo and hi ≤ r: return tree[node]   // 2. fully inside

    mid ← lo + (hi - lo) ÷ 2                 // 3. partial → split
    return query(2·node,     lo,      mid, l, r)
         + query(2·node + 1, mid + 1, hi,  l, r)

function update(node, lo, hi, i, value):
    if lo = hi:
        tree[node] ← value
        return

    mid ← lo + (hi - lo) ÷ 2
    if i ≤ mid: update(2·node,     lo,      mid, i, value)
    else:       update(2·node + 1, mid + 1, hi,  i, value)
    tree[node] ← tree[2·node] + tree[2·node + 1]   // repair on the way up

// Dry run on a = [2, 5, 1, 4], query(l=1, r=2):
//   [0..3] partial → split
//     [0..1] partial → left [0..0] no overlap = 0, right [1..1] inside = 5
//     [2..3] partial → left [2..2] inside = 1, right [3..3] no overlap = 0
//   total = 6 ✓  (visited 7 of 7 nodes here because n is tiny; for large n
//   the "fully inside" case cuts the recursion after ~2 log n nodes)
⚠️
The identity element matters. The no-overlap branch must return something that cannot affect the answer: 0 for sums, +infinity for minimums, -infinity for maximums, 0 for gcd. Returning 0 from a minimum query is the single most common segment-tree bug.

💤 Lazy Propagation

“Add 3 to every element of [l, r]” would touch O(n) leaves if you did it honestly. Lazy propagation is the refusal to do it honestly: mark the node that covers the range with a debt, and pay the debt only when someone descends through it.

📐 Pseudocode · Range Add, Range Sum 
function push(node, lo, hi):               // pay the debt one level down
    if lazy[node] = 0: return
    mid ← lo + (hi - lo) ÷ 2
    apply(2·node,     lo,      mid, lazy[node])
    apply(2·node + 1, mid + 1, hi,  lazy[node])
    lazy[node] ← 0

function apply(node, lo, hi, add):
    tree[node] ← tree[node] + add × (hi - lo + 1)   // whole range
    lazy[node] ← lazy[node] + add                   // owe it to the children

function rangeAdd(node, lo, hi, l, r, add):
    if r < lo or hi < l: return
    if l ≤ lo and hi ≤ r:
        apply(node, lo, hi, add)             // stop here — this is the trick
        return

    push(node, lo, hi)
    mid ← lo + (hi - lo) ÷ 2
    rangeAdd(2·node,     lo,      mid, l, r, add)
    rangeAdd(2·node + 1, mid + 1, hi,  l, r, add)
    tree[node] ← tree[2·node] + tree[2·node + 1]

function query(node, lo, hi, l, r):
    if r < lo or hi < l: return 0
    if l ≤ lo and hi ≤ r: return tree[node]
    push(node, lo, hi)                       // never read a stale child
    mid ← lo + (hi - lo) ÷ 2
    return query(2·node, lo, mid, l, r) + query(2·node + 1, mid + 1, hi, l, r)
🧠
Two rules keep lazy propagation correct. First, tree[node] is always already correct for its own range — the lazy value is what the children have not been told. Second, push before you descend, in every operation, including queries. Almost every lazy bug is a missing push.
⚠️
Assignment is not addition. For “set the whole range to v”, the pending value must be stored as “assign v” with a separate “is pending” flag, because a later assignment overwrites an earlier one instead of stacking with it. Mixing add and assign in one tree means deciding how the two compose — say that out loud before you write it.

🔢 Fenwick Tree (BIT)

A Fenwick tree does less than a segment tree — prefix aggregates only, and the operation must be invertible if you want arbitrary ranges — but it is twenty lines, uses n integers instead of 4n, and is noticeably faster in practice. When the problem is prefix sums with point updates, this is the answer.

📐 Pseudocode · The Whole Structure 
// bit[i] stores the sum of the lowbit(i) elements ending at index i.
// lowbit(i) = i AND (-i) — the lowest set bit of i.
//   lowbit(6) = lowbit(0b110) = 2  → bit[6] covers a[5] + a[6]
//   lowbit(8) = lowbit(0b1000) = 8 → bit[8] covers a[1..8]
// Indices are 1-based. This is not optional: index 0 has no low bit.

function update(i, delta):               // add delta to a[i]
    while i ≤ n:
        bit[i] ← bit[i] + delta
        i ← i + (i AND -i)                // next range that covers i

function prefix(i):                      // sum of a[1..i]
    total ← 0
    while i > 0:
        total ← total + bit[i]
        i ← i - (i AND -i)                // strip the low bit
    return total

function rangeSum(l, r):
    return prefix(r) - prefix(l - 1)  // needs an invertible op

// Both loops strip or add one bit per step, so both are O(log n).
// Building by calling update n times is O(n log n); the O(n) build adds each
// bit[i] into bit[i + lowbit(i)] in one pass, which is worth knowing.

Counting With a BIT

The move that turns a BIT into an interview weapon is indexing it by value rather than by position. bit[v] then means “how many values ≤ v have I seen so far”, and questions about order become prefix sums.

📐 Pseudocode · Count Smaller Elements to the Right 
function countSmallerAfter(a):
    ranks ← compress(a)                   // sorted distinct values → 1..m
    bit ← empty Fenwick tree of size m
    answer ← array of zeros

    for i from n - 1 down to 0:   // right to left
        r ← ranks[a[i]]
        answer[i] ← prefix(r - 1)         // already seen, strictly smaller
        update(r, 1)                      // now a[i] has been seen

    return answer

// Coordinate compression is what makes this work when values are huge or
// negative: only the ORDER of the values matters, never their magnitude.
💡
Recognise the family. Counting inversions, counting smaller elements to the right, reverse pairs, counting good triplets — all of them are “sweep in one direction, ask how many earlier values fall in a range”. You solved several of these with merge sort in Lecture 12; the BIT version is usually shorter and extends to weights and to more than two conditions.

🧩 Variants You Will Meet

Variant What changes Use it for
Min / max segment tree Combine with min or max; identity is ±infinity Range extremes, DP transitions over a value window
Segment tree over values Index by compressed value, not position “Best DP answer among values < x”
Dynamic (sparse) segment tree Create nodes on demand instead of allocating 4n Coordinates up to 10⁹ with few queries
Coordinate compression + static tree Map the endpoints that actually occur to 1..m The same situation, when all queries are known up front
Difference array + one prefix pass No tree at all Range updates, then a single query phase at the end
Merge-sort tree Each node stores its range sorted “How many values in [l, r] are ≤ k”
🧠
Check the difference array first. If every update arrives before every query, you do not need a tree at all: record +v at l and -v at r + 1, then take one prefix pass at the end. That is O(n + q) and five lines. Reach for a tree only when updates and queries are interleaved.

🔍 Choosing a Structure

The workload Structure Why
Range query, no updates Prefix sums (or a sparse table for min/max) O(1) per query, nothing to maintain
All updates first, then all queries Difference array O(n + q) with no structure at all
Point update + prefix sum Fenwick tree Shortest correct answer, smallest constant
Point update + range min / max / gcd Segment tree A BIT cannot invert min or max
Range update + range query Segment tree with lazy propagation Deferred work keeps both at O(log n)
Huge coordinates, few operations Dynamic tree, or compress then build Allocate only what is touched
Counting by value while sweeping BIT over compressed values Order questions become prefix sums

⚠️ Complexity & Bugs

Point update O(log n) O(log n) One root-to-leaf path, or one chain of low bits
Range query O(log n) O(log n) BIT needs an invertible operation
Range update O(log n) with lazy O(log n) with two BITs The two-BIT trick handles range add + range sum

Tree array sized 2n Index out of bounds for non-power-of-two n Allocate 4n
Returning 0 for a min query with no overlap Every minimum comes back as 0 Return the identity: +infinity
Forgetting to pull up after an update Leaf is right, ancestors are stale Recombine children on the way back up

0-based Fenwick indices Infinite loop or silently wrong sums lowbit(0) = 0 — index from 1

Overflow on sums Wrong answers only on large inputs Use 64-bit accumulators for sums of n × 10⁹
Rebuilding the tree per query Correct but times out Build once outside the loop
🔍
How to spot it in an interview. Two numbers together give it away: an array of 10⁵ and a query count of 10⁵, with updates mixed into the queries. If the updates all come first, say “difference array”; if there are no updates, say “prefix sums”; only when they interleave do you reach for a tree — and then say which one and why, because choosing the Fenwick tree when it suffices is itself the signal they are looking for.

💪 In-Lecture Practice Problems

Six problems: the canonical structure, two uses of a Fenwick tree, one that needs no tree at all, and two that combine a tree with compression or laziness.

Problem 01 · The Canonical One
Range Sum Query - Mutable
🔗 LC 307 - Range Sum Query - Mutable
Medium Segment Tree / Fenwick Tree Google · Amazon · Microsoft
›
Problem

Support update(index, value) and sumRange(left, right) on an integer array.

nums = [1, 3, 5]; sumRange(0, 2) → 9; update(1, 2); sumRange(0, 2) → 8
Hints
▶Hint 1 — a nudge

A prefix-sum array answers the query in O(1) but costs O(n) per update. What does that cost over 10⁴ mixed operations?

▶Hint 2 — the key idea

Both operations need to be logarithmic. A Fenwick tree is the shortest structure that does it — store deltas, not values, when updating.

Solution

Write it both ways and know when to offer each. The Fenwick version is twelve lines and is what you should produce first: update takes the delta value − old[i], so you must keep the original array alongside the tree. The segment tree version is longer but generalises to minimum, maximum and gcd, which a Fenwick tree cannot do — say that explicitly, because the follow-up question is almost always “now make it range minimum”.

▶Full solution
📐 Pseudocode · Fenwick Tree, Storing Deltas 
function NumArray(nums):
    n ← length(nums)
    a ← copy of nums                      // needed to compute deltas
    bit ← array of n + 1 zeros
    for i from 0 to n - 1: add(i + 1, nums[i])

function add(i, delta):
    while i ≤ n:
        bit[i] ← bit[i] + delta
        i ← i + (i AND -i)

function prefix(i):
    s ← 0
    while i > 0:
        s ← s + bit[i]
        i ← i - (i AND -i)
    return s

function update(index, value):
    add(index + 1, value - a[index])      // the delta, not the value
    a[index] ← value

function sumRange(left, right):
    return prefix(right + 1) - prefix(left)
TimeO(log n) per op
SpaceO(n)
Problem 02 · BIT Over Values
Count Number of Teams
🔗 LC 1395 - Count Number of Teams
Medium Fenwick Tree (counting) Amazon · Google
›
Problem

Count the triples i < j < k whose ratings are strictly increasing or strictly decreasing.

rating = [2, 5, 3, 4, 1] → 3
Hints
▶Hint 1 — a nudge

n ≤ 1000, so O(n²) passes — but solve it as if n were 10⁵. Fix the middle soldier: what do you need to know about each side?

▶Hint 2 — the key idea

For each j: how many smaller ratings lie to its left, and how many larger lie to its right. Sweep with a BIT indexed by rating.

Solution

The cubic loop is the intended solution here, and the quadratic one fixes the middle element. The reason to write the BIT version anyway is that it is the same code as counting inversions: sweep left to right maintaining a Fenwick tree over compressed ratings, and each position asks two prefix queries. Every “count pairs or triples in order” problem — inversions, reverse pairs, good triplets — is this pattern with a different multiplier.

▶Full solution
📐 Pseudocode · Fix the Middle, Count Both Sides 
function numTeams(rating):
    m ← number of distinct ratings
    left  ← Fenwick tree of size m        // seen so far
    right ← Fenwick tree of size m        // everything, then removed
    for r in rating: right.add(rank(r), 1)

    total ← 0
    for j from 0 to n - 1:
        r ← rank(rating[j])
        right.add(r, -1)                  // j is no longer "to the right"

        lessLeft   ← left.prefix(r - 1)
        moreLeft   ← j - left.prefix(r)
        lessRight  ← right.prefix(r - 1)
        moreRight  ← (n - 1 - j) - right.prefix(r)

        total ← total + lessLeft × moreRight     // increasing
                      + moreLeft × lessRight     // decreasing

        left.add(r, 1)
    return total
TimeO(n log n)
SpaceO(n)
Problem 03 · Query Without a Tree
Range Frequency Queries
🔗 LC 2080 - Range Frequency Queries
Medium Bucketed Indices + Binary Search Amazon · Google
›
Problem

Answer many queries of the form “how many times does value occur in arr[left..right]?”

arr = [12, 33, 4, 56, 22, 2, 34, 33, 22, 12, 34, 56], query(1, 2, 33) → 1
Hints
▶Hint 1 — a nudge

The array never changes. Does that remove the need for a tree?

▶Hint 2 — the key idea

Store, for each value, the sorted list of positions where it occurs. A query is then two binary searches inside one list.

Solution

This problem is here as a corrective. It looks like a range-query problem, so people reach for a segment tree — but nothing is ever updated, so the right answer is a map from value to its sorted index list, and a pair of binary searches. Knowing when not to build a tree is half of what this lecture is for. If the array did change, this becomes a merge-sort tree or a BIT per value, and the cost of that jump is worth stating.

▶Full solution
📐 Pseudocode · Positions Per Value + Binary Search 
function RangeFreqQuery(arr):
    positions ← map from value → list of indices
    for i from 0 to n - 1:
        positions[arr[i]].append(i)       // already sorted

function query(left, right, value):
    if value not in positions: return 0
    list ← positions[value]
    lo ← first index in list ≥ left       // lower bound
    hi ← first index in list > right      // upper bound
    return hi - lo

// No updates → no tree. If updates existed, this becomes a BIT per value
// or a merge-sort tree, at a real cost in memory and code.
TimeO(n) build, O(log n) per query
SpaceO(n)
Problem 04 · Tree Over Values
Longest Increasing Subsequence II
🔗 LC 2407 - Longest Increasing Subsequence II
Hard Segment Tree (max) over values Google · Amazon
›
Problem

Find the longest strictly increasing subsequence in which consecutive elements differ by at most k.

nums = [4, 2, 1, 4, 3, 4, 5, 8, 15], k = 3 → 5
Hints
▶Hint 1 — a nudge

The O(n²) DP asks, for each i, the best dp[j] among earlier valid j. What kind of query is that over the values?

▶Hint 2 — the key idea

dp[v] = best length ending at value v. Then dp[nums[i]] = 1 + max of dp over the value window [nums[i] − k, nums[i] − 1] — a range maximum query.

Solution

This is the lecture’s main lesson applied to dynamic programming: when a DP transition is “the best of all previous states in a range”, a segment tree turns O(n) per step into O(log n). Index the tree by value, not by position, so the constraint “differs by at most k” becomes a contiguous range. Point update, range maximum, no lazy propagation — and a Fenwick tree cannot replace it here, because maximum is not invertible.

▶Full solution
📐 Pseudocode · Range Max Over the Value Axis 
function lengthOfLIS(nums, k):
    V ← max(nums)
    tree ← segment tree over values 1..V, combine = max, identity = 0
    best ← 0

    for x in nums:
        lo ← max(1, x - k)
        hi ← x - 1                        // strictly increasing

        prev ← 0
        if lo ≤ hi: prev ← tree.queryMax(lo, hi)

        length ← prev + 1
        tree.update(x, length)            // point update, keep the max
        best ← max(best, length)

    return best

// The DP is unchanged — only the "best previous state" lookup got faster.
TimeO(n log V)
SpaceO(V)
Problem 05 · Dynamic + Lazy
My Calendar III
🔗 LC 732 - My Calendar III
Hard Lazy Segment Tree / Sweep Google · Amazon
›
Problem

After each booked interval [start, end), return the maximum number of bookings that overlap at any single point.

book(10, 20) → 1, book(50, 60) → 1, book(10, 40) → 2, book(5, 15) → 3
Hints
▶Hint 1 — a nudge

A booking adds 1 to every point in a range, and the answer is the maximum over all points. Which two operations is that?

▶Hint 2 — the key idea

Range add and global maximum — exactly lazy propagation. The coordinates go up to 10⁹, so either create nodes on demand or compress.

Solution

Two solutions, and both are worth knowing. The sweep-line one is shorter: a sorted map with +1 at each start and −1 at each end, then a running total over the keys — O(n) per call, which passes here. The segment tree one is the scalable answer: range add with lazy propagation over a dynamic tree keyed by coordinate, giving O(log C) per booking. Offer the sweep, then say how you would make it logarithmic; that sequence is what interviewers are grading.

▶Full solution
📐 Pseudocode · Range Add, Global Max 
// Sweep version — short, O(n) per call, enough for the constraints
function book(start, end):
    delta[start] ← delta[start] + 1
    delta[end]   ← delta[end] - 1

    active ← 0;  best ← 0
    for key in sorted keys of delta:
        active ← active + delta[key]
        best ← max(best, active)
    return best

// Segment tree version — O(log C), the one that scales
function book(start, end):
    rangeAdd(root, 0, 10⁹, start, end - 1, +1)   // end is exclusive
    return tree[root]                            // root holds the maximum

// Nodes are created only when a range is first touched, so the tree holds
// O(n log C) nodes instead of pre-allocating 4 × 10⁹.
TimeO(log C) per booking
SpaceO(n log C)
Problem 06 · Compress First
Falling Squares
🔗 LC 699 - Falling Squares
Hard Coordinate Compression + Lazy Assign Google · Amazon
›
Problem

Squares drop one at a time onto a number line and rest on whatever is below them. After each drop, return the height of the tallest stack so far.

positions = [[1,2],[2,3],[6,1]] → [2, 5, 5]
Hints
▶Hint 1 — a nudge

A square landing on [l, r) sits at 1 + the maximum current height in that interval. What two operations does that need?

▶Hint 2 — the key idea

Range maximum query, then range assign of the new height. Coordinates reach 10⁸, but there are at most 2n distinct endpoints — compress them.

Solution

Every square is one query and one update on the same interval: read the maximum height under it, then set the whole interval to that plus its side length. The assignment is a set, not an add, so the lazy value needs a pending-assign flag rather than an accumulator. Compression is the other half: only the interval endpoints that actually occur can ever matter, so map the at most 2n of them to a small index range and build a static tree over that.

▶Full solution
📐 Pseudocode · Query Max, Then Assign 
function fallingSquares(positions):
    xs ← sorted distinct of all l and (l + side) values   // compress
    tree ← lazy segment tree over 0..len(xs) - 1, op = max, lazy = assign
    best ← 0;  result ← empty list

    for (left, side) in positions:
        l ← index of left in xs
        r ← index of (left + side) in xs - 1        // half-open

        base ← tree.queryMax(l, r)
        top  ← base + side
        tree.assign(l, r, top)                        // range set, not add

        best ← max(best, top)
        result.add(best)

    return result

// Touching squares must not stack: using a half-open range is what keeps
// [1,2] and [2,3] independent.
TimeO(n log n)
SpaceO(n)
