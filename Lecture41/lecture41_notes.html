Balanced BSTs & Ordered Structures

“Keep everything sorted, even while it changes — and find the nearest value in a single step.”

📚 Lecture 41 of 45 Phase 5 — Advanced Structures ⏱ 4 days 🎯 18 problems 💼 Google · Amazon · Bloomberg · Microsoft
🌍
Why does this topic matter?
A HashMap answers “is x here?” instantly, but it has no idea which key is next to x. A heap knows its smallest item but nothing else. Many interview problems need both: keys kept in sorted order while items are added and removed, plus quick answers to “what is the closest value to x?”, “what is the largest key below 50?” or “what is the k-th smallest?”. A balanced binary search tree does all of that in O(log n) — and in Java you already have one, called TreeMap.
By the end of this lecture you can
  • Use TreeMap and TreeSet’s floor, ceiling, higher, lower and subMap without looking them up
  • Fake a multiset with a TreeMap of counts
  • Explain why a plain BST can become slow, and how a rotation fixes it
  • State the AVL and red-black rules in plain words, without memorising their code
  • Find the k-th smallest with subtree sizes, and explain how a skip list stays fast
  • Choose between TreeMap, PriorityQueue and a sorted array
🧠
The picture to keep in your head: a dictionary on a shelf. A HashMap is a coat-check desk: hand over your ticket and you get your coat back at once, but nobody can tell you whose coat hangs next to yours. A TreeMap is a dictionary: every word sits in alphabetical order, so you can open it at “mango”, and if “mango” is missing, the words just before and just after it are right there. Balancing is the publisher making sure the dictionary is never one enormous chapter — every lookup takes the same few page-flips.
↩️
Built on Lectures 19 and 20. Lecture 19 taught the BST rule (smaller keys to the left, larger to the right) and search, insert and delete on it. Lecture 20 taught heaps. This lecture shows what goes wrong with a plain BST, how real libraries prevent it, and when an ordered tree beats a heap. Lecture 37’s Fenwick tree appears once more as an alternative for rank queries.

☕ Java’s Ordered API

TreeMap<K, V> keeps its keys sorted; TreeSet<E> is the same thing without values. Besides the usual get, put and remove, they answer neighbour questions. Each one below runs in O(log n), and each returns null when no such key exists.

Method Returns Example: keys {10, 20, 30}
floorKey(x) Largest key ≤ x floorKey(25) = 20, floorKey(20) = 20
ceilingKey(x) Smallest key ≥ x ceilingKey(25) = 30, ceilingKey(31) = null
lowerKey(x) Largest key < x lowerKey(20) = 10
higherKey(x) Smallest key > x higherKey(20) = 30
firstKey() / lastKey() Smallest / largest key 10 / 30
pollFirstEntry() / pollLastEntry() Remove and return the smallest / largest Like a heap’s poll, from either end
headMap(x) / tailMap(x) A live view of keys < x / keys ≥ x headMap(30) = {10, 20}
subMap(a, true, b, true) A live view of keys in [a, b] subMap(15, true, 30, true) = {20, 30}

TreeSet has the same family without the word “Key”: floor, ceiling, lower, higher, first, last, pollFirst, headSet, subSet.

☕ Java · Nearest Value 
TreeSet<Integer> set = new TreeSet<>(List.of(10, 20, 30));

int closest(TreeSet<Integer> set, int x) {
    Integer lo = set.floor(x);     // Integer, not int: it may be null
    Integer hi = set.ceiling(x);
    if (lo == null) return hi;
    if (hi == null) return lo;
    return (x - lo <= hi - x) ? lo : hi;
}
// closest(set, 24) → 20,  closest(set, 26) → 30,  closest(set, 99) → 30
💡
Only the neighbours matter. In sorted order, the value closest to x is always either the one just below it or the one just above it — never anything further away. That single fact is behind almost every problem in this lecture: you never scan the whole set, you ask for the floor and the ceiling.

TreeMap as a multiset

A TreeSet cannot hold the same value twice, and Java has no built-in sorted multiset. The standard fix is a TreeMap from value to how many copies there are. The one rule to never forget: when a count drops to zero, remove the key, or firstKey() will report a value that is no longer there.

📐 Pseudocode · Sorted Multiset From a TreeMap 
function addOne(counts, x):
    counts[x] ← counts.getOrDefault(x, 0) + 1

function removeOne(counts, x):
    counts[x] ← counts[x] - 1
    if counts[x] = 0:
        counts.remove(x)                       // essential: keep only values still present

// smallest = counts.firstKey(),  largest = counts.lastKey()  — both O(log n)
// A heap can give you one end; this gives you both ends AND lets you delete any value.

⚖️ Why Balance Matters

Every BST operation walks one path from the root, so it costs the tree’s height. With n keys the height can be as small as about log₂ n — or as large as n. Insert 1, 2, 3, 4, 5 in that order into a plain BST and each key goes to the right of the last one: the “tree” is a linked list, and search is O(n).

Inserted 1,2,3,4,5 (plain BST) Same keys, balanced 1 3 \ / \ 2 2 4 \ / \ 3 1 5 \ 4 height 3: every search ≤ 3 steps \ 5 height 5: search = walk the whole list

Sorted input is not a rare accident — timestamps, IDs and anything read from a sorted file all arrive in order. A self-balancing BST repairs its shape after every insert and delete so the height stays O(log n) no matter what order the keys arrive in.

Rotations: the only repair tool

A rotation lifts a child above its parent while keeping the BST order intact. Picture a mobile hanging from the ceiling: you move the hook from one bar to the one below it, and the pieces rearrange so that one side hangs higher and the other lower. Only three pointers change.

Right rotation at y Left rotation at x y x / \ / \ x C ──→ A y / \ / \ A B B C In-order before and after: A, x, B, y, C — the order never changes.
📐 Pseudocode · Rotations 
function rotateRight(y):
    x ← y.left
    y.left ← x.right                          // B moves across: it was between x and y, and still is
    x.right ← y
    update height (or size) of y, then of x     // y is now below x, so y first
    return x                                  // the new root of this subtree

function rotateLeft(x):
    y ← x.right
    x.right ← y.left
    y.left ← x
    update x, then y
    return y

AVL and red-black trees, at a glance

The two classic self-balancing trees differ only in the rule they enforce and how often they rotate. You will almost never be asked to code one in full; you will be asked what they guarantee and why.

AVL tree Red-black tree
The rule At every node, the heights of the two subtrees differ by at most 1 Nodes are red or black; no red node has a red child; every path from a node down to an empty spot passes the same number of black nodes
Height ≤ about 1.44 log₂ n (tighter) ≤ 2 log₂(n + 1) (looser)
Good at Lookups (shorter paths) Inserts and deletes (fewer rotations)
Where you meet it Textbooks, read-heavy indexes Java’s TreeMap and TreeSet, and a HashMap bucket that grows past 8 entries

AVL insert is short enough to read once. Insert as in a plain BST; then, on the way back up, any node whose subtrees differ in height by 2 is fixed by one or two rotations. There are four cases, named by the path from the unbalanced node down to the new key.

📐 Pseudocode · AVL Insert (Read, Don’t Memorise) 
function height(node): return 0 if node = null else node.height
function balance(node): return height(node.left) - height(node.right)

function insert(node, key):
    if node = null: return new node(key) with height 1
    if key < node.key: node.left ← insert(node.left, key)
    else:              node.right ← insert(node.right, key)
    node.height ← 1 + max(height(node.left), height(node.right))
    b ← balance(node)
    if b > 1 and key < node.left.key:  return rotateRight(node)       // left-left
    if b < -1 and key > node.right.key: return rotateLeft(node)       // right-right
    if b > 1:                                                     // left-right
        node.left ← rotateLeft(node.left);  return rotateRight(node)
    if b < -1:                                                    // right-left
        node.right ← rotateRight(node.right);  return rotateLeft(node)
    return node
🎯
What an interviewer wants to hear. “A plain BST can degrade to O(n) on sorted input. Self-balancing trees fix the shape with rotations after each update, which preserve the in-order sequence. AVL keeps subtree heights within 1; red-black uses colours and allows up to twice the minimum height but rotates less. Java’s TreeMap is red-black, so its operations are O(log n) in the worst case.”

🔢 Order Statistics

TreeMap cannot answer “what is the k-th smallest key?” or “how many keys are smaller than x?” faster than walking through them. Add one field to every node — size, the number of nodes in its subtree — and both become a single walk down the tree. The result is called an order-statistic tree. Rotations must update size exactly as they update height.

📐 Pseudocode · k-th Smallest and Rank With Subtree Sizes 
function size(node): return 0 if node = null else node.size

function kth(node, k):                       // 1-based
    left ← size(node.left)
    if k ≤ left:     return kth(node.left, k)
    if k = left + 1: return node.key            // exactly 'left' keys are smaller
    return kth(node.right, k - left - 1)        // skip the left subtree and this node

function rank(node, x):                     // how many keys are < x
    if node = null: return 0
    if x ≤ node.key: return rank(node.left, x)
    return size(node.left) + 1 + rank(node.right, x)
💡
In Java, without writing a tree. If every value is known in advance (or can be), compress them to indices 1..m and keep a Fenwick tree of counts from Lecture 37: rank is a prefix sum, and the k-th smallest is a binary search over prefix sums. That is what most accepted solutions to “k-th” and “count smaller” problems actually do.

🪜 Skip Lists

A skip list gets balanced-tree speed without any rotations. Start with a sorted linked list (Lecture 14). Give each node a random height by flipping a coin: heads, it also joins the level above; heads again, the level above that. Roughly half the nodes reach level 2, a quarter reach level 3, and so on. The upper levels are express lanes: search along the top level until the next value would overshoot, drop down a level, and repeat.

level 3: head ───────────────────────────> 30 ────────────> null level 2: head ─────────> 10 ─────────> 30 ────> 50 ──> null level 1: head ─> 5 ─> 10 ─> 20 ─> 30 ─> 40 ─> 50 ─> null Search 40: level 3 → 30, level 2 → (50 overshoots) stay at 30, level 1 → 40 ✓
📐 Pseudocode · Skip List Search and Insert 
function predecessors(list, target):          // last node < target on every level
    pred ← array of size MAX_LEVEL;  cur ← list.head
    for lv from list.level - 1 down to 0:
        while cur.next[lv] ≠ null and cur.next[lv].value < target:
            cur ← cur.next[lv]                  // move right in the express lane
        pred[lv] ← cur                          // then drop one level
    return pred

function insert(list, x):
    pred ← predecessors(list, x)
    h ← 1
    while h < MAX_LEVEL and coin flip is heads: h ← h + 1
    for lv from list.level to h - 1: pred[lv] ← list.head   // brand-new levels start at head
    list.level ← max(list.level, h)
    node ← new node(x) with h next-pointers
    for lv from 0 to h - 1:                      // splice in, exactly like a linked list
        node.next[lv] ← pred[lv].next[lv]
        pred[lv].next[lv] ← node

Searches, inserts and deletes all cost O(log n) expected — the randomness is in the coin flips, not in the input, so no insertion order can make it slow on purpose. Java ships one as ConcurrentSkipListMap, used when many threads share an ordered map, because updating a few linked-list pointers is easier to make thread-safe than a rotation.

🧩 Choosing a Structure

You need… Use Why not the others
Exact lookup only, no order HashMap / HashSet O(1) beats O(log n)
Repeatedly take the smallest (or largest) only PriorityQueue Simpler and faster constant; no arbitrary delete needed
Both ends, or delete any item, while inserting TreeMap multiset PriorityQueue.remove(x) is O(n)
Nearest value, or keys in a range, while inserting TreeMap / TreeSet A sorted array needs O(n) per insert
Nearest value, but the data never changes Sorted array + binary search Less memory, faster in practice
k-th smallest or rank, while inserting Fenwick tree over compressed values, or two heaps TreeMap would walk k entries

⚠️ Complexity & Classic Bugs

Operation Plain BST (worst) TreeMap / AVL / red-black Skip list
Search, insert, delete O(n) O(log n) O(log n) expected
floor / ceiling / higher / lower O(n) O(log n) O(log n) expected
First / last key O(n) O(log n) O(1) first, O(log n) last
Iterate over k keys in a range O(n) O(log n + k) O(log n + k)
k-th smallest O(n) O(k) in TreeMap; O(log n) with subtree sizes O(n)
Bug Symptom Fix
int x = set.floor(v); when nothing is ≤ v NullPointerException from unboxing Store the result in an Integer; check null
Leaving zero counts in a TreeMap multiset firstKey() returns a value already removed Remove the key the moment its count hits 0
Comparator that ignores a tie-breaker TreeSet silently drops a different item that “compares equal” Break ties with a unique field such as a name or id
Changing an object’s sort field while it is in a TreeSet remove and contains stop finding it Remove it, change the field, then add it back
Comparator written as a - b Overflow flips the order for large values Use Integer.compare(a, b)
Calling subMap(...).size() in a loop Time limit exceeded A range view’s size is O(k), not O(1); count some other way
Rotation that updates the parent before the child Wrong heights or sizes, then wrong balancing Update the node that moved down first
🔍
How to spot it. “Closest”, “nearest”, “just below”, “next available”, “within t of each other”, a maximum or minimum that must survive deletions or corrections, or “k-th” as items keep arriving.

Problem 01 · Ordered Sliding Window
Contains Duplicate III
🔗 LC 220 - Contains Duplicate III
Hard TreeSet window + ceiling Google · Airbnb · Amazon
›
Problem

Return true if there are two different indices i and j with |i − j| ≤ indexDiff and |nums[i] − nums[j]| ≤ valueDiff.

nums = [1,2,3,1], indexDiff = 3, valueDiff = 0 → true nums = [1,5,9,1,5,9], indexDiff = 2, valueDiff = 3 → false
Hints
▶Hint 1 — a nudge

For each j, only the last indexDiff values can pair with nums[j]. Among those, which single value is worth checking?

▶Hint 2 — the key idea

The smallest value that is at least x − valueDiff: ceiling(x − valueDiff). If even that one is above x + valueDiff, nothing in the window is close enough.

Solution

The brute force compares every pair within indexDiff: O(n · indexDiff). Keep the window of the last indexDiff values in a TreeSet instead. Any valid partner for x lies in [x − valueDiff, x + valueDiff], and the only candidate worth testing is the smallest value in the window that is ≥ x − valueDiff. One ceiling query per element makes the whole scan O(n log k). Two details: compute x − valueDiff in long to avoid overflow, and note that the window never holds duplicates — a duplicate would already have returned true — so a set is enough.

▶Full solution
📐 Pseudocode · One Ceiling Query per Element 
function containsNearbyAlmostDuplicate(nums, indexDiff, valueDiff):
    window ← empty TreeSet
    for i from 0 to length(nums) - 1:
        x ← nums[i]
        c ← window.ceiling(x - valueDiff)             // in long arithmetic
        if c ≠ null and c ≤ x + valueDiff: return true
        window.add(x)
        if i ≥ indexDiff:
            window.remove(nums[i - indexDiff])         // keep only the last indexDiff values
    return false
TimeO(n log k)
SpaceO(k)
Problem 02 · TreeMap Multiset
Stock Price Fluctuation
🔗 LC 2034 - Stock Price Fluctuation
Medium Value → count TreeMap Google · Amazon
›
Problem

Price records arrive as (timestamp, price), possibly out of order, and a later record for the same timestamp corrects the earlier one. Support current() (price at the latest timestamp), maximum() and minimum() over all current records.

update(1,10), update(2,5), current() → 5, maximum() → 10 update(1,3), maximum() → 5, update(4,2), minimum() → 2
Hints
▶Hint 1 — a nudge

A correction must remove the old price from whatever tracks the maximum. What does that rule out?

▶Hint 2 — the key idea

Two prices can be equal, so you need a sorted multiset: a TreeMap from price to how many timestamps have it. Max and min are its last and first keys.

Solution

A HashMap from timestamp to price answers current(), together with the largest timestamp seen. The maximum and minimum are the hard part, because a correction deletes an old price. A heap can only delete lazily (you would pop stale entries later); a TreeMap multiset deletes directly. On update, if the timestamp already had a price, remove one copy of it, then add one copy of the new price. Both ends of the TreeMap are then O(log n) away.

▶Full solution
📐 Pseudocode · HashMap + TreeMap of Counts 
priceAt ← empty HashMap        // timestamp → price
counts ← empty TreeMap         // price → how many timestamps have it
latest ← 0

function update(t, price):
    if t in priceAt:
        removeOne(counts, priceAt[t])          // the correction replaces the old price
    priceAt[t] ← price
    addOne(counts, price)
    latest ← max(latest, t)

function current(): return priceAt[latest]
function maximum(): return counts.lastKey()
function minimum(): return counts.firstKey()
// addOne / removeOne are the multiset helpers from the lecture
TimeO(log n) per call
SpaceO(n)
Problem 03 · Neighbours in a TreeSet
Exam Room
🔗 LC 855 - Exam Room
Medium Widest gap between neighbours Google
›
Problem

n seats in a row, numbered 0 to n − 1. Each arriving student takes the seat that is as far as possible from the nearest other student (the lowest number on ties; seat 0 if the room is empty). Students may also leave.

n = 10: seat() → 0, seat() → 9, seat() → 4, seat() → 2, leave(4), seat() → 5
Hints
▶Hint 1 — a nudge

Between two neighbouring students at a and b, where is the best seat, and how far is it from both?

▶Hint 2 — the key idea

At a + (b − a) / 2, distance (b − a) / 2. The two ends are special: seat 0 is first-student positions away, seat n − 1 is (n − 1 − last) away. Keep the students in a TreeSet so neighbours are adjacent.

Solution

Only three kinds of seat can ever be best: seat 0, the middle of a gap between two neighbouring students, or seat n − 1. Keep the taken seats in a TreeSet, walk it once comparing candidates in increasing seat order, and replace the best only on a strictly larger distance — that is what makes ties go to the smaller seat. leave is a single O(log n) removal. With at most 10⁴ calls, the O(n) scan per seat is fast enough; the faster version keeps the gaps themselves in a TreeSet ordered by size.

▶Full solution
📐 Pseudocode · Scan Neighbouring Pairs 
taken ← empty TreeSet

function seat():
    if taken is empty:
        p ← 0
    else:
        best ← taken.first();  p ← 0                 // sitting at seat 0
        prev ← null
        for s in taken, in increasing order:
            if prev ≠ null:
                d ← (s - prev) / 2                     // integer division
                if d > best: best ← d;  p ← prev + d  // strictly larger: ties keep the smaller seat
            prev ← s
        if (n - 1) - taken.last() > best:
            p ← n - 1
    taken.add(p)
    return p

function leave(p): taken.remove(p)
TimeO(k) seat · O(log k) leave
SpaceO(k)
Problem 04 · Skip List
Design Skiplist
🔗 LC 1206 - Design Skiplist
Hard Linked levels, random heights Google · Amazon
›
Problem

Build a skip list without any library ordered structure. Support search(target), add(num) and erase(num) (which removes one copy and reports whether it existed). Duplicates are allowed.

add(1), add(2), add(3), search(0) → false, add(4), search(1) → true erase(0) → false, erase(1) → true, search(1) → false
Hints
▶Hint 1 — a nudge

All three operations begin the same way. What do you need to know on every level before you can insert or unlink a node?

▶Hint 2 — the key idea

The last node smaller than the target on each level — its predecessor. Write that walk once. Search checks the node after the level-0 predecessor; add and erase splice in or out after each predecessor.

Solution

Use a head node with the maximum number of levels (16 is plenty for 5 × 10⁴ operations) and a level counter for how many are in use. The predecessor walk from the lecture does the real work: start at the top, move right while the next value is smaller, record where you stopped, drop a level. Add picks a coin-flip height and splices the new node in after each recorded predecessor, exactly as a linked-list insert. Erase finds the first node equal to the target on level 0 and unlinks it from every level where the predecessor points at it. Because the walk stops before equal values, duplicates need no special handling.

▶Full solution
📐 Pseudocode · One Predecessor Walk, Three Operations 
MAX_LEVEL ← 16
head ← node with MAX_LEVEL next-pointers;  level ← 1

function predecessors(target):
    pred ← array of size MAX_LEVEL;  cur ← head
    for lv from level - 1 down to 0:
        while cur.next[lv] ≠ null and cur.next[lv].value < target:
            cur ← cur.next[lv]
        pred[lv] ← cur
    return pred

function search(target):
    node ← predecessors(target)[0].next[0]
    return node ≠ null and node.value = target

function add(num):
    pred ← predecessors(num)
    h ← 1
    while h < MAX_LEVEL and random() < 0.5: h ← h + 1
    for lv from level to h - 1: pred[lv] ← head
    level ← max(level, h)
    node ← new node(num) with h next-pointers
    for lv from 0 to h - 1:
        node.next[lv] ← pred[lv].next[lv];  pred[lv].next[lv] ← node

function erase(num):
    pred ← predecessors(num)
    node ← pred[0].next[0]
    if node = null or node.value ≠ num: return false
    for lv from 0 to (number of levels of node) - 1:
        if pred[lv].next[lv] = node:            // the same node, not merely an equal value
            pred[lv].next[lv] ← node.next[lv]
    while level > 1 and head.next[level - 1] = null: level ← level - 1
    return true
TimeO(log n) expected
SpaceO(n) expected
Problem 05 · A Moving k-th Element
Sequentially Ordinal Rank Tracker
🔗 LC 2102 - Sequentially Ordinal Rank Tracker
Hard Two heaps split at k Google · Amazon
›
Problem

Locations are added with a name and a score. A higher score is better; on equal scores the alphabetically smaller name is better. The i-th call to get() returns the i-th best location added so far.

add("bradford",2), add("branford",3), get() → "branford" add("alps",2), get() → "alps" add("orland",2), get() → "bradford"
Hints
▶Hint 1 — a nudge

The position you are asked for only moves forward by one. Can you keep the items split into “already returned” and “the rest”?

▶Hint 2 — the key idea

Two heaps, as in the running median of Lecture 20. The “top” heap keeps the best i − 1 items with its worst on top; the “rest” heap keeps everything else with its best on top — which is exactly the answer to the next get.

Solution

An order-statistic tree would answer “i-th best” directly, but Java does not have one. The query index only ever grows by one, and that makes two heaps enough. Keep the invariant: before the i-th get, top holds exactly the best i − 1 items. A new item might belong in it, so push it into top and then move top’s worst item into rest — top keeps its size and its “best items” property. A get moves the best of rest into top and returns it: it is the best item not among the best i − 1, which is the i-th best. Both heaps use the same comparison, one reversed.

▶Full solution
📐 Pseudocode · The Boundary Moves One Step per Get 
// better(a, b): a.score > b.score, or equal scores and a.name < b.name
top ← heap with the WORST item on top          // the best i - 1 items
rest ← heap with the BEST item on top          // everything else

function add(name, score):
    top.push((name, score))
    rest.push(top.pop())                          // top keeps its size; its worst moves out

function get():
    item ← rest.pop()                             // best item outside the top i - 1
    top.push(item)                                // top now holds the best i
    return item.name
TimeO(log n) per call
SpaceO(n)
