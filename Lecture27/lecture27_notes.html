Dynamic Programming III — Knapsack & Subsets

“One table, three loop orders. Getting the order wrong does not crash — it silently answers a different question.”

📚 Lecture 27 of 38 Phase 4 — Dynamic Programming ⏱ 6 days 🎯 25 problems 💼 Google · Amazon · Meta · Microsoft
🌍
Why does this topic matter?
Interview problems almost never say “knapsack”. They say partition these stones, hit this target, fit these strings inside these limits. All of them are the same table, and once you can see the skeleton through the wording, a whole family of Medium and Hard problems becomes one solved problem with different labels.
By the end of this lecture you can
  • Recognise the knapsack skeleton inside a word problem
  • Tell 0/1, unbounded and bounded apart — and write each loop order correctly
  • Turn subset-sum, partition and target-sum questions into knapsack form
  • Use the same table to count ways or to optimise value
  • Compress a 2D table to 1D without letting an item be used twice

🎒 The Knapsack Skeleton

Every problem in this lecture has the same three pieces. Name them before writing anything.

Piece In the classic problem In a disguised one
Items things you may pack numbers, coins, words, dice
Capacity the bag's weight limit a target sum, a letter budget, a number of rolls
Objective maximise value count ways, decide feasibility, minimise waste
📐 Pseudocode · 0/1 Knapsack, the 2D Version 
// dp[i][c] = best value using the first i items with capacity c
dp ← (n+1) × (capacity+1) table of zeros

for i from 1 to n:
    for c from 0 to capacity:
        dp[i][c] ← dp[i-1][c]                     // skip item i
        if weight[i-1] ≤ c:
            take ← dp[i-1][c - weight[i-1]] + value[i-1]   // ← note i-1
            dp[i][c] ← max(dp[i][c], take)

return dp[n][capacity]

// "Take" reads the PREVIOUS row, which is what stops item i from being
// used twice. Everything else in this lecture is a variation on that line.

🔢 The Three Knapsacks

Same table, three rules about how often an item may be used. The rule lives entirely in the loop order.

0/1 — Each Item at Most Once

📐 Pseudocode · 0/1, Compressed to 1D 
dp ← array of capacity + 1 zeros

for each item:
    for c from capacity down to item.weight:      // ← BACKWARDS
        dp[c] ← max(dp[c], dp[c - item.weight] + item.value)

// Going backwards, dp[c - weight] has not been touched yet in this
// item's pass, so it still means "without this item". Going forwards
// would read a value that already includes it — that is unbounded.

Unbounded — Reuse as Often as You Like

📐 Pseudocode · Unbounded 
dp ← array of capacity + 1 zeros

for each item:
    for c from item.weight to capacity:        // ← FORWARDS
        dp[c] ← max(dp[c], dp[c - item.weight] + item.value)

// Coin Change from Lecture 25 is exactly this, with min() and a count.

Bounded — A Limited Supply

Each item exists k times. The lazy fix is to duplicate the item k times and run 0/1; the interview answer is binary splitting.

📐 Pseudocode · Bounded via Binary Splitting 
// 13 copies → bundles of 1, 2, 4, and the remainder 6.
// Any count from 0 to 13 is some subset of those bundles.
for each item with count k:
    power ← 1
    while k > 0:
        take ← min(power, k)
        add a virtual item of weight take × item.weight
                       and value take × item.value
        k ← k - take
        power ← power × 2

run 0/1 knapsack over the virtual items      // O(capacity × Σ log kᵢ)
🛑
The loop direction is the entire difference. Backwards means each item is used at most once; forwards means it may repeat. Neither version crashes on the wrong input — you simply get the answer to the other problem. When a knapsack solution is “almost right”, check this first.

📏 Compressing to 1D, Safely

The 2D table is easier to reason about; the 1D array is what you write once you trust yourself. The compression is safe only when the loop direction preserves the meaning of the cell you are reading.

Variant Reads Loop over capacity Because
0/1 previous row backwards lower cells must still exclude this item
Unbounded current row forwards lower cells should already include it
Two capacities (e.g. 0s and 1s) previous row both dimensions backwards same argument, twice
🧠
Sanity check with two items. Take weights [2] and capacity 4 with value 3. Backwards gives 3; forwards gives 6, because the single item was packed twice. Running that tiny case by hand is faster than re-reading the loop.

🧩 Subsets in Disguise

Most interview knapsacks never mention a bag. Here is the translation table — learn to perform it in the first minute.

Problem says Items Capacity Objective
“split into two equal halves” the numbers total / 2 feasibility (boolean)
“+ or − each number to reach target” the numbers (total + target) / 2 count subsets
“smash stones together” the stones total / 2 maximise one pile, answer is the gap
“at most m zeros and n ones” the strings two capacities maximise the count taken
“how many ways to make change” the coins the amount count, unbounded
📐 Pseudocode · Partition Equal Subset Sum 
function canPartition(nums):
    total ← sum(nums)
    if total is odd: return false      // a cheap, decisive check
    target ← total ÷ 2

    dp ← array of target + 1, all false
    dp[0] ← true                            // the empty subset makes 0

    for x in nums:
        for c from target down to x:   // backwards: each number used once
            dp[c] ← dp[c] or dp[c - x]

    return dp[target]
⚠️
Target Sum needs one line of algebra. Let P be the numbers you make positive and N the rest. Then P − N = target and P + N = total, so P = (total + target) / 2. If that is not a whole number — or is negative — there are no solutions. Otherwise it is a plain count-the-subsets knapsack.

Counting vs Optimising

The same table answers both kinds of question. Only the combine step changes.

Question Cell holds Combine Base case
Is it possible? boolean or dp[0] = true
How many ways? count + dp[0] = 1
Best value? number max dp[0] = 0
Fewest items? number min dp[0] = 0, rest infinity
🛑
Combinations or permutations? When counting, the nesting decides. Items outside, capacity inside counts combinations — {1,2} and {2,1} are the same (Coin Change II). Capacity outside, items inside counts permutations — they are different (Combination Sum IV). Swapping the loops changes the answer without changing a single line inside them.

⚠️ Complexity & The Classic Bugs

Variant Time Space Note
0/1 knapsack O(n · capacity) O(capacity) pseudo-polynomial: capacity is a value, not a length
Unbounded O(n · capacity) O(capacity) same table, forward loop
Bounded (binary split) O(capacity · Σ log k) O(capacity) beats duplicating every copy
Two capacities O(n · m · n) O(m · n) Ones and Zeroes
Partition into k subsets O(k · 2ⁿ) O(2ⁿ) bitmask search — not a knapsack
Bug Symptom Fix
Forward loop in a 0/1 knapsack Items get used more than once; answers too large Loop capacity backwards
Loops nested the wrong way round when counting Permutations counted as combinations, or vice versa Items outside for combinations, capacity outside for permutations
Wrong base case Every answer is 0, or off by one way dp[0] is true / 1 / 0 depending on the question
Odd total in a partition problem Wasted work, or a wrong true Return false immediately — halves must be whole
Negative or non-integer derived target Index error in Target Sum Check (total + target) is even and non-negative
Huge capacity Memory blows up despite “polynomial” time Capacity is exponential in its digits — look for meet in the middle instead
💡
How to spot it in an interview. A set of items, each with a cost, and a budget that must not be exceeded — then either “can we hit exactly”, “how many ways” or “what is the best value”. Name the items, the capacity and the objective out loud; the loop order follows from whether items repeat.

Problem 01 · Subset Sum
Partition Equal Subset Sum
🔗 LC 416 - Partition Equal Subset Sum
Medium 0/1 Knapsack (Feasibility) Amazon · Google · Meta
›
Problem

Return true if the array can be split into two subsets with equal sums.

nums = [1, 5, 11, 5] → true  ([1,5,5] and [11])  |   nums = [1, 2, 3, 5] → false
Hints
▶Hint 1 — a nudge

You do not need to build both halves. If one subset sums to half the total, the rest does too.

▶Hint 2 — the key idea

So: can any subset reach total / 2? That is 0/1 knapsack with a boolean table — and the capacity loop must run backwards.

Solution

The reduction is the interview answer: two-way partition becomes one subset-sum question. An odd total is an instant false, which also protects the integer division. The backwards loop is what keeps each number to a single use — run it forwards and [5] alone would appear to reach 10.

▶Full solution
📐 Pseudocode · Boolean Knapsack 
function canPartition(nums):
    total ← sum(nums)
    if total mod 2 ≠ 0: return false
    target ← total ÷ 2

    dp ← array of target + 1, all false
    dp[0] ← true                             // empty subset sums to 0

    for x in nums:
        for c from target down to x:    // backwards = use x at most once
            dp[c] ← dp[c] or dp[c - x]

    return dp[target]

// [1,5,11,5]: total 22, target 11 → 11 reachable (11, or 1+5+5) → true ✓
TimeO(n × total)
SpaceO(total)
Problem 02 · Counting Combinations
Coin Change II
🔗 LC 518 - Coin Change II
Medium Unbounded Knapsack (Count) Amazon · Google · Meta
›
Problem

Return the number of coin combinations that add up to amount. Coins may be reused, and order does not matter.

amount = 5, coins = [1, 2, 5] → 4  (5; 2+2+1; 2+1+1+1; 1×5)
Hints
▶Hint 1 — a nudge

Start from Coin Change in Lecture 25 and change min to +. What else has to be right?

▶Hint 2 — the key idea

The nesting. Coins on the outside and amounts on the inside counts each combination once; swapping them would count orderings.

Solution

Two decisions, both invisible in the code. dp[0] = 1 says there is exactly one way to make nothing — take no coins — and without it every count is zero. The loop order is the real lesson: with coins outermost, a combination is only ever built in non-decreasing coin order, so {1,2} and {2,1} are the same path. The inner loop runs forwards because a coin may repeat.

▶Full solution
📐 Pseudocode · Coins Outside, Amounts Inside 
function change(amount, coins):
    dp ← array of amount + 1 zeros
    dp[0] ← 1                                // one way to make nothing

    for coin in coins:                    // ← combinations: coins outermost
        for a from coin to amount:      // forwards: reuse allowed
            dp[a] ← dp[a] + dp[a - coin]

    return dp[amount]

// Swap the two loops and you count permutations instead — that is
// Combination Sum IV, a different problem with identical arithmetic.
TimeO(coins × amount)
SpaceO(amount)
Problem 03 · Two Capacities
Ones and Zeroes
🔗 LC 474 - Ones and Zeroes
Medium 0/1 Knapsack, 2D Capacity Google · Amazon
›
Problem

Given binary strings and budgets of m zeros and n ones, return the largest number of strings you can select without exceeding either budget.

strs = ["10","0001","111001","1","0"], m = 5, n = 3 → 4
Hints
▶Hint 1 — a nudge

Each string costs something. What exactly does it cost, and what is the bag?

▶Hint 2 — the key idea

It costs its count of zeros and its count of ones — two capacities at once. The table becomes dp[zeros][ones], and both loops run backwards.

Solution

Nothing new except a second dimension. Each string is an item whose weight is a pair, so the table is two-dimensional and the objective is a plain count. Both capacity loops must run backwards for the same reason as the 1D case: the cells being read have to still mean “before this string”. Count the zeros and ones once per string rather than inside the loops.

▶Full solution
📐 Pseudocode · Backwards in Both Dimensions 
function findMaxForm(strs, m, n):
    dp ← (m+1) × (n+1) table of zeros

    for s in strs:
        zeros ← count of '0' in s;  ones ← length(s) - zeros
        for i from m down to zeros:      // both backwards
            for j from n down to ones:
                dp[i][j] ← max(dp[i][j], dp[i - zeros][j - ones] + 1)

    return dp[m][n]
TimeO(L × m × n)
SpaceO(m × n)
Problem 04 · Disguised Subset Sum
Last Stone Weight II
🔗 LC 1049 - Last Stone Weight II
Medium 0/1 Knapsack (Minimise Gap) Amazon · Google
›
Problem

Repeatedly smash two stones together; the difference survives. Return the smallest possible weight of the final stone.

stones = [2, 7, 4, 1, 8, 1] → 1
Hints
▶Hint 1 — a nudge

Every smash assigns a stone a plus or a minus sign. What does the final weight equal, in terms of two groups?

▶Hint 2 — the key idea

The gap between the two groups: total − 2 × oneGroup. Minimise that by making one group as close to total / 2 as possible — a subset-sum maximisation.

Solution

The simulation is a red herring; the algebra is the problem. Any sequence of smashes is equivalent to splitting the stones into two piles, and the survivor is the difference between the pile sums. So fill a boolean (or max-value) knapsack up to total / 2, take the largest reachable sum, and return total − 2 × best. The same reduction solves Partition Array to Minimise Sum Difference.

▶Full solution
📐 Pseudocode · Minimise the Gap 
function lastStoneWeightII(stones):
    total ← sum(stones)
    half ← total ÷ 2

    dp ← array of half + 1 zeros             // dp[c] = best sum ≤ c that is reachable
    for s in stones:
        for c from half down to s:
            dp[c] ← max(dp[c], dp[c - s] + s)

    return total - 2 × dp[half]

// [2,7,4,1,8,1]: total 23, best pile ≤ 11 is 11 → 23 − 22 = 1 ✓
TimeO(n × total)
SpaceO(total)
Problem 05 · Order Matters
Combination Sum IV
🔗 LC 377 - Combination Sum IV
Medium Unbounded (Permutations) Google · Amazon · Meta
›
Problem

Count the number of ordered sequences of the given numbers that add up to target. Different orders count separately, despite the title.

nums = [1, 2, 3], target = 4 → 7
Hints
▶Hint 1 — a nudge

This looks identical to Coin Change II. Read the examples: is (1,2,1) the same as (1,1,2)?

▶Hint 2 — the key idea

No — order counts. So the target must be the outer loop and the numbers the inner one, which lets every ordering be built independently.

Solution

A deliberate trap, paired with the previous card. With the target outside, dp[t] is reached by appending any number last, so each ordering is counted once. With numbers outside, orderings collapse into combinations. Nothing else differs — same array, same addition, same base case of 1. The follow-up about negative numbers has no answer under this model, since sequences could then be infinite.

▶Full solution
📐 Pseudocode · Target Outside, Numbers Inside 
function combinationSum4(nums, target):
    dp ← array of target + 1 zeros
    dp[0] ← 1

    for t from 1 to target:            // ← permutations: target outermost
        for x in nums:
            if x ≤ t: dp[t] ← dp[t] + dp[t - x]

    return dp[target]

// nums [1,2,3], target 4 → 7 sequences, including (1,2,1) and (2,1,1)
TimeO(target × n)
SpaceO(target)
Problem 06 · State as a Difference
Tallest Billboard
🔗 LC 956 - Tallest Billboard
Hard Knapsack Keyed on Difference Google · Amazon
›
Problem

Split the rods into two disjoint groups of equal total height (some rods may go unused) and return the largest such height.

rods = [1, 2, 3, 6] → 6  (1+2+3 against 6)
Hints
▶Hint 1 — a nudge

Two piles, and only their difference matters while you are building them. Can the difference be the state?

▶Hint 2 — the key idea

Let dp[d] be the tallest shorter pile achievable when the piles differ by d. Each rod goes on the taller pile, the shorter pile, or neither.

Solution

A capacity-free knapsack: the state is not a budget but a difference, and the value stored is the shorter pile’s height. Each rod gives three transitions, and adding it to the shorter pile may flip which pile is taller — that is the fiddly case. The answer is dp[0], the tallest pair of equal piles. Differences are bounded by the total, so the table stays small.

▶Full solution
📐 Pseudocode · dp[difference] = shorter pile 
function tallestBillboard(rods):
    dp ← map {0: 0}                    // difference → tallest shorter pile

    for rod in rods:
        next ← copy of dp              // "use this rod nowhere"
        for (d, shorter) in dp:
            // add to the taller pile: difference grows
            next[d + rod] ← max(next[d + rod], shorter)

            // add to the shorter pile: it may overtake
            newDiff ← |d - rod|
            newShorter ← shorter + min(d, rod)
            next[newDiff] ← max(next[newDiff], newShorter)
        dp ← next

    return dp[0]
TimeO(n × total)
SpaceO(total)
