Design Data Structures

“One structure per job, linked by keys, kept consistent on every call.”

📚 Lecture 43 of 45 Phase 6 — Interview Mastery ⏱ 5 days 🎯 20 problems 💼 Google · Amazon · Meta · Microsoft · Uber
🌍
Why does this topic matter?
“Design a class that supports these four operations, each in O(1)” is one of the most common interview formats, because it tests everything at once: knowing what each structure is fast at, combining them, and writing code that keeps several pieces of state in agreement. No single structure from this course answers such a question alone. The skill is choosing the right two or three and wiring them together — and that skill follows a method you can learn.
By the end of this lecture you can
  • Turn a list of operations and speed limits into a design, step by step
  • Recognise the classic combinations: map + linked list, array + map, buckets, heap + map, ordered sets
  • Use lazy deletion, history lists and lazy iterators when direct updates are too slow
  • State the invariant that links your structures, and check every operation against it
  • Answer the usual follow-ups: thread safety, memory limits and scale
🧠
The picture to keep in your head: a restaurant kitchen. No single cook does everything. The ticket rail keeps orders in sequence, the pass holds dishes ready to go out, and the order number printed on every ticket and plate is what ties them together. A designed data structure is the same: each part is fast at one job, and a shared key — an id, a node reference, an array index — lets one part find the matching entry in another. The rule of the kitchen is the rule of the code: when an order changes, every station that holds it must hear about it.

🗺️ The Design Method

Every design question hands you the same two lists: the operations and how fast each must be. Work through five steps, out loud, before writing any code.

Step Ask yourself Example: insert, remove, getRandom — all O(1)
1. List What are the operations and their required costs? Three operations, each O(1)
2. Match Which structure does each operation fast? Random pick: an array. Find a value: a HashMap.
3. Link What does one structure store about the other? The map stores each value’s index in the array
4. Invariant What must always be true between them? map[v] = i exactly when array[i] = v
5. Walk Does every operation keep the invariant? Remove fills the gap with the last element — so fix that element’s index too
You need, fast… Reach for Seen in
Lookup by key HashMap Lecture 16
Random element; index access Array / ArrayList Lecture 11
Move or remove a known element anywhere Doubly linked list Lecture 14
Newest / oldest item Stack / queue / deque Lecture 15
Smallest or largest, repeatedly Heap Lecture 20
Nearest, range, both ends, arbitrary delete TreeMap / TreeSet Lecture 41
Prefix searches over strings Trie Lecture 36
Range sums with updates Fenwick / segment tree Lecture 37

🧩 Classic Combinations

HashMap + doubly linked list: order you can rearrange

A linked list keeps things in an order and can move or remove a node in O(1) — if you already hold the node. A HashMap from key to node gives you exactly that. This is the LRU cache you built in Lecture 16: the list runs from most to least recently used, get moves a node to the front, and eviction removes the back. The list is doubly linked because removing a node means reconnecting its previous and next neighbours.

📐 Pseudocode · LRU in Ten Lines (Recap of Lecture 16) 
map ← key → node;  list ← doubly linked list with dummy head and tail

function get(key):
    if key not in map: return -1
    node ← map[key];  list.moveToFront(node)       // O(1): we hold the node
    return node.value

function put(key, value):
    if key in map: map[key].value ← value;  list.moveToFront(map[key]);  return
    if size(map) = capacity:
        old ← list.removeBack();  map.remove(old.key)   // node stores its key for this
    node ← new node(key, value);  list.addFront(node);  map[key] ← node

Array + map of indices: O(1) delete and random pick

An array picks a random element in O(1) but deletes from the middle in O(n). Unless order matters: then swap with the last element and pop the end. A map from value to index finds the element to remove. The step people forget is updating the moved element’s index.

📐 Pseudocode · Remove by Swapping With the Last 
function remove(val):                       // arr, and pos: value → index
    if val not in pos: return false
    i ← pos[val];  last ← arr[length(arr) - 1]
    arr[i] ← last;  pos[last] ← i                 // move the last element into the hole
    arr.removeLast();  pos.remove(val)            // works even when val IS the last element
    return true

Buckets by count: O(1) “most” and “least”

When the query is “the most (or least) frequent” and counts change by one at a time, keep a bucket per count: a map from count to the keys that have it, plus the current minimum or maximum count. A key moves to the neighbouring bucket on each update, and the extreme bucket is always known. LFU Cache (Lecture 14), All O’one (Lecture 16) and Maximum Frequency Stack (Lecture 6) are all this idea.

💤 Lazy Deletion

Java’s PriorityQueue cannot change or remove an arbitrary entry quickly (remove(x) is O(n)). The fix is to stop trying. Keep the true state in a HashMap; treat the heap as a list of hints. On an update, push a new entry and leave the old one where it is. When an entry reaches the top, check it against the map: if it no longer matches, it is stale — throw it away and look again.

📐 Pseudocode · Heap With Lazy Deletion 
current ← id → priority                         // the truth
heap ← max-heap of (priority, id)               // hints, possibly stale

function update(id, p):  current[id] ← p;  heap.push((p, id))
function remove(id):     current.remove(id)          // the heap is not touched

function popBest():
    while heap is not empty:
        (p, id) ← heap.pop()
        if id in current and current[id] = p:   // still true?
            current.remove(id);  return id
    return none
// Every entry is pushed once and popped at most once: O(log n) amortised per call.

🕓 History & Snapshots

“What was the value at time t?” Copying everything at every snapshot is too slow and too big. Instead, record only the changes: for each key, a list of (time, value) pairs. Times only increase, so the list is sorted, and the value at time t is the last change at or before t — a binary search (Lecture 13). You met this in Time-Based Key-Value Store (Lecture 5); Snapshot Array below is the same idea with a snapshot counter as the clock.

➡️ Iterators

An iterator hands out items one at a time through hasNext() and next(). The good ones are lazy: rather than building the whole answer in the constructor, they do just enough work to produce the next item. That saves memory, and an iterator over a huge or endless source only works this way. Put the work in hasNext(), make it safe to call twice in a row, and have next() call it first.

💬 Follow-up Questions

After the code works, interviewers often push on the design. You are not expected to build these, only to reason about them.

Follow-up A good first answer
“Several threads use it at once.” Guard every method with one lock (synchronized) so the structures never disagree; then mention finer-grained locks or ConcurrentHashMap as an optimisation.
“It no longer fits in memory.” Evict (LRU/LFU), or split the keys across machines by hash — a first step towards the system design of Lecture 45.
“Reads far outnumber writes.” Precompute on write so that reads are trivial.
“Lazy deletion grows the heap.” Rebuild the heap from the live entries once stale ones outnumber live ones.

⚠️ Complexity & Classic Bugs

Design Operations Cost
HashMap + doubly linked list get, put, evict O(1)
Array + map of indices insert, remove, getRandom O(1) average
Buckets by count increment, decrement, min/max O(1)
Heap + lazy deletion update, remove, pop best O(log n) amortised
History list per key set, get at time t O(1) set, O(log h) get
Bug Symptom Fix
Updating one structure but not the other Lookups return values that were removed Write the invariant down; check it at the end of every method
Swap-with-last without fixing the moved index Later removes delete the wrong element Set pos[last] ← i before popping
LRU node that does not store its key Cannot remove the evicted key from the map Store the key in the node
Popping a heap entry without checking it Returns an item that was edited or removed Compare with the map; skip stale entries
Changing state before knowing the call can succeed A failed withdrawal still removes notes Plan on a copy; commit only on success
next() without calling hasNext() first Returns a list, or crashes on an empty one Put the preparation in hasNext(); call it from next()

How to spot it. “Design a class”, “implement the following methods”, a required cost per operation (“each in O(1)”, “average O(1)”), or a list of calls with expected outputs instead of a single input.

💪 In-Lecture Practice Problems

Five designs, one per technique: an array with an index map, a history list, a heap of free slots, lazy deletion, and a lazy iterator.

Problem 01 · Array + Map of Indices
Insert Delete GetRandom O(1) - Duplicates allowed
🔗 LC 381 - Insert Delete GetRandom O(1) - Duplicates allowed
Hard Swap with last, sets of indices Amazon · Meta · LinkedIn
›
Problem

A collection that may hold duplicates. insert(val) returns true if val was not present before; remove(val) removes one copy and returns true if there was one; getRandom() returns an element with probability proportional to how many copies it has. Every call must be O(1) on average.

insert(1) → true, insert(1) → false, insert(2) → true getRandom() → 1 with probability 2/3 remove(1) → true, getRandom() → 1 or 2, each with probability 1/2
Hints
▶Hint 1 — a nudge

Without duplicates this is Lecture 5’s RandomizedSet: an array plus value → index. What must change when a value can sit in several places?

▶Hint 2 — the key idea

Map each value to a set of indices. Removing takes any one index from val’s set, moves the last element into it, and moves that element’s index in its own set from the end to the hole.

Solution

Run the design method. getRandom in O(1) forces an array: a uniform random index is automatically proportional to the number of copies. Finding some copy of val forces a map, and since a value may sit at several indices, the map stores a set of them. The invariant: i is in idx[v] exactly when nums[i] = v. Insert appends and records the index. Remove takes any index i of val, copies the last element into position i, adds i to the last element’s set and removes its old index (the end), then pops. The order of those two set updates matters when the element removed is itself the last one — add first, then discard, and the case takes care of itself.

▶Full solution
📐 Pseudocode · Array + Value → Set of Indices 
nums ← empty array;  idx ← value → set of indices

function insert(val):
    idx[val].add(length(nums));  nums.append(val)
    return size(idx[val]) = 1                     // first copy?

function remove(val):
    if idx[val] is empty: return false
    i ← any element of idx[val];  idx[val].remove(i)
    lastIndex ← length(nums) - 1;  last ← nums[lastIndex]
    nums[i] ← last
    idx[last].add(i)                              // add first ...
    idx[last].remove(lastIndex)                   // ... then drop the old slot
    nums.removeLast()
    return true

function getRandom():
    return nums[randomInt(0, length(nums) - 1)]
TimeO(1) average per call
SpaceO(n)
Problem 02 · History List
Snapshot Array
🔗 LC 1146 - Snapshot Array
Medium Changes per index + binary search Google · Amazon
›
Problem

An array of length n starts as all zeros. set(index, val) changes one element; snap() takes a snapshot and returns its id (0, 1, 2…); get(index, snapId) returns the value the element had when that snapshot was taken.

SnapshotArray(3), set(0, 5), snap() → 0, set(0, 6), get(0, 0) → 5
Hints
▶Hint 1 — a nudge

Copying the array on each snap costs O(n) per call and O(n · snaps) memory. Most elements never change between snapshots — what is worth recording?

▶Hint 2 — the key idea

Only the changes. For each index, keep a list of (snapId, value). A get finds the last change with snapId ≤ the requested one by binary search.

Solution

This is the history technique with the snapshot counter as the clock. Each index starts with the entry (−1, 0), so a get before any change finds 0. A set appends (currentSnapId, val) — or overwrites the last entry if it already has the current id, because only the final value before a snap counts. snap() just returns the counter and increments it: O(1), with nothing copied. Because snapIds in each list only increase, get can binary-search for the last entry at or before the requested snapshot. Memory is proportional to the number of sets, not to n times the number of snapshots.

▶Full solution
📐 Pseudocode · Record Changes, Not Copies 
history[i] ← [(-1, 0)] for every index i;  snapId ← 0

function set(index, val):
    h ← history[index]
    if h.last.snap = snapId: h.last.value ← val   // same snapshot: overwrite
    else: h.append((snapId, val))

function snap():
    snapId ← snapId + 1
    return snapId - 1

function get(index, id):
    h ← history[index]
    k ← last position in h with h[k].snap ≤ id   // binary search
    return h[k].value
TimeO(1) set/snap · O(log s) get
SpaceO(n + sets)
Problem 03 · Heap of Free Slots
Dinner Plate Stacks
🔗 LC 1172 - Dinner Plate Stacks
Hard Stacks + min-heap of non-full Amazon
›
Problem

An endless row of stacks, each holding at most capacity plates. push(val) goes on the leftmost stack that is not full; pop() takes from the rightmost non-empty stack; popAtStack(i) takes from stack i. Pops return −1 when there is nothing to take.

capacity 2: push 1, 2, 3, 4, 5 → stacks [1,2] [3,4] [5] popAtStack(0) → 2, push(20), push(21), popAtStack(0) → 20, popAtStack(2) → 21 pop() → 5, pop() → 4, pop() → 3, pop() → 1, pop() → -1
Hints
▶Hint 1 — a nudge

Push and pop each need a different “extreme” stack. Which one is cheap to find already, and which needs a helper structure?

▶Hint 2 — the key idea

The rightmost non-empty stack is the end of the list once empty stacks are trimmed off. The leftmost non-full stack needs a min-heap of indices — add an index when a pop makes a full stack non-full, and skip entries that went stale.

Solution

Scanning for the leftmost non-full stack is O(number of stacks) per push, too slow for 2 × 10⁵ calls. So keep a min-heap free of indices that might be non-full. Entries can go stale in two ways: the stack filled up again, or it was trimmed off the end. Rather than deleting them, push checks the top and discards stale entries — lazy deletion from the lecture. A stack enters the heap when it is created with room left, or when a pop takes it from full to not full. Pop trims empty stacks from the end of the list, then pops the last one. Each index is pushed into and popped from the heap a bounded number of times per operation, so everything is O(log n) amortised.

▶Full solution
📐 Pseudocode · Lazily Cleaned Heap of Free Stacks 
stacks ← empty list of stacks;  free ← min-heap of indices

function push(val):
    while free is not empty and
          (free.top ≥ length(stacks) or stacks[free.top] is full):
        free.pop()                                // stale entry
    if free is not empty:
        i ← free.top;  stacks[i].push(val)
        if stacks[i] is full: free.pop()
    else:
        stacks.append(new stack containing val)
        if capacity > 1: free.push(length(stacks) - 1)

function pop():
    while stacks is not empty and stacks.last is empty:
        stacks.removeLast()                       // trim empty stacks off the end
    if stacks is empty: return -1
    return popAtStack(length(stacks) - 1)

function popAtStack(i):
    if i ≥ length(stacks) or stacks[i] is empty: return -1
    if stacks[i] is full: free.push(i)          // it is about to have room
    return stacks[i].pop()
TimeO(log n) amortised
SpaceO(n)
Problem 04 · Lazy Deletion
Design Task Manager
🔗 LC 3408 - Design Task Manager
Medium Map of truth + heap of hints Amazon · Google
›
Problem

Tasks have a user, a unique id and a priority. Support add, edit(taskId, newPriority), rmv(taskId), and execTop(), which removes the task with the highest priority (the highest taskId on ties) and returns its userId, or −1 if none are left.

TaskManager([[1,101,10],[2,102,20],[3,103,15]]) add(4,104,5), edit(102,8), execTop() → 3 (task 103, priority 15) rmv(101), add(5,105,15), execTop() → 5
Hints
▶Hint 1 — a nudge

A heap gives the top task quickly. What goes wrong when a task’s priority is edited, or it is removed?

▶Hint 2 — the key idea

Leave old heap entries alone. Keep taskId → (userId, priority) in a map as the truth, push a fresh entry on every edit, and in execTop discard any popped entry that no longer matches the map.

Solution

This is lazy deletion exactly as in the lecture. The map is the single source of truth; the max-heap, ordered by (priority, taskId), may contain entries that are out of date. An edit updates the map and pushes a new heap entry; a remove only deletes from the map. execTop pops until it finds an entry whose task still exists with the same priority — the priority check matters, because an edited task leaves its old entry behind, and without the check the task would run at its old priority. Every entry is pushed once and discarded at most once, so each call is O(log n) amortised.

▶Full solution
📐 Pseudocode · Skip Stale Entries at the Top 
info ← taskId → (userId, priority)               // the truth
heap ← max-heap of (priority, taskId)           // ties: larger taskId first

function add(userId, taskId, priority):
    info[taskId] ← (userId, priority);  heap.push((priority, taskId))

function edit(taskId, newPriority):
    add(info[taskId].userId, taskId, newPriority)   // old entry becomes stale

function rmv(taskId): info.remove(taskId)

function execTop():
    while heap is not empty:
        (p, t) ← heap.pop()
        if t in info and info[t].priority = p:
            user ← info[t].userId;  info.remove(t)
            return user
    return -1
TimeO(log n) amortised
SpaceO(n + edits)
Problem 05 · Lazy Iterator
Flatten Nested List Iterator
🔗 LC 341 - Flatten Nested List Iterator
Medium Stack, work done in hasNext Meta · Google · LinkedIn
›
Problem

Each element of a nested list is either an integer or another nested list. Build an iterator that returns all the integers in order through hasNext() and next().

[[1,1],2,[1,1]] → 1, 1, 2, 1, 1 [1,[4,[6]]] → 1, 4, 6
Hints
▶Hint 1 — a nudge

Flattening everything in the constructor with recursion works. How would you avoid doing all that work up front?

▶Hint 2 — the key idea

Keep a stack of items still to visit, in reverse order. In hasNext, while a list is on top, replace it by its elements (reversed). When an integer is on top, you are ready.

Solution

The eager version flattens the whole structure with a DFS in the constructor — correct, and fine in most interviews, but it spends all its time and memory before the first next(). The lazy version replaces the recursion with an explicit stack, as in Lecture 18’s iterative traversals. The stack holds items still to visit, the next one on top. hasNext() unpacks lists on the top until an integer surfaces or the stack is empty; it changes nothing if an integer is already on top, so calling it twice is safe. next() calls hasNext() and pops. Empty inner lists simply unpack to nothing.

▶Full solution
📐 Pseudocode · Unpack Only When Needed 
function constructor(nestedList):
    stack ← elements of nestedList, pushed from last to first

function hasNext():
    while stack is not empty and stack.top is a list:
        list ← stack.pop()
        push the elements of list from last to first   // first element ends on top
    return stack is not empty

function next():
    hasNext()                                     // make sure an integer is on top
    return stack.pop()
TimeO(1) amortised per call
SpaceO(N + L)
