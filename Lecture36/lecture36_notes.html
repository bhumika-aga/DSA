Tries — Prefix Trees

“A hash set answers is this word here? — a trie also answers could a word still start like this?”

📚 Lecture 36 of 45 Phase 5 — Advanced Structures ⏱ 4 days 🎯 18 problems 💼 Google · Meta · Amazon
🌍
Why does this topic matter?
A hash set stores words as opaque blobs: it can tell you whether "apple" is present, and nothing else. A trie stores them letter by letter along shared paths, so a partial word is a real position in the structure. That one change is what makes autocomplete, wildcard matching, dictionary search on a grid and maximum-XOR queries all fall out of the same twenty lines of code. It is also the structure interviewers reach for when they want to see whether you can design one from scratch rather than import it.
By the end of this lecture you can
  • Write insert, search and startsWith from memory in O(L)
  • Explain the memory cost of a trie and when a hash set wins
  • Run a DFS inside a trie to handle wildcards
  • Drive a grid DFS with a trie and prune it as words are found
  • Build a binary trie and answer maximum-XOR queries bit by bit
🧠
The picture to keep in your head: Signposts at every junction. Picture every word as a road. Words that start the same share the road until they part ways, and at every junction a signpost lists the letters you can take next. Looking up a word means following the signs; autocomplete means driving to where the typed prefix ends and listing every destination further along.

🔠 The Node

A trie is a tree where the edges carry the letters, not the nodes. A node is therefore just two things: where you can go next, and whether the path that reached you spells a complete word.

📐 Pseudocode · The Whole Structure 
structure TrieNode:
    children ← array of 26 empty slots     // or a map: char → TrieNode
    isWord   ← false                       // does a word END here?

root ← new TrieNode()                      // the root spells the empty string

// "app" and "apple" share four nodes:
//   root -a-> -p-> -p-> [isWord] -l-> -e-> [isWord]
// The shared prefix is stored exactly once. That is the entire idea.
🧠
The isWord flag is not optional. Without it the trie cannot distinguish “app is a stored word” from “app is only on the way to apple”. Every trie bug list starts with someone who returned true for the second case.

⚙️ Insert, Search, Prefix

All three operations are the same walk. They differ only in what they do when the walk ends: insert creates missing nodes, search checks the flag, and startsWith simply reports that it arrived.

📐 Pseudocode · The Three Operations 
function insert(word):
    node ← root
    for ch in word:
        i ← ch - 'a'
        if node.children[i] is empty:
            node.children[i] ← new TrieNode()
        node ← node.children[i]
    node.isWord ← true

function walk(word):                    // shared by both lookups
    node ← root
    for ch in word:
        i ← ch - 'a'
        if node.children[i] is empty: return null
        node ← node.children[i]
    return node

function search(word):
    node ← walk(word)
    return node ≠ null AND node.isWord

function startsWith(prefix):
    return walk(prefix) ≠ null      // arriving is enough

// Every operation is O(L) in the length of the word — independent of how
// many words the trie holds. A hash set is O(L) too, because hashing reads
// the whole string; the trie's win is startsWith, which a hash set cannot do.

A Dry Run

Insert "app", then "apple", then ask three questions. Follow the flag, not the node.

Call Walk Ends at Result
insert("app") creates a → p → p node “app” isWord ← true
insert("apple") reuses a → p → p, creates l → e node “apple” isWord ← true
search("app") a → p → p node “app” ✅ true — the flag is set
search("appl") a → p → p → l node “appl” ❌ false — arrived, flag unset
startsWith("appl") a → p → p → l node “appl” ✅ true — arriving is enough

💾 Memory & Trade-offs

The array-of-26 node is fast and simple, and it is also the reason tries are called memory-hungry: every node pays for 26 pointers even if it uses one. A hash map per node pays only for the children that exist, at the cost of a lookup per character.

Choice Per node Use it when
TrieNode[26] 26 references, dense Lowercase letters only — the interview default
Map<Character, TrieNode> One entry per real child Unicode, mixed case, or a sparse alphabet
TrieNode[2] 2 references Binary tries over the bits of a number
Hash set of strings One entry per word You only ever ask for whole words — then a trie is overkill
⚠️
Say the trade-off out loud in the interview. Total space is O(total characters inserted) nodes, each with an alphabet-sized array. For 10 000 words averaging 8 letters that is up to 80 000 nodes × 26 references — noticeably more than the strings themselves. You take that deal because prefix queries become free.

❓ Wildcard Search

search("b.d") should match bad, bud and bid. A single walk cannot do it, because a dot has 26 possible next steps — so the walk becomes a DFS, and the position in the pattern becomes part of the state.

📐 Pseudocode · DFS Inside the Trie 
function search(pattern):
    return dfs(pattern, 0, root)

function dfs(pattern, i, node):
    if node is null: return false
    if i = length(pattern): return node.isWord

    ch ← pattern[i]
    if ch = '.':
        for c from 0 to 25:          // try every branch
            if dfs(pattern, i + 1, node.children[c]):
                return true
        return false

    return dfs(pattern, i + 1, node.children[ch - 'a'])

// Cost: O(L) with no dots, up to O(26^d · L) with d dots. Leading dots are
// the expensive ones, because nothing has narrowed the search yet.
🧠
Why the trie and not 26 regex matches? Because a missing child ends a whole branch instantly. The trie has already thrown away every word that does not share the prefix you have matched so far, so the DFS explores only paths that really exist in the dictionary.

🔍 Trie + Grid DFS

Word Search II asks for every dictionary word hidden in a board. The naive plan — run a grid DFS once per word — costs words × m × n × 4ᴹ. Reverse the roles: walk the board once, and let the trie tell you when to give up.

📐 Pseudocode · One Walk, All Words 
function findWords(board, words):
    root ← trie built from words          // store the word at its end node
    found ← empty list

    for each cell (r, c):
        dfs(r, c, root)

    function dfs(r, c, node):
        if (r, c) outside board: return
        ch ← board[r][c]
        if ch = '#': return              // already on this path

        next ← node.children[ch - 'a']
        if next is null: return            // no word continues this way

        if next.word ≠ null:
            found.add(next.word)
            next.word ← null              // report each word once

        board[r][c] ← '#'                 // mark visited
        for (nr, nc) in four neighbours of (r, c):
            dfs(nr, nc, next)
        board[r][c] ← ch                  // restore on the way out

    return found

// The single line "if next is null: return" replaces the entire word loop.

Pruning as You Go

Storing the word on its end node and blanking it after the first find solves duplicates. The stronger trick is to delete exhausted branches: after the recursion returns, if next has no children left and no word, unlink it from its parent. The trie shrinks as the search proceeds, and a board full of the same letter stops being a disaster.

⚠️
The classic timeout. A 12×12 board of all as with the word "aaaaaaaaaaaa" in the dictionary is the test that kills unpruned solutions. Without pruning you re-explore the same dead branch from every cell; with it, the branch disappears the first time it is exhausted.

⚡ Binary (XOR) Tries

Nothing says the alphabet has to be letters. Insert the 32 bits of a number from the most significant end and you get a two-child trie where “go to the opposite bit” is exactly the greedy step maximum XOR needs: to make a bit of the answer 1, the two numbers must differ there.

📐 Pseudocode · Maximum XOR Against the Trie 
function insert(x):
    node ← root
    for b from 31 down to 0:
        bit ← (x >> b) AND 1
        if node.children[bit] is empty:
            node.children[bit] ← new TrieNode()
        node ← node.children[bit]

function maxXorWith(x):
    node ← root;  best ← 0
    for b from 31 down to 0:
        bit  ← (x >> b) AND 1
        want ← 1 - bit                       // the opposite bit gives a 1
        if node.children[want] ≠ empty:
            best ← best OR (1 << b)
            node ← node.children[want]
        else:
            node ← node.children[bit]        // forced to match
    return best

// Insert every number, then query every number: O(32n) instead of O(n²).
🧠
Greedy is safe here because the bits are ordered by value: one high bit outweighs every lower bit combined, so taking it whenever it is available can never be a mistake. This is the same argument that justifies the bit-by-bit mask solution you met in Lecture 9 — the trie just makes the candidate lookup explicit.

Queries with a ceiling (“the partner must be ≤ m”) look harder, but they are the same trie used offline: sort the numbers, sort the queries by their limit, and insert numbers into the trie only as the limit grows past them. Every query then runs against a trie that contains exactly the legal partners.

🌊 Streams & Reversed Tries

Some problems ask about endings rather than beginnings: “does the last part of everything I have seen so far spell a word?” A trie only matches forwards — so reverse the words, and feed the stream backwards.

📐 Pseudocode · Stream of Characters 
function StreamChecker(words):
    root ← trie of every word REVERSED
    seen ← empty list                        // the stream so far
    maxLen ← length of the longest word

    function query(ch):
        seen.append(ch)
        node ← root
        for i from length(seen) - 1 down to max(0, length(seen) - maxLen):
            node ← node.children[seen[i] - 'a']   // walking BACKWARDS
            if node is null: return false
            if node.isWord: return true
        return false

// Reversing turns "ends with" into "starts with". The maxLen bound keeps
// each query at O(longest word) no matter how long the stream grows.

🧩 When to Reach for One

What the problem asks Structure Why
Is this exact word in the set? Hash set O(L) and far less memory — a trie buys nothing
Does any word start with this prefix? Trie A prefix is a node; a hash set has no such concept
All words sharing a prefix, ranked Trie + DFS (or sort + binary search) The prefix node roots the whole answer set
Match a pattern with wildcards Trie + DFS Dead branches are pruned by construction
Find many words inside one text or grid Trie driving the search One traversal for the whole dictionary
Maximum XOR, or bitwise partner queries Binary trie Greedy on bits from the top, O(32) per query
Does the stream end with a word? Reversed trie Reversal turns a suffix question into a prefix one
💡
A sorted array is the poor man's trie. If the dictionary is static and you only need prefix queries, sorting it once and binary searching for the prefix range gives the same answers with no extra structure. Mention it — interviewers like candidates who know when not to build something.

⚠️ Complexity & Bugs

L is the length of one word, n the number of words, Σ the alphabet size (26 here).

Operation Time Space Note
insert / search / startsWith O(L) — Independent of how many words are stored
Build the whole trie O(n · L) O(n · L · Σ) Nodes × alphabet array
Wildcard search, d dots O(Σᵈ · L) O(L) stack Leading dots cost the most
All words under a prefix O(size of that subtree) O(L) stack Output-sensitive — you pay for what you return
Word Search II O(m · n · 4 · 3ᴹ⁻¹) O(total letters) Pruning is what makes it fast in practice
Binary trie insert / query O(32) O(32n) Fixed bit width, so effectively O(1)
Bug Symptom Fix
Treating “node exists” as “word” search("appl") returns true Check isWord, not the node
Forgetting the empty string Crash or wrong answer on "" The root is a valid end node — decide what it means
Indexing with the raw character Array out of bounds Always ch - 'a', and validate the range
Not un-marking the grid cell Word Search II misses valid words Restore board[r][c] after the recursion
Duplicate words in the output Same word found from two cells Blank the word on its end node after the first find
Binary trie built from bit 0 up Greedy picks the wrong partner Insert from the highest bit down — value order matters
Rebuilding the trie inside a loop Passes small tests, times out on large ones Build once, query many times
🔍
How to spot it in an interview. The words prefix, autocomplete, dictionary and starts with are the obvious signals. The quieter ones are “given a list of words, for each …” — which usually means one shared structure rather than n separate searches — and any XOR question with n up to 10⁵, which is a binary trie asking to be built.

Problem 01 · The Structure Itself
Implement Trie (Prefix Tree)
🔗 LC 208 - Implement Trie (Prefix Tree)
Medium Trie Fundamentals Google · Amazon · Microsoft
›
Problem

Implement a trie with insert, search and startsWith.

insert("apple"), search("apple") → true, search("app") → false, startsWith("app") → true
Hints
▶Hint 1 — a nudge

A node needs exactly two fields. What is the second one, and what goes wrong without it?

▶Hint 2 — the key idea

All three methods are the same walk down the tree. Only the ending differs: create, check the flag, or just report arrival.

Solution

Write this one until it is muscle memory — it is the base of every other problem in this lecture. The single design decision is the isWord flag: search requires it, startsWith ignores it. Factoring the shared walk into one private helper is worth saying out loud, because it is what stops the two lookups drifting apart when you extend them later.

▶Full solution
📐 Pseudocode · Insert, Search, startsWith 
structure TrieNode:
    children ← array of 26 empty slots
    isWord   ← false

function Trie():
    root ← new TrieNode()

function insert(word):
    node ← root
    for ch in word:
        i ← ch - 'a'
        if node.children[i] is empty:
            node.children[i] ← new TrieNode()
        node ← node.children[i]
    node.isWord ← true

function walk(s):
    node ← root
    for ch in s:
        node ← node.children[ch - 'a']
        if node is empty: return null
    return node

function search(word):     return walk(word) ≠ null and walk(word).isWord
function startsWith(pre):  return walk(pre) ≠ null
TimeO(L) per op
SpaceO(total letters)
Problem 02 · Wildcards
Design Add and Search Words Data Structure
🔗 LC 211 - Design Add and Search Words Data Structure
Medium Trie + DFS Meta · Google · Amazon
›
Problem

Support addWord and search, where the searched word may contain . as a wildcard matching any single letter.

addWord("bad"), addWord("dad"), search("b..") → true, search("b.e") → false
Hints
▶Hint 1 — a nudge

With no dots this is the plain walk. What does a dot force you to do that a letter does not?

▶Hint 2 — the key idea

Branch. At a dot, recurse into all 26 children and return true if any branch succeeds — the pattern index becomes part of the state.

Solution

The walk becomes a DFS, and that is the whole difference. Pass the pattern position and the current node; a letter takes one step, a dot tries every existing child. The trie earns its place here because a missing child kills an entire branch at once — with a hash set you would have to test every stored word. Note that the cost is worst when the dots come first, before anything has narrowed the search.

▶Full solution
📐 Pseudocode · Branch at Every Dot 
function addWord(word):
    // identical to the plain trie insert

function search(pattern):
    return dfs(pattern, 0, root)

function dfs(pattern, i, node):
    if node is null: return false
    if i = length(pattern): return node.isWord

    ch ← pattern[i]
    if ch ≠ '.':
        return dfs(pattern, i + 1, node.children[ch - 'a'])

    for c from 0 to 25:                  // wildcard: try them all
        if dfs(pattern, i + 1, node.children[c]):
            return true
    return false
TimeO(26ᵈ · L)
SpaceO(total letters)
Problem 03 · Autocomplete
Search Suggestions System
🔗 LC 1268 - Search Suggestions System
Medium Trie + DFS (or sort + binary search) Amazon · Google
›
Problem

After each character the user types, return up to three lexicographically smallest products that start with what has been typed so far.

products = ["mobile","mouse","moneypot","monitor","mousepad"], searchWord = "mouse" → suggestions after m, mo, mou, mous, mouse
Hints
▶Hint 1 — a nudge

Each prefix of the search word is a node. What lives underneath that node?

▶Hint 2 — the key idea

Exactly the matching products. Sort the products first, then a DFS from the prefix node meets them in lexicographic order — stop after three.

Solution

Two clean solutions, and you should name both. With a trie: insert the sorted products, walk one character at a time, and DFS the subtree for the first three words — if the walk falls off the trie, every later prefix is empty too. Without a trie: sort the products and binary search the prefix range, which is shorter to write and often what an interviewer expects when the dictionary is static. The trie version is the one that generalises to a live, changing catalogue.

▶Full solution
📐 Pseudocode · Walk the Prefix, DFS the Subtree 
function suggestedProducts(products, searchWord):
    sort(products)                           // lexicographic order for free
    root ← trie built from products
    result ← empty list
    node ← root

    for ch in searchWord:
        if node ≠ null:
            node ← node.children[ch - 'a']
        result.add(collect(node, 3))

    return result

function collect(node, limit):             // DFS in a..z order
    out ← empty list
    if node is null: return out
    if node.isWord: out.add(node.word)
    for c from 0 to 25:
        if size(out) = limit: break
        out.addAll(collect(node.children[c], limit - size(out)))
    return out
TimeO(n·L + L·3)
SpaceO(total letters)
Problem 04 · Dictionary on a Board
Word Search II
🔗 LC 212 - Word Search II
Hard Trie + Grid DFS Google · Amazon · Airbnb
›
Problem

Given an m × n board of letters and a list of words, return every word that can be formed by a path of adjacent cells without reusing a cell.

board = [[o,a,a,n],[e,t,a,e],[i,h,k,r],[i,f,l,v]], words = ["oath","pea","eat","rain"] → ["oath","eat"]
Hints
▶Hint 1 — a nudge

Running the single-word Word Search once per word repeats the same board walks. What could tell you, mid-walk, that no word continues this way?

▶Hint 2 — the key idea

A trie of all the words. Walk the board once, carrying a trie node alongside the cell — when the child is missing, stop immediately.

Solution

This is the problem the whole lecture builds to. Inverting the loops — board outside, dictionary inside the trie — turns a per-word search into one traversal. Three details make it pass: store the word itself on its end node so you can report it without rebuilding the string, blank that field after the first find so duplicates are impossible, and unlink exhausted nodes so a board of identical letters does not explode.

▶Full solution
📐 Pseudocode · One Traversal, Trie-Guided 
function findWords(board, words):
    root ← trie of words, storing word at its end node
    found ← empty list

    for r from 0 to rows - 1:
        for c from 0 to cols - 1:
            dfs(r, c, root)
    return found

function dfs(r, c, node):
    if (r, c) off board: return
    ch ← board[r][c]
    if ch = '#': return                  // on the current path

    next ← node.children[ch - 'a']
    if next is null: return                // the trie prunes the walk

    if next.word ≠ null:
        found.add(next.word)
        next.word ← null                      // report once

    board[r][c] ← '#'
    dfs(r-1, c, next);  dfs(r+1, c, next)
    dfs(r, c-1, next);  dfs(r, c+1, next)
    board[r][c] ← ch                          // restore

    if next has no children and next.word = null:
        unlink next from node                 // prune the dead branch
TimeO(m·n·4·3ᴸ⁻¹)
SpaceO(total letters)
Problem 05 · Binary Trie
Maximum XOR With an Element From Array
🔗 LC 1707 - Maximum XOR With an Element From Array
Hard Binary Trie + Offline Queries Google · Amazon
›
Problem

For each query (x, m), return the maximum of x XOR nums[j] over all nums[j] ≤ m, or −1 if no element qualifies.

nums = [0,1,2,3,4], queries = [[3,1],[1,3],[5,6]] → [3, 3, 7]
Hints
▶Hint 1 — a nudge

Without the ≤ m limit this is the plain maximum-XOR trie. What does the limit change about which numbers the trie should contain?

▶Hint 2 — the key idea

Answer the queries out of order. Sort nums and sort queries by m, then insert numbers only as m grows past them — every query sees exactly its legal candidates.

Solution

Two ideas stacked. The binary trie gives the greedy bit-by-bit maximum, and processing the queries offline — in an order of your choosing, remembering to restore the original order at the end — turns the constraint into a simple insertion schedule. Answering queries out of order is a technique worth naming; it reappears with segment trees and with Mo’s algorithm later in this phase.

▶Full solution
📐 Pseudocode · Sort Both, Insert Lazily 
function maximizeXor(nums, queries):
    sort(nums)
    order ← indices of queries sorted by their limit m
    ans ← array of -1, length = number of queries
    root ← empty binary trie
    i ← 0

    for q in order:
        (x, m) ← queries[q]
        while i < length(nums) and nums[i] ≤ m:   // now legal
            insert(nums[i]);  i ← i + 1
        if i > 0:
            ans[q] ← maxXorWith(x)                    // greedy, bit 31 → 0

    return ans

// maxXorWith takes the opposite bit when that child exists, otherwise the
// matching one — a high bit is worth more than every lower bit together.
TimeO((n + q) log + 32(n + q))
SpaceO(32n)
Problem 06 · Reversed Trie
Stream of Characters
🔗 LC 1032 - Stream of Characters
Hard Reversed Trie Google · Amazon
›
Problem

Given a list of words, answer for each streamed character whether some word is a suffix of the characters seen so far.

words = ["cd","f","kl"], then a, b, c, d → false, false, false, true
Hints
▶Hint 1 — a nudge

A trie matches forwards, but the question is about endings. What transformation makes those the same problem?

▶Hint 2 — the key idea

Store the words reversed, and walk the stream backwards from the newest character. Stop after the longest word’s length.

Solution

The reversal is the entire solution, and it is a move worth keeping: any “ends with” question becomes a “starts with” question if you flip both sides. The second detail is the bound — walking back only as far as the longest word keeps each query O(L) however long the stream becomes, which is what stops the obvious solution from degrading over millions of queries. A real production system would use Aho-Corasick; say so, then write this.

▶Full solution
📐 Pseudocode · Reverse the Words, Walk Backwards 
function StreamChecker(words):
    root ← empty trie
    for w in words: insert(reverse(w))
    maxLen ← length of the longest word
    seen ← empty list

function query(letter):
    seen.append(letter)
    node ← root
    lo ← max(0, length(seen) - maxLen)

    for i from length(seen) - 1 down to lo:
        node ← node.children[seen[i] - 'a']
        if node is null: return false      // no suffix can match
        if node.isWord: return true

    return false
TimeO(L) per query
SpaceO(total letters)
