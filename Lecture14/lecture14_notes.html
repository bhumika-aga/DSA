Linked Lists

"Linear logic with non-contiguous memory. Master pointers to master the universe."

📚 Lecture 14 of 45 Phase 2 — Core Data Structures ⏱ 6 days 🎯 27 problems 💼 Google · Meta · Uber
🌍
Why does this topic matter?
Linked Lists are the first true pointer-based data structure you will encounter. Mastering them teaches you how to manipulate heap objects by reference — the foundational skill behind Trees, Graphs, and advanced caches. Linked List problems are common at Google, Meta, and Uber because they test pointer logic and visual memory reasoning simultaneously. A solid Linked List foundation makes Trees feel trivial.
By the end of this lecture you can
  • Understand linked list as a recursive data structure
  • Master pointer manipulation (next, prev, dummy head sentinel)
  • Learn fast & slow pointer technique (Floyd's Cycle Detection algorithm)
  • Implement reversal in-place (iterative and recursive forms)
  • Handle edge cases: empty list, single node, circular list

📖 What is a Linked List?

An array stores elements in contiguous (side-by-side) memory cells. A Linked List stores elements in scattered memory. Each element (called a Node) is an independent heap object containing:

  1. The actual data (e.g. an int value)
  2. A pointer (reference) to the next Node in the chain

The last node's next field is null, marking the end. There is no random access — to reach the Kth node you must traverse from the head, following next pointers one by one. This is why indexing a Linked List is O(N), not O(1).

Array vs Linked List — Memory Model: ARRAY ┌────┬────┬────┬────┬────┐ │ 10 │ 20 │ 30 │ 40 │ 50 │ ← contiguous, same block └────┴────┴────┴────┴────┘ LINKED ┌──────────┐ ┌──────────┐ ┌──────────┐ LIST: │ val: 10 │────▶│ val: 20 │────▶│ val: 30 │──▶ null │ next: ● │ │ next: ● │ │ next:null│ └──────────┘ └──────────┘ └──────────┘ [0x1A4 heap] [0x7B2 heap] [0x3F9 heap] ← scattered
💡
Array vs Linked List — Key Trade-offs:
✅ O(1) insertion/deletion at head — just redirect one pointer
✅ Dynamic size — no pre-allocation, grows as needed
❌ O(N) random access — must traverse from the head
❌ Extra memory per node for the next pointer
❌ Poor cache performance — nodes are scattered in memory

🔑 How Pointer Manipulation Works

All Linked List operations — insert, delete, reverse — reduce to reassigning next (and prev) pointers. The chain exists only because of these references. Lose a reference and you permanently lose access to the rest of the list.

INSERT node C between A and B: BEFORE: A ──▶ B ──▶ null STEP 1: C.next = B // C now points to B ← DO THIS FIRST STEP 2: A.next = C // A now points to C AFTER: A ──▶ C ──▶ B ──▶ null ✓ ⚠️ If you did A.next = C FIRST, you lose the reference to B — memory leak! DELETE node B from: A ──▶ B ──▶ C ──▶ null STEP 1: A.next = B.next // Skip B entirely AFTER: A ──▶ C ──▶ null ✓ (B is now unreferenced → GC)

🏗️ Anatomy & Types

Unlike Arrays, which store elements in contiguous memory, a Linked List stores elements in scattered memory. Each element (Node) contains data and a Pointer (reference) to the next node.

1.1 — The ListNode blueprint

📐 Pseudocode · The List Node 
record ListNode:
    val              // the data
    next             // the following node, or null at the tail
    prev             // the preceding node — doubly linked lists only

// A new node starts detached:
node ← ListNode(val = x, next = null, prev = null)

Picture three boxes, each with two compartments: a value, and an arrow to the next box. The list 3 → 7 → 9 is three such boxes, and the last arrow points to null — “nothing after this”. The variable head is simply a note of where the first box is. That is the whole structure, and it explains its one weakness: to reach the 9 you must start at the head and follow two arrows, because nothing records where the third box lives.

Box 1 Box 2 Box 3
val 3 7 9
next → Box 2 → Box 3 null
⚠️
Lose the head, lose the list. If you overwrite head without saving it anywhere, no variable points to the first box any more, and the whole list is unreachable. Most linked-list bugs are some version of this: an arrow reassigned before the old target was saved.

1.2 — The Three Fundamental Types

  • Singly Linked List: Forward only. Last node points to null.
  • Doubly Linked List (DLL): Forward & Backward. Allows O(1) deletion if node is given.
  • Circular: Last node points to the Head. Essential for buffers and round-robin scheduling.
Type Can walk backwards? Delete a node you are holding Typical use
Singly linked No O(n) — you must find its predecessor Most interview problems; stacks
Doubly linked Yes O(1) — it knows its own predecessor LRU caches; browser back/forward
Circular Keeps going round Depends on single or double links Round-robin schedulers; ring buffers

🧠 Core Algorithms

2.1 — The Sentinel Strategy (Dummy Head)

A "Sentinel" node is a dummy node that points to the actual head. It eliminates special if (head == null) cases for insertion/deletion.

📐 Pseudocode · Delete Example 
function removeElements(head, val):
    dummy ← ListNode(0)            // sentinel: deleting the head is no longer a special case
    dummy.next ← head
    curr ← dummy

    while curr.next ≠ null:
        if curr.next.val = val:
            curr.next ← curr.next.next   // unlink — and DON'T advance, the new next may match too
        else:
            curr ← curr.next
    return dummy.next

Why is the head special? Every other node is removed the same way: stand on the node before it and point its arrow past it. The head has no node before it — so without a sentinel, deleting it needs a separate branch of code, and forgetting that branch is the classic bug. The dummy node gives the head a predecessor, so one rule covers every position. At the end you return dummy.next, which is the real head even if the old one was deleted.

Step List (after the dummy) curr stands on Action
start 6 → 1 → 6 dummy next is 6: unlink it
2 1 → 6 dummy next is 1: move forward
3 1 → 6 1 next is 6: unlink it
4 1 1 next is null: stop — return dummy.next = 1

2.2 — In-place Reversal

The bread and butter of interview questions. The trick is to maintain three pointers: prev, curr, and nextNode.

📐 Pseudocode · Reverse a Linked List 
// Three pointers, one pass. Draw it once and you own it forever.
prev ← null
cur  ← head

while cur ≠ null:
    nxt ← cur.next      // 1. remember where we were going
    cur.next ← prev     // 2. flip the arrow backwards
    prev ← cur          // 3. shuffle both pointers forward
    cur  ← nxt

return prev              // prev is the new head

Here is the loop on 1 → 2 → 3, one row per trip. Watch the arrows flip one at a time: prev is the finished, reversed part; cur is the node being turned round; nxt is the bookmark that stops you losing the rest of the list.

After trip prev cur Reversed so far Still to do
start null 1 (nothing) 1 → 2 → 3
1 1 2 1 2 → 3
2 2 3 2 → 1 3
3 3 null 3 → 2 → 1 (nothing)
💡
Why save nxt first? Step 2 overwrites cur.next. Without the bookmark, the only arrow to the rest of the list is gone the moment you flip it.

🔄 Advanced Variations

3.1 — Copy List with Random Pointers

💡
The Interweaving Pattern: Instead of using a HashMap for O(n) space, interweave copy nodes between originals: A -> A' -> B -> B'. This allows random assignment in O(1) space.
📐 Pseudocode · Logic Flow 
// Copy a list with random pointers in O(1) extra space:
// 1. Interweave copies:  after every node, insert its copy
//                        curr.next ← ListNode(curr.val, next = curr.next)
// 2. Assign randoms:     curr.next.random ← curr.random.next   (if curr.random ≠ null)
// 3. Detach:             original.next ← original.next.next, and the same for the copies

Each node here has a second arrow, random, that can point to any node in the list or to nothing. The difficulty is that when you copy a node, its random arrow still points into the original list. The straightforward fix is a hash map from each original node to its copy: one pass creates every copy, a second pass sets copy.next and copy.random by looking the originals up. That is O(n) extra space and is a perfectly good interview answer; the interweaving trick above is the follow-up for O(1) space.

3.2 — Flattening Multilevel DLL

Treat the child pointer like a "branch". Use a recursive approach or an iterative stack to attach children between curr and curr.next.

📐 Pseudocode · Recursive Blueprint 
function flatten(head):
    if head = null: return head
    curr ← head
    while curr ≠ null:
        if curr.child ≠ null:
            next ← curr.next
            childHead ← flatten(curr.child)

            // splice the flattened child in after curr
            curr.next ← childHead
            childHead.prev ← curr
            curr.child ← null

            // reconnect the child's tail to what used to follow curr
            tail ← childHead
            while tail.next ≠ null: tail ← tail.next
            if next ≠ null:
                tail.next ← next
                next.prev ← tail
        curr ← curr.next
    return head

⚡ Cache Design

👀
Preview — covered fully in Lecture 43. Caches are your first look at designing a structure from two others. This section shows how a HashMap and a doubly linked list work together for LRU and LFU. Lecture 43 (Design Data Structures) turns this into a general method, with lazy deletion, history lists and iterators added.

4.1 — Least Recently Used (LRU) Cache

Requires O(1) operations for both get and put. Achieved by combining a HashMap (for lookups) and a Doubly Linked List (for ordering).

📐 Pseudocode · HashMap + DLL Logic 
record LRUCache:
    map        // key → node, for O(1) lookup
    list       // doubly linked list, most recently used at the head

function get(cache, key):
    if key not in cache.map: return -1
    node ← cache.map[key]
    cache.list.moveToHead(node)      // mark as most recently used
    return node.val

Why these two structures? A hash map finds any key in O(1), but it has no idea which key was used longest ago. A doubly linked list keeps items in order of use and can move or remove a node in O(1) — if you already have the node in hand. Put them together and each covers the other’s gap: the map hands you the node, the list moves it. put is the other half:

📐 Pseudocode · put — Insert or Update, Evicting When Full 
function put(cache, key, value):
    if key in cache.map:                        // already present: update and refresh
        node ← cache.map[key]
        node.val ← value
        cache.list.moveToHead(node)
        return
    if size(cache.map) = cache.capacity:        // full: evict the least recently used
        old ← cache.list.removeTail()
        delete cache.map[old.key]
    node ← ListNode(key, value)
    cache.list.addToHead(node)
    cache.map[key] ← node

4.2 — Least Frequently Used (LFU) Logic

LFU is the "hard mode" variation. Instead of one list, it uses multiple lists mapped by frequency. If total capacity is reached, evict the LRU item from the minFrequency list.

📐 Pseudocode · LFU Solution Architecture 
// 1. freqMap:  frequency → doubly linked list of nodes with that frequency
// 2. cache:    key → node, for O(1) lookup
// 3. minFreq:  the smallest frequency present, for O(1) eviction

function updateFreq(node):
    remove node from freqMap[node.freq]
    if node.freq = minFreq and freqMap[node.freq] is empty:
        minFreq ← minFreq + 1
    node.freq ← node.freq + 1
    append node to freqMap[node.freq]      // create the list if needed

One detail decides most LFU bugs: when several keys share the lowest frequency, the one to evict is the least recently used among them. That is why each frequency gets its own doubly linked list rather than a set — the list remembers the order of use within one frequency, exactly as the LRU cache does.

⚠️ Classic Bugs

The complexity section above covers the costs. These are the mistakes that most often break code that looks correct — check your solution against every row before calling it done.

Bug Symptom Fix
Reassigning next before saving it The rest of the list is lost Save first: nxt ← cur.next
Reading cur.next.next at the end NullPointerException Check cur ≠ null and cur.next ≠ null
Deleting the head node The old head is returned Put a dummy node in front of the head
Fast pointer moving one step Cycle detection never finishes early Move fast two steps per turn
Not cutting a list after splitting it Infinite loop later Set tail.next ← null
Returning head after reversing Returns a one-node list Return prev
Picking the wrong middle node Wrong half on even lengths Decide which middle you need and test length 2

💪 In-Lecture Practice Problems

Problem 01 · Recursion
Reverse Nodes in k-Group
🔗 LC 25 - Reverse Nodes in k-Group
Hard Amazon · Meta · Microsoft · Google Recursion
›
Problem

Reverse nodes of a linked list k at a time and return the modified list. If the number of nodes is not a multiple of k, the left-out nodes at the end should remain as they are.

Hints
▶Hint 1 — a nudge

Reversing the whole list is easy. The hard part is stitching each reversed block back on.

▶Hint 2 — the key idea

Before reversing a block, walk k nodes ahead to confirm a full group exists. Keep a pointer to the node before the group so you can reattach both ends.

Solution
▶Full solution
📐 Pseudocode · Recursive 
function reverseKGroup(head, k):
    // 1. is there a full group of k nodes?
    curr ← head
    count ← 0
    while curr ≠ null and count ≠ k:
        curr ← curr.next
        count ← count + 1
    if count < k: return head               // leftover tail stays as it is

    // 2. reverse everything after this group first
    curr ← reverseKGroup(curr, k)

    // 3. reverse this group, pointing its tail at the reversed remainder
    repeat k times:
        tmp ← head.next
        head.next ← curr
        curr ← head
        head ← tmp
    return curr                             // the new head of this group
TimeO(N)
SpaceO(N/k)
Problem 02 · Two Pointers
Palindrome Linked List
🔗 LC 234 - Palindrome Linked List
Easy Amazon · Meta · Microsoft Fast & Slow
›
Problem

Check if a linked list is a palindrome in O(1) extra space. Requires finding the middle, reversing the second half, and comparing.

Hints
▶Hint 1 — a nudge

You cannot walk backwards. What if the second half pointed the other way?

▶Hint 2 — the key idea

Find the middle with slow/fast pointers, reverse the second half in place, then compare the two halves node by node. Restore the list afterwards if asked.

Solution
▶Full solution
📐 Pseudocode · Mid + Reverse 
function isPalindrome(head):
    fast ← head;  slow ← head
    while fast ≠ null and fast.next ≠ null:      // slow ends at the middle
        fast ← fast.next.next
        slow ← slow.next
    if fast ≠ null: slow ← slow.next             // odd length: skip the centre node

    slow ← reverse(slow)                          // reverse the second half
    fast ← head
    while slow ≠ null:
        if fast.val ≠ slow.val: return false
        fast ← fast.next
        slow ← slow.next
    return true
TimeO(N)
SpaceO(1)
Problem 03 · Pointers
Remove Nth Node From End
🔗 LC 19 - Remove Nth Node
Medium Amazon · Meta · Google · Microsoft Gap Pointers
›
Problem

Remove the n-th node from the end of the list and return its head. Solve in one pass using a dummy head and a constant gap.

Hints
▶Hint 1 — a nudge

Two passes work. One pass needs a fixed-width gap between two pointers.

▶Hint 2 — the key idea

Advance a lead pointer n steps first, then move both until the lead hits the end. A dummy head node makes deleting the actual head painless.

Solution
▶Full solution
📐 Pseudocode · One Pass 
function removeNthFromEnd(head, n):
    start ← ListNode(0)
    start.next ← head
    slow ← start;  fast ← start
    repeat n + 1 times: fast ← fast.next      // open a gap of n nodes
    while fast ≠ null:                        // slide the gap to the end
        slow ← slow.next
        fast ← fast.next
    slow.next ← slow.next.next                // slow sits just before the target
    return start.next
TimeO(N)
SpaceO(1)
Problem 04 · Merge Sort
Sort List
🔗 LC 148 - Sort List
Medium Amazon · Google · Meta · Microsoft Divide & Conquer
›
Problem

Sort a linked list in O(n log n) time and O(1) memory. Divide and conquer approach is best.

Hints
▶Hint 1 — a nudge

O(n log n) with O(1) space rules out quicksort and rules out copying to an array.

▶Hint 2 — the key idea

Merge sort: split at the middle with slow/fast pointers, sort both halves, then merge. Cut the list in two — set prev.next = null — or you will recurse forever.

Solution
▶Full solution
📐 Pseudocode · Merge Sort 
function sortList(head):
    if head = null or head.next = null: return head
    prev ← null;  slow ← head;  fast ← head
    while fast ≠ null and fast.next ≠ null:   // find the middle
        prev ← slow
        slow ← slow.next
        fast ← fast.next.next
    prev.next ← null                          // CUT the list in two, or recursion never ends
    left ← sortList(head)
    right ← sortList(slow)
    return merge(left, right)                 // standard two-list merge
TimeO(N log N)
SpaceO(log N) stack
Problem 05 · Dummy Head
Merge Two Sorted Lists
🔗 LC 21 - Merge Two Sorted Lists
Easy Splice, Do Not Copy Amazon · Apple · Microsoft
›
Problem

Merge two sorted linked lists into one sorted list by splicing the existing nodes together, and return its head.

1 → 2 → 4 and 1 → 3 → 4  →  1 → 1 → 2 → 3 → 4 → 4
Hints
▶Hint 1 — a nudge

Which list's head becomes the answer's head? Handling that case separately is what makes the code messy.

▶Hint 2 — the key idea

Start from a dummy node and keep a tail pointer. Repeatedly attach the smaller head and advance that list. When one list runs out, attach the other whole.

Solution

The dummy node removes every special case: you never ask “is this the first node?”, you just append to tail. Because you relink existing nodes instead of allocating new ones, the extra space is O(1). This merge step is exactly the one that Merge Sort on lists calls, so it is worth being able to write from memory.

▶Full solution
📐 Pseudocode · Dummy + Tail 
function mergeTwoLists(a, b):
    dummy ← new node(0)              // sentinel: never part of the answer
    tail ← dummy

    while a ≠ null and b ≠ null:
        if a.val ≤ b.val:            // ≤ keeps the merge stable
            tail.next ← a;  a ← a.next
        else:
            tail.next ← b;  b ← b.next
        tail ← tail.next

    if a ≠ null: tail.next ← a       // attach whatever is left
    else: tail.next ← b
    return dummy.next
TimeO(n + m)
SpaceO(1)
Problem 06 · Hard Cache
LFU Cache
🔗 LC 460 - LFU Cache
Hard Google · Amazon · Uber
›
Problem

Design and implement a data structure for a Least Frequently Used (LFU) cache. It should support get and put operations in O(1) time complexity.

Hints
▶Hint 1 — a nudge

Like LRU, but ties on frequency must be broken by recency.

▶Hint 2 — the key idea

Map key → node, plus map frequency → doubly linked list of nodes at that frequency, plus a minFreq counter. Evict from the front of the minFreq list.

Solution
▶Full solution
📐 Pseudocode · Frequency Map + DLL 
record LFUCache:
    cache       // key → node
    freqMap     // frequency → doubly linked list of nodes
    capacity
    minFreq

function get(c, key):
    if key not in c.cache: return -1
    node ← c.cache[key]
    updateFreq(c, node)
    return node.val

function updateFreq(c, node):
    oldList ← c.freqMap[node.freq]
    remove node from oldList
    if node.freq = c.minFreq and oldList is empty:
        c.minFreq ← c.minFreq + 1
    node.freq ← node.freq + 1
    append node to c.freqMap[node.freq]     // create the list if it doesn't exist
TimeO(1)
SpaceO(N)
Problem 07 · Floyd's Algorithm
Linked List Cycle Detection
🔗 LC 141
Easy Amazon · Microsoft · Meta · Bloomberg Fast/Slow Pointers
›
Problem

Given head of a linked list, return true if it contains a cycle (a node whose next points back to a previous node).

1 → 2 → 3 → 4 ↑ ↓ └── 6 ← 5 ← cycle → true 1 → 2 → 3 → null ← no cycle → false
Hints
▶Hint 1 — a nudge

A HashSet works but costs O(n) memory. The constraint is O(1).

▶Hint 2 — the key idea

Floyd's tortoise and hare: slow moves 1, fast moves 2. If they ever meet there is a cycle; if fast reaches null there is not.

Solution

Floyd's Tortoise & Hare: slow moves 1 step, fast moves 2 steps. In a cycle, fast laps slow and they meet. No cycle → fast reaches null. Uses O(1) space vs O(N) for a HashSet approach.

▶Full solution
📐 Pseudocode · Floyd's Cycle Detection 
// slow moves 1 step, fast moves 2. If there is a loop they must meet;
// if there isn't, fast falls off the end first.
slow ← head; fast ← head

while fast ≠ null and fast.next ≠ null:
    slow ← slow.next
    fast ← fast.next.next
    if slow = fast: break        // they met — a cycle exists

if fast = null or fast.next = null: return null   // no cycle

// To find WHERE the loop starts: reset one pointer to the head and
// walk both one step at a time. They meet at the entry node.
slow ← head
while slow ≠ fast:
    slow ← slow.next
    fast ← fast.next

return slow

// Why they must meet: once both are inside a cycle of length L,
// fast gains exactly one step on slow per iteration,
// so it catches slow within L iterations. ✓
TimeO(N)
SpaceO(1)
Problem 08 · Carry Propagation
Add Two Numbers
🔗 LC 2
Medium Amazon · Microsoft · Meta · Adobe Linked List Math
›
Problem

Two linked lists represent integers in reverse digit order. Add them, return the sum as a linked list.

l1=2→4→3 (342) l2=5→6→4 (465) 342 + 465 = 807 → Output: 7→0→8
Hints
▶Hint 1 — a nudge

It is long addition, digit by digit, with the digits conveniently already reversed.

▶Hint 2 — the key idea

Walk both lists together carrying the overflow. Keep looping while either list remains or a carry is left — that last case is what people forget.

Solution

Simulate grade-school addition: sum = l1.val + l2.val + carry, node value = sum%10, new carry = sum/10. Treat exhausted list nodes as 0. Add a final carry node if needed.

▶Full solution
📐 Pseudocode · Digit-by-Digit with Carry 
function addTwoNumbers(l1, l2):
    dummy ← ListNode(0)
    curr ← dummy
    carry ← 0
    while l1 ≠ null or l2 ≠ null or carry ≠ 0:   // the final carry needs a node too
        sum ← carry
        if l1 ≠ null:
            sum ← sum + l1.val;  l1 ← l1.next
        if l2 ≠ null:
            sum ← sum + l2.val;  l2 ← l2.next
        carry ← sum ÷ 10
        curr.next ← ListNode(sum mod 10)
        curr ← curr.next
    return dummy.next
// 2+5=7, carry 0 → 7   4+6=10, carry 1 → 0   3+4+1=8, carry 0 → 8
// Result: 7 → 0 → 8 ✓
TimeO(max(M,N))
SpaceO(max(M,N))
