Testing & Debugging Your Own Code

“Code that works on the examples is half done.”

📚 Lecture 3 of 45 Phase 1 — Foundations ⏱ 3 days 🎯 15 problems 💼 Google · Amazon · Meta · Microsoft
🌍
Why does this topic matter?
Writing code that works on the examples is the easy half. The hard half is code that works on every input — the empty list, the single item, the number too big to store. Interviewers deliberately test the awkward cases, and judges hide them in their test sets. This lecture is about finding your own bugs before anyone else does: tracing by hand, a checklist of inputs that break most code, and a calm process for when the computer says you are wrong.
By the end of this lecture you can
  • Dry-run any short piece of code with a trace table
  • Run the edge-case checklist against a solution before calling it done
  • Spot and fix off-by-one errors, including the leftover-group bug
  • State an invariant and use it to locate a bug
  • Read a judge's verdict and know which kind of bug to hunt for
☕
Still on paper. Every technique in this lecture works with a pencil and a sheet of paper, and that is how you should practise it. In an interview there is often no computer to run your code on — tracing it by hand is the test.

✍️ Dry Running on Paper

A dry run means executing your code in your head, one line at a time, writing down every variable as it changes. It feels slow. It is the single fastest way to find a bug, because you see exactly the moment a value goes wrong.

📐 Pseudocode · Code to Trace 
function sumOfEvens(a):
    total ← 0
    for i from 0 to length(a) - 1:
        if a[i] mod 2 = 0:
            total ← total + a[i]
    return total

Trace it on a = [3, 4, 7, 10] by drawing a table: one column per variable, one row per trip round the loop.

i a[i] even? total after
start — — 0
0 3 no 0
1 4 yes 4
2 7 no 4
3 10 yes 14
🧠
Like a pilot’s checklist. Pilots are highly skilled and still read every item off a checklist before take-off — because the mistakes that matter are the ones you are sure you would not make. A trace table is your checklist: boring, mechanical, and it catches exactly the errors your confidence skips over.

🧱 The Edge-Case Checklist

Most wrong answers are not wrong on normal inputs. They are wrong on the extreme ones. Before calling any solution finished, run it (on paper) against this list. Not every row applies to every problem — but you should be able to say why each one does not.

Input What tends to break
Empty — no items at all Reading a[0]; dividing by the length; loops that assume one item
Exactly one item “Compare with the next one” logic; pairs that do not exist
Exactly two items Off-by-one in loops that stop at n − 2
Every value the same Strict < versus ≤; “the second largest”
Already sorted / sorted backwards Algorithms that assume some disorder; worst cases
Negative numbers and zero Tricks that assume positives; products; “max starts at 0”
Very large values Overflow: a sum or product too big for its number type
Duplicates “Find the position” when there are two; counting twice
Odd and even lengths Finding a middle; pairing items up
The answer is at the very start or very end Loops that stop one step early
⚠️
Overflow is invisible. A number type can only hold values up to a limit — for a standard integer, a little over 2 billion. Go past it and the value silently wraps round to a large negative number. Nothing crashes; you just get a wrong answer. Multiplying two numbers near 100,000 already overflows. You will see exactly where the limits are in Lecture 4.

📏 Off-by-One Errors

The most common bug in programming is being off by exactly one: looping one time too many, stopping one step too early, reading one past the end. They come from four questions you answered without noticing.

Ask yourself The two answers that get mixed up
Does the range include its end? 0 to n − 1 (n items) versus 0 to n (n + 1 items)
Is the comparison strict? < versus ≤ — they differ on exactly one value
Where does the loop start? Index 0 or index 1 — counting from 1 is a common habit to unlearn
What happens after the loop? Work left over for the last group, which the loop never processed
💡
The fencepost question. A fence 10 metres long with a post every metre needs 11 posts, not 10. Whenever you count gaps versus items, stop and check with the smallest case: a fence 1 metre long has 2 posts.
📐 Pseudocode · The Leftover Bug — Longest Run of Equal Characters 
function longestRun(s):
    best ← 0;  run ← 1
    for i from 1 to length(s) - 1:
        if s[i] = s[i - 1]:
            run ← run + 1
        else:
            best ← max(best, run)       // a run just ended — record it
            run ← 1
    return best                         // BUG: the LAST run is never recorded

// "aabbb" returns 2, not 3. Fix: return max(best, run).
// The trace table on a string that ENDS with its longest run finds this instantly.

⚓ Invariants: What Must Stay True

An invariant is a sentence that is true before the loop starts and stays true after every trip round it. For sumOfEvens above: “total is the sum of the even numbers among the items already looked at.” If you can state the invariant, you can check it at any row of your trace table — and the first row where it fails is where the bug is.

🚨 Reading a Wrong Answer

When you do run code on a judge like LeetCode, the error message tells you which kind of bug to hunt for. Each verdict points at a different place.

Verdict It means Look for
Wrong Answer It ran, and produced the wrong output An edge case from the checklist; an off-by-one; overflow
Time Limit Exceeded Correct (maybe), but far too slow Your Big-O versus the constraint — Lecture 1’s table
Runtime Error It crashed Reading past the end of a list; dividing by zero; empty input
Memory Limit Exceeded It used too much memory A huge table; recursion too deep; copying data in a loop
🔍
Read the failing input. Judges usually show the exact input that failed. Do not guess — copy it, trace it by hand, and find the first row where your trace disagrees with what you expected.

🔎 Finding the Bug Quickly

When the failing input is large and the trace table would be enormous, halve the search instead. Print the key variables at the midpoint of your code. If they are already wrong, the bug is in the first half; if not, the second. Each check cuts the suspects in half — the same O(log n) idea from Lecture 1, applied to debugging.

📐 Pseudocode · Printing at the Midpoint 
function solve(a):
    b ← step1(a)
    c ← step2(b)
    print("after step 2:", c)         // correct here? then the bug is later
    d ← step3(c)
    return step4(d)

⚖️ Testing Against a Brute Force

Here is the professional trick for problems where the fast solution is clever and the slow one is obvious. Write both. Generate many small random inputs, run both solutions on each, and stop the moment they disagree. That input is a small, concrete bug report — and the brute force from Lecture 2 is what makes it possible.

📐 Pseudocode · A Stress Test 
repeat 1000 times:
    a ← random list of 1 to 8 small numbers
    if fastSolution(a) ≠ bruteForce(a):
        print("mismatch on", a)
        stop

⚠️ Complexity & Classic Bugs

Bug Symptom Fix
Last group never processed Wrong only when the answer is at the end Handle the leftover after the loop
Reading a[0] on empty input Runtime error on the empty case Check for empty first
< where ≤ was meant Wrong only when values are equal Test with all-equal input
Starting “best” at 0 Wrong when every value is negative Start at the first item, or at minus infinity
Multiplying large numbers Negative results from positive inputs Use a bigger number type, or avoid the product
Comparing decimals for equality 0.1 + 0.2 ≠ 0.3 Compare whole numbers or fractions instead
Changing a list while looping over it Items skipped or processed twice Loop over a copy, or build a new list
Testing only the given examples Passes the samples, fails hidden tests Run the edge-case checklist every time

💪 In-Lecture Practice Problems

Four problems where the algorithm is easy and the bugs are not. For each one, write your edge-case list before reading the hints.

Problem 01 · The Overflow Trap
Sign of the Product of an Array
🔗 LC 1822 - Sign of the Product of an Array
Easy Avoid the product Amazon · Microsoft
›
Problem

Return 1 if the product of all numbers is positive, −1 if negative, and 0 if it is zero.

nums = [-1,-2,-3,-4,3,2,1] → 1
Hints
▶Hint 1 — a nudge

Multiply everything, then check the sign. Now try 1,000 numbers each close to 100. What happens to the product?

▶Hint 2 — the key idea

It overflows and the sign becomes garbage. You never needed the product — only whether there is a zero, and how many negatives there are.

Solution

The naive solution is correct in maths and wrong on a computer: a thousand numbers around 100 multiply to a value with two thousand digits, far past any integer type, and the stored result wraps to nonsense. The fix is to notice you only need the sign: a zero anywhere gives 0, otherwise an even count of negatives gives 1 and an odd count gives −1. Whenever a problem asks for a property of a huge value, ask whether you can compute the property without the value.

▶Full solution
📐 Pseudocode · Count Negatives, Never Multiply 
function arraySign(nums):
    negatives ← 0
    for each x in nums:
        if x = 0: return 0              // edge case settles it at once
        if x < 0: negatives ← negatives + 1
    return 1 if negatives mod 2 = 0 else -1
TimeO(n)
SpaceO(1)
Problem 02 · The Leftover Bug
Consecutive Characters
🔗 LC 1446 - Consecutive Characters
Easy Run length, with the last run handled Amazon · Google
›
Problem

Return the length of the longest run of one repeated character in a string.

s = "abbcccddddeeeeedcba" → 5   |   s = "aaa" → 3
Hints
▶Hint 1 — a nudge

Write it, then trace it on "aaa" and on "abbb". Does your loop record the final run?

▶Hint 2 — the key idea

If you only update the best when a run ends, the last run never ends inside the loop. Update the best on every step instead.

Solution

This is the leftover bug from the lecture, in the wild. A loop that records a run “when the character changes” never records the run that reaches the end of the string — so “aaa” returns 0 or 1 instead of 3. Updating best on every step removes the special case entirely. The general lesson: when a loop processes items in groups, trace an input whose most important group is the last one.

▶Full solution
📐 Pseudocode · Update the Best Every Step 
function maxPower(s):
    best ← 1;  run ← 1
    for i from 1 to length(s) - 1:
        if s[i] = s[i - 1]:
            run ← run + 1
        else:
            run ← 1
        best ← max(best, run)           // every step, so the last run counts too
    return best
TimeO(n)
SpaceO(1)
Problem 03 · Edge Cases Everywhere
Compare Version Numbers
🔗 LC 165 - Compare Version Numbers
Medium Careful parsing Amazon · Google · Microsoft
›
Problem

Compare two version strings like "1.01" and "1.001" part by part. Return −1, 0 or 1.

"1.01" vs "1.001" → 0   |   "1.0" vs "1.0.0" → 0   |   "0.1" vs "1.1" → −1
Hints
▶Hint 1 — a nudge

Before designing anything, list the edge cases the examples hint at. What should "01" compare as? What about versions with different numbers of parts?

▶Hint 2 — the key idea

Leading zeros do not matter ("01" = "1"), and a missing part counts as 0 ("1.0" = "1.0.0"). Compare part by part as numbers, padding the shorter one with zeros.

Solution

The algorithm is trivial; the edge cases are the whole problem. Comparing the strings directly fails on leading zeros; comparing the lists fails on different lengths. Writing the checklist first — leading zeros, different lengths, trailing zeros, equal versions — turns each into a single line of the solution. This is the pattern for every “parse and compare” problem: enumerate the awkward inputs before you write the loop.

▶Full solution
📐 Pseudocode · Part by Part, Missing Parts Are Zero 
function compareVersion(v1, v2):
    a ← split v1 on "."
    b ← split v2 on "."
    for i from 0 to max(length(a), length(b)) - 1:
        x ← number(a[i]) if i < length(a) else 0     // "01" becomes 1; missing is 0
        y ← number(b[i]) if i < length(b) else 0
        if x < y: return -1
        if x > y: return 1
    return 0
TimeO(n + m)
SpaceO(n + m)
Problem 04 · Checklist-Driven
Validate IP Address
🔗 LC 468 - Validate IP Address
Medium Rules as a checklist Amazon · Microsoft · Meta
›
Problem

Decide whether a string is a valid IPv4 address, a valid IPv6 address, or neither.

"172.16.254.1" → "IPv4"   |   "256.256.256.256" → "Neither"
Hints
▶Hint 1 — a nudge

Write down every rule as a separate line before coding. For IPv4, how many can you find? (There are at least five.)

▶Hint 2 — the key idea

IPv4: exactly 4 parts; each part non-empty; digits only; no leading zero unless the part is "0"; value ≤ 255. IPv6: exactly 8 parts of 1–4 hexadecimal digits.

Solution

A problem with no algorithm and a dozen ways to be wrong. The reliable approach is the checklist: turn each rule into one check, and test each check with an input designed to break it (“1.1.1”, “1..1.1”, “01.1.1.1”, “256.1.1.1”, “1.1.1.1.”). Most wrong submissions miss exactly one rule; writing the rules out first is how you do not.

▶Full solution
📐 Pseudocode · One Check per Rule 
function validIPAddress(ip):
    if ip contains "." and isIPv4(ip): return "IPv4"
    if ip contains ":" and isIPv6(ip): return "IPv6"
    return "Neither"

function isIPv4(ip):
    parts ← split ip on "."             // must keep empty parts: "1..1.1" has one
    if length(parts) ≠ 4: return false
    for each p in parts:
        if length(p) = 0 or length(p) > 3: return false
        if p is not all digits: return false
        if length(p) > 1 and p[0] = '0': return false   // no leading zeros
        if number(p) > 255: return false
    return true

function isIPv6(ip):
    parts ← split ip on ":"
    if length(parts) ≠ 8: return false
    for each p in parts:
        if length(p) < 1 or length(p) > 4: return false
        if p has a character outside 0-9, a-f, A-F: return false
    return true
TimeO(n)
SpaceO(n)
