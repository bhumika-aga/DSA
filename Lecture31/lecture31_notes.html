Union-Find (Disjoint Set Union)

“Two arrays and ten lines of code that answer ‘are these two in the same group?’ faster than you can ask.”

📚 Lecture 31 of 45 Phase 3 — Core Patterns ⏱ 4 days 🎯 20 problems 💼 Google · Amazon · Meta · Microsoft
🌍
Why does this topic matter?
Lecture 21 counted connected components with DFS, and Kruskal's algorithm in Lecture 23 quietly borrowed a structure it never explained. This is that structure. DFS answers connectivity for a graph that has stopped changing; Union-Find answers it while edges are still arriving, in near-constant time per query — and it is short enough to write from memory under interview pressure.
By the end of this lecture you can
  • Write find and union with both optimisations, from memory
  • Explain path compression and union by size, and what each one fixes
  • Detect a cycle in an undirected graph with one pass of unions
  • Union things that are not integers — strings, emails, coordinates
  • Choose between Union-Find and DFS for a given problem

👥 A Forest of Groups

Every element starts alone. Each group is a tree, and the group is identified by its root — not by anything meaningful, just “whoever is at the top”. Two elements are in the same group exactly when they reach the same root.

📐 Pseudocode · The Naive Version 
parent ← array where parent[i] = i      // everyone is their own root

function find(x):
    while parent[x] ≠ x: x ← parent[x]   // walk up to the root
    return x

function union(a, b):
    ra ← find(a);  rb ← find(b)
    if ra = rb: return false          // already together
    parent[ra] ← rb                      // hang one root under the other
    return true

// Correct, but a long chain makes find() O(n) — one union at a time can
// build 1 → 2 → 3 → ... → n. The next section fixes exactly that.
union(1,2) union(3,4) union(2,4)   →   1 → 2 → 4    3 → 4     root of everything = 4  |  find(1) walks 1 → 2 → 4

⚡ The Two Optimisations

Both are one line each, and together they take the cost of an operation from O(n) to almost O(1). Write both, always — there is no reason not to.

Path Compression

📐 Pseudocode · find, with Compression 
function find(x):
    if parent[x] ≠ x:
        parent[x] ← find(parent[x])      // point straight at the root on the way back
    return parent[x]

// Iterative version, if recursion depth is a worry:
// root ← x; while parent[root] ≠ root: root ← parent[root]
// while parent[x] ≠ root: parent[x], x ← root, parent[x]

Every node touched by a lookup is re-pointed at the root, so the same walk is never paid for twice. The tree flattens as you use it.

Union by Size (or Rank)

📐 Pseudocode · union, by Size 
size ← array of 1s                       // how many nodes each root owns
components ← n                           // handy free statistic

function union(a, b):
    ra ← find(a);  rb ← find(b)
    if ra = rb: return false

    if size[ra] < size[rb]: swap ra, rb    // always attach the smaller tree
    parent[rb] ← ra
    size[ra] ← size[ra] + size[rb]
    components ← components - 1
    return true
🧠
Why “smaller under larger”? A node's depth only grows when its tree is the one being attached. Attaching the smaller tree means a node's depth can increase only when its group at least doubles in size — so no node is ever deeper than log₂n, even before compression.
📏
The complexity, honestly. With both optimisations, m operations on n elements cost O(m · α(n)), where α is the inverse Ackermann function. For any n you can write down — including the number of atoms in the universe — α(n) ≤ 4. Treat it as constant, and say “amortised near-constant, inverse Ackermann” when asked.

🧩 What It Is Actually For

Three questions, all answered by the same ten lines: how many groups are there, are these two together, and does this new edge close a cycle.

Cycle Detection

📐 Pseudocode · Redundant Edge 
// In an undirected graph, an edge whose endpoints are ALREADY connected
// must close a cycle.
dsu ← new DSU(n)
for (a, b) in edges:
    if not dsu.union(a, b):
        return (a, b)                  // the first edge that connects two connected nodes

// This is also the whole of Kruskal's MST from Lecture 23: sort the edges
// by weight and keep the ones whose union succeeds.

Uniting Things That Are Not Numbers

DSU indexes an array, so anything else needs a mapping first. That mapping is usually the interesting half of the problem.

Problem What gets united The mapping trick
Accounts Merge email addresses map each email to an id; union all emails of one account
Equality Equations lowercase letters 26 slots; union on ==, then check every !=
Most Stones Removed rows and columns union row r with column ~c, so the two spaces never collide
Regions Cut By Slashes quarters of a cell split each cell into 4 triangles, union across the borders
⚠️
Two id spaces, one array. When you union two kinds of thing (rows and columns, people and groups), give each kind its own range of indices — row r at r and column c at n + c, for example. Overlapping the ranges silently merges unrelated things, and the answer comes out too small.

⚖️ Weighted Union-Find

A variation worth knowing: store a value on each edge to the parent, so the structure answers relations rather than just membership. Evaluate Division is the classic — if a/b = 2 and b/c = 3, then a/c = 6.

📐 Pseudocode · DSU with Ratios 
parent ← map from name to name
ratio ← map from name to number          // value of this node ÷ value of its parent

function find(x):                       // returns (root, x ÷ root)
    if parent[x] = x: return (x, 1)
    (root, r) ← find(parent[x])
    parent[x] ← root                     // compress
    ratio[x] ← ratio[x] × r              // and fix the stored ratio to match
    return (root, ratio[x])

function union(a, b, value):             // a ÷ b = value
    (ra, va) ← find(a);  (rb, vb) ← find(b)
    if ra = rb: return
    parent[ra] ← rb
    ratio[ra] ← value × vb ÷ va

// query(a, b): same root → ratio[a] ÷ ratio[b]; different roots → unknown

📊 DSU vs BFS / DFS

Union-Find BFS / DFS
Edges arrive over time ✅ natural — union as they come ❌ rebuild the traversal each time
“Are these two connected?” queries ✅ near O(1) each O(V + E) per query
Shortest path ❌ knows groups, not distances ✅ BFS
Which nodes are in my component needs a second pass to list them ✅ the traversal visits them
Directed graphs ❌ union is symmetric ✅ DFS with colours
Removing edges ❌ — process in reverse instead ✅ rebuild
🧠
When edges disappear, run time backwards. DSU cannot split a group. Problems that remove things — bricks falling, islands sinking — are solved by processing the removals in reverse, so every step becomes an addition. That trick turns several Hard problems into ordinary ones.

⚠️ Complexity & The Classic Bugs

Version find union Notes
Naive parent array O(n) O(n) a chain of unions degenerates to a linked list
Union by size only O(log n) O(log n) depth is bounded by doubling
Path compression only O(log n) amortised O(log n) flattens as it is used
Both O(α(n)) O(α(n)) at most 4 for any real input
Bug Symptom Fix
Comparing parent[a] with parent[b] Elements in one group look separate Always compare find(a) with find(b)
Attaching a node instead of its root The structure stops being a forest Union works on roots only
Overlapping id ranges Unrelated things merge; count too low Offset the second kind of id
Counting components by scanning parent[i] == i mid-run Wrong count if compression has not run Keep a counter, decremented on each successful union
Expecting a group to split Deletions give nonsense Process the operations in reverse
Recursive find on a deep chain Stack overflow before compression kicks in Use the iterative find, or union by size
💡
How to spot it in an interview. “Are these two connected?”, “how many groups?”, “merge these accounts”, “which edge creates a cycle?”, or edges that arrive one at a time. If the question also needs paths or distances, it is BFS instead — and if things get removed, reverse the timeline and use DSU anyway.

💪 In-Lecture Practice Problems

Six problems: the same ten lines each time. What changes is what you decide to union — nodes, letters, emails, rows, or ratios.

Problem 01 · Cycle Detection
Redundant Connection
🔗 LC 684 - Redundant Connection
Medium Union-Find Amazon · Google · Meta
›
Problem

A tree with n nodes had one extra edge added. Return the edge that can be removed so the graph is a tree again; if several work, return the last one in the input.

edges = [[1,2],[1,3],[2,3]] → [2,3]
Hints
▶Hint 1 — a nudge

What is special about an edge whose two endpoints are already connected?

▶Hint 2 — the key idea

Union the edges in order. The first union that fails — both endpoints already share a root — is the redundant edge.

Solution

The canonical first Union-Find problem. Processing edges in order means the first failing union is also the last edge of the cycle in input order, which is exactly what the problem asks for. No graph is ever built: the DSU alone answers it in one pass, at near-constant cost per edge.

▶Full solution
📐 Pseudocode · Union Until One Fails 
function findRedundantConnection(edges):
    n ← length(edges)
    parent ← array 0..n where parent[i] = i
    size ← array of 1s

    for (a, b) in edges:
        if not union(a, b): return (a, b)   // already connected → closes a cycle

function find(x):
    if parent[x] ≠ x: parent[x] ← find(parent[x])
    return parent[x]

function union(a, b):
    ra ← find(a);  rb ← find(b)
    if ra = rb: return false
    if size[ra] < size[rb]: swap ra, rb
    parent[rb] ← ra;  size[ra] ← size[ra] + size[rb]
    return true
TimeO(n α(n))
SpaceO(n)
Problem 02 · Union on Letters
Satisfiability of Equality Equations
🔗 LC 990 - Satisfiability of Equality Equations
Medium Union, Then Verify Google · Amazon · Meta
›
Problem

Given equations like "a==b" and "b!=c" over single lowercase letters, return true if some assignment satisfies all of them.

["a==b","b!=a"] → false   |   ["a==b","b==c","a==c"] → true
Hints
▶Hint 1 — a nudge

Equality is transitive; inequality is not. Which one should build the groups?

▶Hint 2 — the key idea

Two passes. First union every == pair. Then check every != pair: if both sides share a root, the constraints contradict each other.

Solution

The order matters and the reason is worth saying out loud: equality is an equivalence relation, so it can be merged incrementally, while != is only a test. Doing both in one pass would let a later equality invalidate an inequality you already accepted. Only 26 slots are needed, so the DSU is an array of 26.

▶Full solution
📐 Pseudocode · Merge Equalities First 
function equationsPossible(equations):
    dsu ← new DSU(26)

    for eq in equations:                    // pass 1: build the groups
        if eq[1] = '=':
            dsu.union(index(eq[0]), index(eq[3]))

    for eq in equations:                    // pass 2: test the rest
        if eq[1] = '!':
            if dsu.find(index(eq[0])) = dsu.find(index(eq[3])):
                return false
    return true
TimeO(n α(26))
SpaceO(1)
Problem 03 · Union on Strings
Accounts Merge
🔗 LC 721 - Accounts Merge
Medium Map to Ids, Then Union Amazon · Google · Meta
›
Problem

Each account is a name plus a list of emails. Two accounts belong to the same person if they share any email. Merge them and return each person’s sorted email list.

[["John","a@x","b@x"],["John","b@x","c@x"],["Mary","m@x"]] → John: [a@x, b@x, c@x]; Mary: [m@x]
Hints
▶Hint 1 — a nudge

Union-Find works on integers. What has to happen to the emails first?

▶Hint 2 — the key idea

Give every distinct email an id, and remember which name it belongs to. Within one account, union the first email with each of the others; then group the emails by root.

Solution

Two maps carry the problem: email to id, and email to owner name. Uniting each account’s emails to its first email links every account that shares any address, however long the chain. Grouping by root and sorting each list gives the output; the name comes from any member, since all of them agree.

▶Full solution
📐 Pseudocode · Emails to Ids 
function accountsMerge(accounts):
    id ← empty map;  owner ← empty map
    for account in accounts:
        for email in account.emails:
            if email not in id: id[email] ← size(id)
            owner[email] ← account.name

    dsu ← new DSU(size(id))
    for account in accounts:
        first ← id[account.emails[0]]
        for email in account.emails:
            dsu.union(first, id[email])          // one account = one group

    groups ← empty map                            // root → emails
    for email in id:
        groups[dsu.find(id[email])].append(email)

    return for each group: [owner of any member] + sorted(emails)
TimeO(n log n)
SpaceO(n)
Problem 04 · Two Id Spaces
Most Stones Removed with Same Row or Column
🔗 LC 947 - Most Stones Removed with Same Row or Column
Medium Union Rows with Columns Google · Amazon · Meta
›
Problem

Stones sit on a grid. A stone may be removed if it shares a row or column with another remaining stone. Return the largest number of stones that can be removed.

stones = [[0,0],[0,1],[1,0],[1,2],[2,1],[2,2]] → 5
Hints
▶Hint 1 — a nudge

Think about one connected group of stones. How many of them can you remove?

▶Hint 2 — the key idea

All but one — so the answer is stones − components. Build the components by uniting each stone’s row with its column.

Solution

Two ideas. The counting argument (a group of size k loses k−1 stones, because removals can always be ordered to leave one behind) turns the problem into counting components. Then the modelling trick: union row r with column c, keeping the two kinds of id in separate ranges — 10000 + c, or ~c — so a row never collides with a column.

▶Full solution
📐 Pseudocode · Rows and Columns as Nodes 
function removeStones(stones):
    dsu ← new DSU over a map of ids            // ids created on demand

    for (r, c) in stones:
        dsu.union(rowId(r), colId(c))          // colId offset so the spaces never overlap

    roots ← empty set
    for (r, c) in stones:
        roots.add(dsu.find(rowId(r)))          // one root per component of stones

    return length(stones) - size(roots)

// 6 stones forming 1 component → 6 − 1 = 5 removable ✓
TimeO(n α(n))
SpaceO(n)
Problem 05 · Weighted DSU
Evaluate Division
🔗 LC 399 - Evaluate Division
Medium Union-Find with Ratios Google · Amazon · Meta
›
Problem

Given equations like a / b = 2.0, answer queries such as a / c. Return −1 when the answer cannot be determined.

equations a/b = 2, b/c = 3 · queries a/c → 6.0, c/a → 0.333, x/x → -1.0
Hints
▶Hint 1 — a nudge

Variables in the same group have a fixed ratio to each other. Where can that ratio be stored?

▶Hint 2 — the key idea

On the edge to the parent: ratio[x] is the value of x divided by the value of its root. Multiply the ratios as find compresses the path.

Solution

This is Union-Find carrying data. Each node stores its value relative to the root; when path compression re-points a node at the root, the stored ratio must be multiplied by its old parent’s ratio to stay correct. A query on two variables with the same root is a division of their stored ratios, and different roots (or an unknown variable) means −1. Build with a DFS over an explicit graph if the weighted version feels risky under pressure.

▶Full solution
📐 Pseudocode · Ratios on the Edges 
parent ← map name → name;  ratio ← map name → number

function find(x):                      // returns (root, x ÷ root)
    if parent[x] = x: return (x, 1)
    (root, r) ← find(parent[x])
    parent[x] ← root
    ratio[x] ← ratio[x] × r             // keep the stored ratio consistent
    return (root, ratio[x])

function union(a, b, value):            // a ÷ b = value
    (ra, va) ← find(a);  (rb, vb) ← find(b)
    if ra = rb: return
    parent[ra] ← rb
    ratio[ra] ← value × vb ÷ va

function query(a, b):
    if a not in parent or b not in parent: return -1
    (ra, va) ← find(a);  (rb, vb) ← find(b)
    if ra ≠ rb: return -1
    return va ÷ vb
TimeO((n + q) α(n))
SpaceO(n)
Problem 06 · Offline Queries
Checking Existence of Edge Length Limited Paths
🔗 LC 1697 - Checking Existence of Edge Length Limited Paths
Hard Sort Edges + Sort Queries Google · Amazon
›
Problem

For each query [p, q, limit], answer whether a path exists between p and q using only edges strictly shorter than limit.

n = 3, edges = [[0,1,2],[1,2,4],[2,0,8]], queries = [[0,1,2],[0,2,5]] → [false, true]
Hints
▶Hint 1 — a nudge

Answering each query on its own means rebuilding the graph every time. What if the queries did not have to be answered in order?

▶Hint 2 — the key idea

Sort the edges by weight and the queries by limit. Sweep both: add every edge below the current limit, then answer the query with a single connectivity check.

Solution

The offline trick: nothing says you must answer queries in the order given. Keep each query’s original index, sort everything by weight, and let the DSU grow monotonically as the limit rises — each edge is added once across all queries. Union-Find is the right structure precisely because edges only ever get added, never removed.

▶Full solution
📐 Pseudocode · Sweep Both Sorted Lists 
function distanceLimitedPathsExist(n, edges, queries):
    sort edges by weight ascending
    tagged ← queries, each remembering its original index
    sort tagged by limit ascending

    dsu ← new DSU(n)
    answer ← array of length(queries)
    i ← 0

    for (p, q, limit, index) in tagged:
        while i < length(edges) and edges[i].weight < limit:
            dsu.union(edges[i].a, edges[i].b)      // every edge added once, ever
            i ← i + 1
        answer[index] ← (dsu.find(p) = dsu.find(q))

    return answer
TimeO(E log E + Q log Q)
SpaceO(n + Q)
