Mock Interviews & System Thinking

“The interview is not a test of what you know. It is a test of what you can show, out loud, in forty-five minutes.”

🌍
Why does this topic matter?
Strong candidates fail interviews every day with correct code, because the interviewer could not follow their thinking, because an empty input crashed it, or because they froze when asked how the design would scale. The final lecture puts everything together under realistic conditions: complete mock rounds with a fixed framework, deliberate edge-case practice, the basics of system design that entry-level roles expect, and the behavioural stories every company asks for.
By the end of this lecture you can
  • Run a coding round end to end with the UMPIRE framework, talking throughout
  • Score a mock interview and turn the score into practice
  • Check the standard edge cases for each kind of input
  • Sketch a small system: requirements, numbers, API, storage, cache, load balancer
  • Tell a clear STAR story about your own work
🧠
The picture to keep in your head: a driving test. The examiner already knows you can make the car move. They are watching whether you check your mirrors, signal before you turn, and stay calm when a cyclist appears. A coding interview is the same: reaching the right answer is the minimum. The marks come from the visible habits — clarifying the question (checking the mirrors), explaining your plan (signalling), and testing edge cases before the interviewer finds them (the cyclist).

⚖️ The UMPIRE Framework

UMPIRE is a checklist for a coding round. Its value is that you never have to decide what to do next: you are always in exactly one stage, and the interviewer can always tell which.

Stage Lecture 2 step Say something like…
Understand 1. Understand “So I return true if the path ever visits a point twice? Can the string be empty?”
Match 2. Size it up · 5. Match a pattern “n is up to 10⁴, so O(n) or O(n log n). Seen before? That is a HashSet.”
Plan 3. Brute force · 4. Find the waste “Brute force compares every pair of points, O(n²). A set of visited points makes it O(n). Shall I code that?”
Implement — “I store points as strings "x,y" so they hash correctly.”
Review 6. Test on paper “Tracing "NES": (0,0), (0,1), (1,1), (1,0) — no repeats, false. Now "NESW": back to (0,0), true.”
Evaluate — “O(n) time and space. With a huge path I could encode the point as one long instead of a string.”

A sample round, compressed

Interviewer: Given moves N, S, E, W from (0,0), does the path cross itself? You (U): Cross means visiting any point a second time, including the start? Interviewer: Yes. You (U): Up to 10⁴ moves, all valid letters? ... Great. Example: "NESW" is true. You (M): "Visited before" in O(1) is a HashSet question. You (P): Brute force keeps a list and scans it: O(n²). A set of points is O(n). I'll add (0,0) first, then each new point; seeing one twice returns true. Interviewer: Sounds good. You (I): [writes code, saying why the origin goes in first] You (R): Trace "NES" → false. "NESW" → true at the last step. Empty → false. You (E): O(n) time, O(n) space. Could pack x and y into one long to avoid strings.

🎭 Running a Mock Interview

A mock only helps if it is realistic. Find a partner (a friend, a study group, or a peer-practice site), take turns as interviewer, and use a shared editor without autocomplete. If you practise alone, record yourself talking and watch it back — uncomfortable and very effective. Afterwards the interviewer scores each area from 1 to 4:

Area 1 — weak 4 — strong
Communication Long silences; code appears without explanation Thinks aloud; checks in before big decisions
Problem solving Jumps to code; no brute force; stuck without a way out Brute force, then a justified improvement
Coding Messy, repeated logic; unclear names Clean, well-named, correct on the first read
Testing Interviewer finds the bugs Traces cases and fixes bugs unprompted

Log the scores next to the problem in your Lecture 44 log. Your lowest area, not your lowest pattern, is what to fix in the last week.

🧱 Edge-Case Drills

Interviewers keep a short list of inputs that break most solutions. Check yours against the same list before you say “done”.

Input Always try
Arrays Empty; one element; all equal; already sorted and reverse sorted; negatives; duplicates
Numbers 0; −1; the largest int (overflow); division by zero; negative modulo
Strings Empty; one character; all the same character; spaces at the ends; upper and lower case
Trees Null root; one node; a single long chain; duplicate values
Graphs & grids Disconnected parts; cycles; self-loops; a 1 × n grid; start equals target
Intervals Touching ends [1,2],[2,3]; one inside another; unsorted input
Geometry Vertical lines; identical points; slopes that differ only after rounding

🏗️ System Design Foundations

Entry-level roles increasingly include one short design discussion. Nobody expects you to design a whole platform; they expect a calm, ordered conversation. Follow four steps: requirements (what must it do, for how many users), rough numbers (requests per second, storage), a high-level diagram, then one deeper dive the interviewer chooses.

The building blocks

Block In one sentence The trade-off to mention
REST API Endpoints such as POST /urls and GET /{code} that clients call over HTTP Keep them simple; version them (/v1/)
SQL database Tables with fixed columns, joins and transactions Strong consistency; harder to spread across machines
NoSQL (key-value) Look up a value by its key, spread over many machines Scales easily; fewer query features
Cache A fast in-memory copy of hot data (an LRU cache from Lecture 16, run as a service) Much faster reads; data may be stale
Load balancer Spreads incoming requests over several identical servers Servers must be stateless, so any one can handle any request
Replication & sharding Copies of the data for reads and safety; data split by key across machines for size More machines, more ways to fail

Worked example: a URL shortener

Requirements. Turn a long URL into a short code; redirect anyone who visits the code. Reads (visits) far outnumber writes. Numbers. Say 100 million new links a month — about 40 per second — and a hundred times as many visits. Seven base-62 characters give 62⁷ ≈ 3.5 × 10¹² codes, far more than enough.

client ──▶ load balancer ──▶ web server ─┬─▶ cache (code → URL, LRU) (stateless) │ miss ↓ └─▶ database (code → URL, sharded by code) POST /urls {longUrl} → 201 {shortUrl} GET /{code} → 301 redirect to longUrl
📐 Pseudocode · Id to Short Code (Base 62) 
ALPHABET ← "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ"

function toCode(id):                          // id from a counter, unique
    code ← ""
    repeat:
        code ← ALPHABET[id mod 62] + code
        id ← id / 62                              // integer division
    until id = 0
    return code
// Many servers? Give each a block of ids (1–1000, 1001–2000, ...) so codes never clash.

Deeper dives an interviewer might pick: how to hand out unique ids across servers (blocks of ids, as above), what to do when a popular link overloads one cache node (replicate hot keys), and whether the same long URL should always get the same code (store URL → code too, exactly as in the practice problem below).

🗣️ Behavioural Rounds

Every company asks about your past: a conflict, a failure, something you owned. Answer with STAR, in about two minutes:

Part Share of the answer Contents
Situation ~15% Where and when, in two sentences
Task ~10% What you were responsible for
Action ~60% What you did, step by step, and why — say “I”, not “we”
Result ~15% What changed, with a number if possible, and what you learnt

Prepare a story bank of four to six stories from projects, internships, university or volunteering: a technical challenge, a disagreement, a mistake, a tight deadline, helping someone, and learning something fast. Most questions can be answered by one of them. Amazon maps every question to its published Leadership Principles, so read those before an Amazon loop.

💪 In-Lecture Practice Problems

Five rounds, each testing one interview skill: a design discussion, a clean first solution, edge cases, a careful simulation, and improving a brute force step by step.

Problem 01 · Code That Leads to Design
Encode and Decode TinyURL
🔗 LC 535 - Encode and Decode TinyURL
Medium Counter + base 62 + two maps Amazon · Google · Uber
›
Problem

Design encode(longUrl), which returns a short URL, and decode(shortUrl), which returns the original. Any scheme is allowed as long as decode(encode(url)) = url.

encode("https://leetcode.com/problems/design-tinyurl") → "http://tinyurl.com/1" decode("http://tinyurl.com/1") → "https://leetcode.com/problems/design-tinyurl"
Hints
▶Hint 1 — a nudge

What is the simplest way to guarantee that two different URLs never get the same short code?

▶Hint 2 — the key idea

A counter: every new URL gets the next integer, written in base 62 so that it stays short. A map code → URL decodes; a map URL → code avoids storing the same URL twice.

Solution

The coding part is short, so this round is really about the conversation. Clarify first: must the same URL always get the same code? Should codes be hard to guess? A counter gives unique codes with no collisions to handle, and base 62 keeps them to a few characters. Random codes are the alternative: harder to guess, but you must check for collisions. After coding, expect “how would this work for millions of users?” — which is the URL shortener design in this lecture: a database instead of the maps, blocks of ids per server instead of one counter, and a cache in front for popular links.

▶Full solution
📐 Pseudocode · Counter, Base 62, Two Maps 
urlOf ← code → long URL;  codeOf ← long URL → code;  nextId ← 1

function encode(longUrl):
    if longUrl not in codeOf:
        code ← toCode(nextId);  nextId ← nextId + 1   // base 62, from the lecture
        urlOf[code] ← longUrl;  codeOf[longUrl] ← code
    return "http://tinyurl.com/" + codeOf[longUrl]

function decode(shortUrl):
    code ← the part of shortUrl after the last "/"
    return urlOf[code]
TimeO(L) per call
SpaceO(total URL length)
Problem 02 · A Clean First Solution
Count Good Nodes in Binary Tree
🔗 LC 1448 - Count Good Nodes in Binary Tree
Medium DFS carrying the path maximum Microsoft · Amazon
›
Problem

A node is good if no node on the path from the root to it has a greater value. Count the good nodes.

root = [3,1,4,3,null,1,5] → 4 (3, 4, the lower 3, and 5)
Hints
▶Hint 1 — a nudge

To judge a node you do not need the whole path — only one number from it. Which?

▶Hint 2 — the key idea

The largest value on the path so far. Pass it down as a parameter; a node is good if its value is at least that.

Solution

This round is about delivery, not difficulty. Understand: “no greater value” means equal values count as good — ask, and write it down. Match: a property of the path from the root is information passed down a DFS (Lecture 18). Plan: the brute force stores the whole path and scans it at every node; only its maximum matters, so carry that instead. Review with the example, then the edge cases: a single node (1), all equal values (every node is good), and a chain that only decreases (only the root). Evaluate: O(n) time and O(h) stack — mention that a very deep tree could need an iterative version.

▶Full solution
📐 Pseudocode · Pass the Maximum Down 
function goodNodes(root):
    return dfs(root, -infinity)

function dfs(node, maxSoFar):
    if node = null: return 0
    good ← 1 if node.val ≥ maxSoFar else 0       // equal counts as good
    m ← max(maxSoFar, node.val)
    return good + dfs(node.left, m) + dfs(node.right, m)
TimeO(n)
SpaceO(h)
Problem 03 · Edge Cases Decide It
Max Points on a Line
🔗 LC 149 - Max Points on a Line
Hard Reduced (dx, dy) per anchor point Google · Apple
›
Problem

Given distinct integer points on a plane, return the largest number of them that lie on one straight line.

[[1,1],[2,2],[3,3]] → 3 [[1,1],[3,2],[5,3],[4,1],[2,3],[1,4]] → 4
Hints
▶Hint 1 — a nudge

Fix one point. Every other point defines a line through it. When do two of those lines coincide?

▶Hint 2 — the key idea

When they have the same direction. Store the direction as (dx, dy) divided by gcd(dx, dy) with a fixed sign — never as a floating-point slope — and count in a map.

Solution

The idea is short; the round is won or lost on edge cases, so list them before coding. Fix an anchor point i and count the points j > i by direction: points sharing a direction from i lie on one line through i. The traps: (1) a vertical line has dx = 0, where dy/dx is undefined; (2) floating-point slopes can make different directions compare equal, or equal ones differ; (3) (1, 2) and (−1, −2) are the same direction. A reduced integer pair fixes all three: divide by the gcd, then make dx positive, or make dy positive when dx is 0. Answer = 1 (the anchor) + the largest count. With one or two points the answer is simply n.

▶Full solution
📐 Pseudocode · Count Directions From Each Anchor 
function maxPoints(points):
    n ← length(points)
    if n ≤ 2: return n
    best ← 0
    for i from 0 to n - 1:
        count ← empty map                         // direction → points
        for j from i + 1 to n - 1:
            dx ← xj - xi;  dy ← yj - yi
            g ← gcd(|dx|, |dy|);  dx ← dx / g;  dy ← dy / g
            if dx < 0 or (dx = 0 and dy < 0):
                dx ← -dx;  dy ← -dy               // one sign per direction
            count[(dx, dy)] ← count[(dx, dy)] + 1
        best ← max(best, 1 + largest value in count)
    return best
TimeO(n² log C)
SpaceO(n)
Problem 04 · A Careful Simulation
Robot Collisions
🔗 LC 2751 - Robot Collisions
Hard Sort by position + stack Amazon
›
Problem

Robots stand at distinct positions on a line, each with a health and a direction (L or R), all moving at the same speed. When two meet, the one with lower health is removed and the other loses 1 health; equal health removes both. Return the healths of the survivors in the order the robots were given.

positions = [3,5,2,6], healths = [10,10,15,12], directions = "RLRL" → [14] positions = [1,2,5,6], healths = [10,10,11,11], directions = "RLRL" → []
Hints
▶Hint 1 — a nudge

Sort by position. Which pairs can ever meet — and in what order do the collisions happen for a robot moving left?

▶Hint 2 — the key idea

Only an R to the left of an L collide, nearest first — the same stack as Asteroid Collision in Lecture 27. Keep right-movers on a stack; each left-mover fights the top until one of them is gone.

Solution

Say the brute force first: simulate time steps until nothing moves towards anything — slow, but it pins down the rules. Then notice that after sorting by position, two robots meet only when an R is left of an L, and a left-mover meets the nearest surviving right-mover first. So walk left to right with a stack of right-movers. For a left-mover, compare with the top: the weaker is removed, the stronger loses 1 health and, if it is the left-mover, keeps fighting the next one. The careful parts, which are what this round tests: keep the original indices so the answer can be returned in input order, and handle the equal-health case, which removes both.

▶Full solution
📐 Pseudocode · Right-Movers Wait on a Stack 
function survivedRobotsHealths(pos, h, dir):
    order ← indices 0..n-1 sorted by pos           // h is a copy we may change
    stack ← empty                                 // indices of right-movers
    for i in order:
        if dir[i] = 'R': stack.push(i);  continue
        while stack is not empty and h[i] > 0:
            j ← stack.top
            if h[j] < h[i]:  h[j] ← 0;  stack.pop();  h[i] ← h[i] - 1
            else if h[j] > h[i]:  h[j] ← h[j] - 1;  h[i] ← 0
            else:  h[j] ← 0;  h[i] ← 0;  stack.pop()      // equal: both go
    return [h[i] for i from 0 to n - 1 if h[i] > 0]   // original order
TimeO(n log n)
SpaceO(n)
Problem 05 · Brute Force to Optimal, Out Loud
Reaching Points
🔗 LC 780 - Reaching Points
Hard Work backwards with modulo Google · Amazon
›
Problem

From a point (x, y) you may move to (x + y, y) or (x, x + y). Can you get from (sx, sy) to (tx, ty)? All values are positive and up to 10⁹.

(1,1) → (3,5): true (1,1) → (1,2) → (3,2) → (3,5) (1,1) → (2,2): false (1,1) → (1,1): true
Hints
▶Hint 1 — a nudge

Going forwards there are two choices at every step. How many choices are there going backwards from (tx, ty)?

▶Hint 2 — the key idea

One: the larger coordinate must have been made by adding the smaller. Subtracting repeatedly is slow for (10⁹, 1); replace it with modulo, the way Euclid’s gcd does.

Solution

This round is judged on the climb, so narrate each step. Step 1: search forwards (DFS or BFS) — correct but exponential. Step 2: go backwards; since values are positive, the larger of tx and ty was the one just increased, so the previous point is unique and the search becomes a single path. Step 3: that path can have 10⁹ steps, e.g. (10⁹, 1), because the same subtraction repeats; one modulo does all of them, making it O(log). The edge case is stopping in time: once tx reaches sx, you can only have been adding sx to y, so check whether ty − sy is a positive multiple of sx (and symmetrically for y). Test (1,1)→(1,1) and (1,1)→(2,2) out loud.

▶Full solution
📐 Pseudocode · Backwards, Many Steps per Modulo 
function reachingPoints(sx, sy, tx, ty):
    while tx > sx and ty > sy and tx ≠ ty:
        if tx > ty: tx ← tx mod ty                // undo many (x + y, y) moves at once
        else:       ty ← ty mod tx
    if tx = sx and ty = sy: return true
    if tx = sx: return ty > sy and (ty - sy) mod tx = 0   // only y grew, in steps of sx
    if ty = sy: return tx > sx and (tx - sx) mod ty = 0
    return false
TimeO(log max(tx, ty))
SpaceO(1)
