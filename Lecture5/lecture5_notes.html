Java Memory Management & Collections

"You rent memory from the JVM. Understand the landlord — or face eviction (OutOfMemoryError)."

📚 Lecture 5 of 45Phase 1 — Foundations⏱ 4 days🎯 35 problemsGoogle · Oracle · Goldman
🌍
Why does this topic matter?
Memory management is invisible — until it crashes your program. Understanding where a variable lives (stack vs heap) explains every "surprising" Java behaviour you will ever encounter: why primitives are copied but objects are shared, why passing an object to a method can change it while passing an int never can, and why a missing null check causes a NullPointerException. This knowledge also directly impacts how you reason about the space complexity of your algorithms.
By the end of this lecture you can
  • Master the difference between Stack (static) and Heap (dynamic) memory
  • Understand how Java handles primitive vs. object references
  • Grasp Garbage Collection as a background process and why it matters
  • Identify and prevent common memory leaks in Java applications
🧠
The picture to keep in your head: A desk and a warehouse. The stack is your desk: the papers for the task you are doing right now, stacked in order, cleared away the moment the task finishes. The heap is a warehouse: things that need to outlive one task go there, and you keep a ticket (a reference) to find them. Every so often a cleaner — the garbage collector — walks the aisles and throws out any box nobody holds a ticket for.

📖 Before We Start — The Big Picture

Every Java program runs inside the Java Virtual Machine (JVM) — a software layer that sits between your code and the real hardware. The JVM manages all memory on your behalf, splitting it into distinct regions, each with a specific job.

Stack = a small, fast notepad on your desk. Each method call writes its local variables here. When the method returns, the page is torn off and thrown away. Heap = a large warehouse. Every object you create with new is stored here and stays until nobody is referencing it anymore. The Garbage Collector is the warehouse cleaner — it periodically sweeps away objects nobody is using.

🔗
How it connects: Lecture 4 taught you what types exist. This lecture explains where they live in memory. Lecture 6 (OOP) builds on this — every object you create goes onto the heap, and understanding that is why == compares addresses, not values.

☕ Java · Memory Layout
int x = 42;               // x lives on STACK (primitive)
String s = "hi";          // s (ref) on STACK → String object on HEAP
int[] arr = {1,2,3};    // arr (ref) on STACK → int[3] on HEAP

// Reference copy ≠ object copy!
int[] a = {1,2,3};
int[] b = a;           // b points to SAME array
b[0] = 99;
System.out.println(a[0]); // → 99! Same heap array

// Deep copy needed for independence:
int[] c = Arrays.copyOf(a, a.length);

🔡 String Pool & Interning

☕ Java · String Pool
String a = "hello";           // Pool["hello"] → 0xAAA
String b = "hello";           // same Pool object 0xAAA
System.out.println(a == b);      // → true

String c = new String("hello");// bypasses pool → new heap obj
System.out.println(a == c);      // → false (different refs)
System.out.println(a.equals(c)); // → true  (same content)

String d = c.intern();          // force into pool
System.out.println(a == d);      // → true

// RULE: ALWAYS use .equals() for string comparison. Never ==.

🗑 Garbage Collection

💡
Generational Hypothesis: Most objects die young. GC exploits this by collecting the small Young Generation frequently (Minor GC — fast) and the Old Generation rarely (Major GC — slow Stop-the-World).

HashMap Internals

🔍
Bucket index = hash(key) & (n-1). Collisions form a linked list per bucket. When chain length ≥ 8 it treeifies to a Red-Black Tree (O(log n) worst case). Doubles capacity when size > capacity × 0.75.

⚠️ Complexity & Classic Bugs

The costs worth quoting in an interview first, then the mistakes that most often break code that looks correct. Every row in the second table is a bug someone has shipped.

Operation Cost Note
Create an object O(size) now, plus later garbage collection Allocation is cheap; collection is not free
Call a method O(1) stack frame Freed automatically on return
Recursion d levels deep O(d) stack space Default limit is a few thousand frames
Reuse a string literal Free — it comes from the pool Same object every time
new String("x") A new heap object every time Rarely what you want
Bug Symptom Fix
Recursion too deep StackOverflowError around 10⁴ levels Rewrite as a loop, or use an explicit stack
Unbounded static collections Memory grows until the program dies Remove entries you no longer need; cap caches
Holding references you no longer use The garbage collector cannot free them Keep variables in the narrowest scope
Expecting a method to change the caller's variable Reassigning a parameter has no effect outside Return the new value instead
Mutating an object that was passed in The caller sees surprising changes Copy it first if the caller should not be affected
Boxing in hot loops Slow code and heavy garbage collection Prefer int[] over List<Integer> in tight loops
Relying on garbage collection to close things Files or connections stay open Close resources explicitly with try-with-resources

💪 In-Lecture Practice Problems

P01 · HashMap Grouping
Find Duplicate File in System
🔗 LC 609 - Find Duplicate File in System
Medium Map to a List Amazon · Google · Dropbox
›
Problem

Each input string is a directory followed by files written as name(content). Return every group of file paths whose contents are identical, keeping only groups with at least two files.

["root/a 1.txt(abcd) 2.txt(efgh)", "root/c 3.txt(abcd)"] → [["root/a/1.txt", "root/c/3.txt"]]
Hints
▶Hint 1 — a nudge

“Same content” is a grouping key. Which collection maps one key to many values?

▶Hint 2 — the key idea

Split each line on spaces. For every file, cut it at ( into a name and a content, and append dir + "/" + name to map.computeIfAbsent(content, k -> new ArrayList<>()).

Solution

A HashMap<String, List<String>> keyed by file content does all the work. computeIfAbsent allocates each list on the heap only when it is first needed, and the map stores a reference to it — the map itself never holds the strings. Because String overrides equals and hashCode, two identical contents built separately still land in the same bucket.

▶Full solution
☕ Java · Group by Content 
List<List<String>> findDuplicate(String[] paths) {
    Map<String, List<String>> byContent = new HashMap<>();
    for (String line : paths) {
        String[] parts = line.split(" ");
        String dir = parts[0];
        for (int i = 1; i < parts.length; i++) {
            int open = parts[i].indexOf('(');
            String name = parts[i].substring(0, open);
            String content = parts[i].substring(open + 1, parts[i].length() - 1);
            byContent.computeIfAbsent(content, k -> new ArrayList<>())
                     .add(dir + "/" + name);
        }
    }
    List<List<String>> result = new ArrayList<>();
    for (List<String> group : byContent.values())
        if (group.size() > 1) result.add(group);
    return result;
}
TimeO(total characters)
SpaceO(total characters)
P02 · HashMap + Comparator
Sort Array by Increasing Frequency
🔗 LC 1636 - Sort Array by Increasing Frequency
Easy Count Then Sort Amazon · Google · eBay
›
Problem

Sort nums by increasing frequency. When two values appear equally often, the larger value comes first.

nums = [2, 3, 1, 3, 2] → [1, 3, 3, 2, 2]
Hints
▶Hint 1 — a nudge

You cannot sort by frequency before you know the frequencies.

▶Hint 2 — the key idea

Count with a HashMap, copy the values into an Integer[], and sort with a comparator: frequency ascending, then value descending.

Solution

Two collection lessons meet here. The map gives O(1) frequency lookups from inside the comparator. The boxing is not optional: Arrays.sort(int[]) has no comparator overload, so you need Integer[] — an array of references to heap objects, which costs memory but allows a custom order.

▶Full solution
☕ Java · Count, Box, Sort 
int[] frequencySort(int[] nums) {
    Map<Integer, Integer> freq = new HashMap<>();
    for (int x : nums) freq.merge(x, 1, Integer::sum);

    Integer[] boxed = new Integer[nums.length];
    for (int i = 0; i < nums.length; i++) boxed[i] = nums[i];

    Arrays.sort(boxed, (a, b) -> {
        int fa = freq.get(a), fb = freq.get(b);
        if (fa != fb) return fa - fb;   // rarer values first
        return b - a;                   // ties: larger value first
    });

    for (int i = 0; i < nums.length; i++) nums[i] = boxed[i];
    return nums;
}
TimeO(n log n)
SpaceO(n)
P03 · HashMap Design
Design Authentication Manager
🔗 LC 1797 - Design Authentication Manager
Medium Map with Expiry Twitter · Amazon
›
Problem

Design an authentication manager where each token lives timeToLive seconds. Support generate(id, t), renew(id, t) (only if the token has not expired) and countUnexpiredTokens(t).

ttl = 5: generate("a", 2) expires at 7 · renew("a", 6) expires at 11 · count(12) → 0
Hints
▶Hint 1 — a nudge

What is the smallest piece of state you must remember per token?

▶Hint 2 — the key idea

Store tokenId → expiryTime in a HashMap. A token is alive at time t when expiry > t. Renewing is a put guarded by that check.

Solution

One HashMap<String, Integer> is the whole design. The interesting part is memory: expired tokens stay in the map forever unless you remove them, which is exactly the leak this lecture warns about with long-lived maps. Pruning with the iterator's remove() during the count keeps the map the size of the live tokens.

▶Full solution
☕ Java · Map of Expiry Times 
class AuthenticationManager {
    private final int ttl;
    private final Map<String, Integer> expiry = new HashMap<>();

    AuthenticationManager(int timeToLive) { this.ttl = timeToLive; }

    void generate(String tokenId, int currentTime) {
        expiry.put(tokenId, currentTime + ttl);
    }

    void renew(String tokenId, int currentTime) {
        Integer exp = expiry.get(tokenId);
        if (exp != null && exp > currentTime) expiry.put(tokenId, currentTime + ttl);
    }

    int countUnexpiredTokens(int currentTime) {
        Iterator<Integer> it = expiry.values().iterator();
        int alive = 0;
        while (it.hasNext()) {
            if (it.next() > currentTime) alive++;
            else it.remove();          // prune, or the map leaks
        }
        return alive;
    }
}
TimeO(1) generate and renew
SpaceO(live tokens)
P04 · HashMap Lookup
Contains Duplicate II
🔗 LC 219 - Contains Duplicate II
Easy Last Index Seen Amazon · Google · Meta
›
Problem

Return true when two distinct indices i and j hold the same value and |i - j| ≤ k.

nums = [1, 2, 3, 1], k = 3 → true  |  nums = [1, 2, 3, 1, 2, 3], k = 2 → false
Hints
▶Hint 1 — a nudge

For a repeated value, which earlier occurrence is the only one worth remembering?

▶Hint 2 — the key idea

Keep value → last index. At index i, if the value is in the map and i - map.get(v) ≤ k, return true; then overwrite the stored index with i.

Solution

The closest earlier occurrence is always the most recent one, so a map of last indices suffices. Watch the boxing: map.get(v) hands back an Integer object, so comparing two of them with == would compare references. Subtracting unboxes them, which is what you want.

▶Full solution
☕ Java · Last-Seen Index 
boolean containsNearbyDuplicate(int[] nums, int k) {
    Map<Integer, Integer> lastIndex = new HashMap<>();
    for (int i = 0; i < nums.length; i++) {
        Integer prev = lastIndex.get(nums[i]);
        if (prev != null && i - prev <= k) return true;
        lastIndex.put(nums[i], i);      // keep only the most recent index
    }
    return false;
}

// [1,2,3,1], k = 3: at i=3 prev=0, 3 - 0 <= 3 -> true
TimeO(n)
SpaceO(n)
P05 · Deque as a Stack
Final Prices With a Special Discount in a Shop
🔗 LC 1475 - Final Prices With a Special Discount in a Shop
Easy Stack of Indices Amazon · Google
›
Problem

prices[i] is an item's price. It gets a discount equal to prices[j], where j is the first index after i with prices[j] ≤ prices[i]. Return the final price of every item.

prices = [8, 4, 6, 2, 3] → [4, 2, 4, 2, 3]
Hints
▶Hint 1 — a nudge

Scanning forward from each item is O(n²). Which items are still waiting for their discount?

▶Hint 2 — the key idea

Push indices onto an ArrayDeque. When the current price is at most the price at the top index, that top item has found its discount: pop and apply. Then push the current index.

Solution

Use ArrayDeque rather than the legacy Stack class — it is not synchronized and is backed by a resizable array, so it is both faster and the modern idiom. Each index is pushed once and popped at most once, which makes the whole pass O(n). This “stack of items still waiting” is the monotonic stack you meet properly in Lecture 15.

▶Full solution
☕ Java · Waiting Stack 
int[] finalPrices(int[] prices) {
    int[] ans = prices.clone();
    Deque<Integer> waiting = new ArrayDeque<>();   // indices with no discount yet
    for (int i = 0; i < prices.length; i++) {
        while (!waiting.isEmpty() && prices[waiting.peek()] >= prices[i]) {
            int j = waiting.pop();
            ans[j] = prices[j] - prices[i];        // first price <= it, to its right
        }
        waiting.push(i);
    }
    return ans;
}
TimeO(n)
SpaceO(n)
P06 · Deque as a Queue
Number of Students Unable to Eat Lunch
🔗 LC 1700 - Number of Students Unable to Eat Lunch
Easy Queue Simulation Amazon · Google
›
Problem

Students queue for sandwiches stacked on a counter. The student at the front takes the top sandwich if it matches their preference (0 or 1), otherwise they move to the back of the queue. Return how many students never eat.

students = [1, 1, 1, 0, 0, 1], sandwiches = [1, 0, 0, 0, 1, 1] → 3
Hints
▶Hint 1 — a nudge

Simulate it with a real queue first. What condition means the line can never move again?

▶Hint 2 — the key idea

The rotation only stops when nobody left in the queue wants the top sandwich. So count how many students prefer 0 and how many prefer 1, then walk the sandwich stack until one has no taker.

Solution

Model it first with ArrayDeque as a FIFO queue (offer at the tail, poll at the head) to see the process. Then notice that the order of the students never matters — only the two counts do. The counting version answers in O(n) with O(1) memory, and it cannot loop forever.

▶Full solution
☕ Java · Count Preferences 
int countStudents(int[] students, int[] sandwiches) {
    int[] want = new int[2];
    for (int s : students) want[s]++;

    for (int i = 0; i < sandwiches.length; i++) {
        int top = sandwiches[i];
        if (want[top] == 0) return sandwiches.length - i;  // nobody takes it
        want[top]--;
    }
    return 0;
}

// Queue version, for comparison:
// Deque<Integer> q = new ArrayDeque<>();
// rotate with q.offer(q.poll()) until a whole lap matches nothing.
TimeO(n)
SpaceO(1)
P07 · HashSet
Find the Difference of Two Arrays
🔗 LC 2215 - Find the Difference of Two Arrays
Easy Set Difference Amazon · Microsoft
›
Problem

Given two arrays, return two lists: the distinct values of nums1 that are not in nums2, and the distinct values of nums2 that are not in nums1.

nums1 = [1, 2, 3], nums2 = [2, 4, 6] → [[1, 3], [4, 6]]
Hints
▶Hint 1 — a nudge

Searching an array for membership is O(n) each time. Which collection answers that in O(1)?

▶Hint 2 — the key idea

Put each array into a HashSet<Integer>. Then collect the values of the first set where !second.contains(x), and the other way round.

Solution

Sets drop duplicates for free and answer contains in O(1) on average, which is the whole point of hashing. removeAll on a copy also works, but be careful: it may iterate the argument collection, so its cost depends on which side you pass — a good reminder to know what a library method does internally.

▶Full solution
☕ Java · Two Sets
List<List<Integer>> findDifference(int[] nums1, int[] nums2) {
    Set<Integer> a = new HashSet<>(), b = new HashSet<>();
    for (int x : nums1) a.add(x);
    for (int x : nums2) b.add(x);

    List<Integer> onlyA = new ArrayList<>(), onlyB = new ArrayList<>();
    for (int x : a) if (!b.contains(x)) onlyA.add(x);
    for (int x : b) if (!a.contains(x)) onlyB.add(x);

    return List.of(onlyA, onlyB);
}
TimeO(n + m)
SpaceO(n + m)
