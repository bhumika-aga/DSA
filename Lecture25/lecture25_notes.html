Two Pointers & Sliding Window

“Stop re-reading the same elements. Every pattern here is one idea — touch each item a constant number of times, and O(n²) collapses to O(n).”

📚 Lecture 25 of 45 Phase 3 — Core Patterns ⏱ 6 days 🎯 30 problems 💼 Google · Amazon · Meta · Uber
🌍
Why does this topic matter?
You have already met these pointers piecemeal — in Arrays, in Searching, in Linked Lists. This lecture puts them in one place so they stop being five tricks and become one decision. Between them, two pointers and sliding windows cover a very large slice of the array and string questions asked at every company on this page, and they are the difference between a solution that passes and one that times out.
By the end of this lecture you can
  • Consolidate every two-pointer and sliding-window pattern into one mental model
  • Recognise which shape a problem needs within twenty seconds of reading it
  • Write the expand/shrink template from memory, for both longest and shortest
  • Handle multi-pointer problems: 3Sum, 4Sum and beyond, including deduplication
  • Use the at-most trick to count “exactly k” without a second algorithm
🧠
The picture to keep in your head: A camera panning across a view. When a camera pans, you do not retake the whole photo — one edge gains a new strip and the other loses one. A sliding window works the same way: add what enters on the right, remove what leaves on the left. Two pointers from both ends are two people searching a sorted bookshelf from opposite ends and meeting in the middle.

🧭 The Decision Guide

Everything in this lecture is one idea: stop re-reading the same elements. A brute-force pair loop reads every element n times. Two pointers and sliding windows read each element a constant number of times, which turns O(n²) into O(n). The only skill worth drilling is picking the right shape in the first twenty seconds.

What the problem says Shape to reach for Signature move
“sorted array” + find a pair / triple Opposite ends lo = 0, hi = n-1, move the one that helps
“subarray of size exactly k” Fixed window add right, remove left, every step
“longest / shortest subarray such that …” Variable window expand right, shrink left while invalid
“in-place, keep order, drop some” Same direction slow writes, fast reads
“exactly k distinct / exactly k odds” At-most trick atMost(k) − atMost(k−1)
⚠️
The one precondition people forget
Sliding windows need the answer to be monotonic as the window grows — adding an element must never make an invalid window valid again. That holds for positive numbers, distinct-character counts and frequency caps. It breaks the moment negatives enter, which is why Subarray Sum Equals K is a prefix-sum problem, not a window problem.

↔️ Opposite Ends — Converging Pointers

Start wide, walk inwards. Each step throws away a candidate you can prove is useless, so n steps settle the whole problem. This only works when the array is sorted, or when the quantity you are optimising depends on the two ends alone.

📐 Pseudocode · Converging Pointers 
// The array is sorted, so the sum moves predictably:
//   move lo right  -> sum increases
//   move hi left   -> sum decreases
lo ← 0
hi ← length(a) - 1

while lo < hi:
    sum ← a[lo] + a[hi]
    if sum = target: return (lo, hi)
    if sum < target: lo ← lo + 1     // need more
    else:              hi ← hi - 1     // need less

return NOT_FOUND
TimeO(n) — each index visited once
SpaceO(1)

Scaling Up: 3Sum and 4Sum

A k-sum problem is a (k−1)-sum problem with one number pinned. Sort once, fix the outer index, then run the converging pair inside. Each extra level costs one more loop: 3Sum is O(n²), 4Sum is O(n³).

📐 Pseudocode · 3Sum — anchor + converging pair 
sort(a)
result ← empty list

for i from 0 to n - 3:
    if i > 0 and a[i] = a[i-1]: continue   // skip duplicate anchors

    lo ← i + 1;  hi ← n - 1
    while lo < hi:
        s ← a[i] + a[lo] + a[hi]
        if s = 0:
            record (a[i], a[lo], a[hi])
            while lo < hi and a[lo] = a[lo+1]: lo ← lo + 1
            while lo < hi and a[hi] = a[hi-1]: hi ← hi - 1
            lo ← lo + 1;  hi ← hi - 1
        else if s < 0: lo ← lo + 1
        else:          hi ← hi - 1

return result
💡
Duplicates are the whole difficulty
3Sum is not hard because of the pointers — it is hard because the answer must contain no repeated triple. Skip a duplicate anchor before the inner loop, and skip duplicate lo/hi values only after recording a hit. Sorting first is what makes both skips a single comparison.

When Both Ends Decide the Answer

Container With Most Water and Trapping Rain Water are not sorted, yet converging pointers still work — because the quantity being measured (width × shorter wall) depends only on the two ends. Always move the pointer at the shorter wall: the width shrinks either way, so moving the taller one can never improve the answer.

📐 Pseudocode · Container With Most Water 
// Area is width x the SHORTER wall, so the short side is the bottleneck.
lo ← 0;  hi ← n - 1;  best ← 0

while lo < hi:
    best ← max(best, (hi - lo) × min(h[lo], h[hi]))
    if h[lo] < h[hi]: lo ← lo + 1     // only raising the short wall can help
    else:               hi ← hi - 1

return best
TimeO(n)
SpaceO(1)

🪟 Fixed-Size Window

The simplest window: size never changes. Build the first k elements, then for every step add one on the right and drop one on the left. The work per step is O(1), so the whole scan is O(n) no matter how big k is.

📐 Pseudocode · Fixed Window — roll, don't rebuild 
// Build the first window, then roll it along.
sum ← sum of a[0 .. k-1]
best ← sum

for right from k to n - 1:
    sum ← sum + a[right] - a[right - k]   // add new, drop old
    best ← max(best, sum)

return best
TimeO(n)
SpaceO(1)

🎚️ Variable-Size Window — Expand and Shrink

This is the one to memorise. Nearly every “longest / shortest subarray such that…” question is the same eight lines: the right pointer always moves forward, and the left pointer only catches up when the window breaks the rule. Each index enters once and leaves once, so it is O(n) even though there are two loops.

📐 Pseudocode · The Universal Sliding-Window Template 
// The universal template. Only the three marked lines change.
left ← 0
best ← 0
state ← empty        // counts, a sum, a frequency map ...

for right from 0 to n - 1:
    add a[right] to state              // <-- 1. grow

    while state is invalid:               // <-- 2. the rule
        remove a[left] from state
        left ← left + 1

    best ← max(best, right - left + 1)   // <-- 3. what you want

return best

// Longest valid window  -> record AFTER the while loop (as above).
// Shortest valid window -> record INSIDE the while loop, before shrinking,
//                          and invert the condition to 'while state is VALID'.

Longest: Record After Shrinking

📐 Pseudocode · Longest Substring Without Repeating Characters (LC 3) 
function lengthOfLongestSubstring(s):
    last ← map from character → (last index where it appeared) + 1, default 0
    left ← 0;  best ← 0

    for right from 0 to length(s) - 1:
        c ← s[right]
        left ← max(left, last[c])          // jump past the previous copy (never move back)
        best ← max(best, right - left + 1)
        last[c] ← right + 1
    return best
TimeO(n) — right advances n times, left never rewinds
SpaceO(1) — fixed alphabet

Shortest: Record Before Shrinking

Flip the template and the same machinery finds the smallest window instead. Minimum Window Substring is the canonical hard version: keep a need map and a counter of how many required characters are still missing. The window is valid the moment that counter hits zero.

📐 Pseudocode · Minimum Window Substring (LC 76) 
need ← frequency map of t
missing ← length(t)
left ← 0;  bestLen ← infinity

for right from 0 to n - 1:
    if need[s[right]] > 0: missing ← missing - 1
    need[s[right]] ← need[s[right]] - 1

    while missing = 0:                  // window is VALID -> try to shrink
        if right - left + 1 < bestLen:
            bestLen ← right - left + 1;  bestStart ← left
        need[s[left]] ← need[s[left]] + 1
        if need[s[left]] > 0: missing ← missing + 1
        left ← left + 1

return substring at bestStart of length bestLen
💡
Why one counter beats comparing two maps
Re-checking “does the window contain every character of t?” costs O(52) per step. Tracking a single missing integer makes the validity test O(1). Characters not in t go negative in the map and are simply never counted — that is what the > 0 guards are doing.
TimeO(|s| + |t|)
SpaceO(|t|)

🐢 Same Direction — Slow Writes, Fast Reads

When a problem says “in place, keep the relative order, remove the ones that don't qualify”, use two pointers moving the same way. The fast pointer reads every element; the slow pointer marks where the next keeper belongs. Everything before slow is finished and correct.

📐 Pseudocode · Read/Write Two Pointers 
// slow = write cursor, fast = read cursor
slow ← 0

for fast from 0 to n - 1:
    if keep(a[fast]):
        a[slow] ← a[fast]
        slow ← slow + 1

return slow                 // length of the cleaned prefix
TimeO(n)
SpaceO(1)

🎯 The At-Most Trick

A sliding window can count subarrays with at most k of something, because that property is monotonic — shrink the window and it stays true. It cannot directly count exactly k, because that is not monotonic. The fix is arithmetic, not algorithmic:

🧮
exactly(k) = atMost(k) − atMost(k−1)
Every subarray with at most k distinct values is either one with at most k−1, or one with exactly k. Subtract and only the exact ones survive. You write the window once and call it twice.
📐 Pseudocode · Subarrays with K Different Integers (LC 992) 
function exactly(k):
    return atMost(k) - atMost(k - 1)

function atMost(k):
    count ← 0;  left ← 0;  freq ← empty map

    for right from 0 to n - 1:
        if freq[a[right]] = 0: k ← k - 1
        freq[a[right]] ← freq[a[right]] + 1

        while k < 0:                     // too many distinct -> shrink
            freq[a[left]] ← freq[a[left]] - 1
            if freq[a[left]] = 0: k ← k + 1
            left ← left + 1

        count ← count + (right - left + 1)   // every window ending at right

    return count
⚠️
Why right - left + 1?
When the window [left, right] is valid, every subarray that ends at right and starts anywhere from left onwards is also valid. That is exactly right - left + 1 subarrays — so you count them all in O(1) instead of enumerating them.
TimeO(n) — two passes of the same window
SpaceO(k)

⏱ Complexity & The Four Classic Bugs

Bug What you see Fix
Recording in the wrong place Off-by-one on every answer Longest → record after the while; shortest → inside it
Shrinking with if instead of while Passes small tests, fails big ones One step may not restore validity — loop until it does
Forgetting to undo state on shrink Counts drift, window never reopens Every add on the right needs a matching remove on the left
Using a window with negative numbers Wrong answers, no crash Not monotonic — switch to prefix sums (Lecture 26)
📈
Why two nested loops are still O(n)
The inner while looks like it makes this quadratic. It doesn't: left only ever moves forward and can advance at most n times in total across the whole run. Amortised, every index is added once and removed once — 2n operations.

Problem 01 · LC 167
Two Sum II — Input Array Is Sorted
Medium Opposite Ends Amazon · Google · Adobe
▶
Problem

Given a 1-indexed sorted array and a target, return the indices of the two numbers that add up to it. Exactly one solution exists, and you may not use extra space.

Input: [2,7,11,15], target=9 → Output: [1,2]
Hints
▶Hint 1 — a nudge

The array is sorted — that is the whole gift. What happens to the sum if you move the left pointer right? What about moving the right pointer left?

▶Hint 2 — the key idea

Start at both ends. If the sum is too small the only way to grow it is lo++; if it is too big the only way to shrink it is hi--. Neither move can skip the answer.

Solution

A HashMap would work but costs O(n) space, and the sorted input makes it unnecessary. Converging pointers solve it in constant space.

▶Full solution
📐 Pseudocode · Two Sum II 
function twoSum(a, target):
      lo ← 0;  hi ← length(a) - 1
      while lo < hi:
          sum ← a[lo] + a[hi]
          if sum = target: return [lo + 1, hi + 1]     // 1-indexed answer
          if sum < target: lo ← lo + 1                 // need bigger
          else: hi ← hi - 1                            // need smaller
      return []
TimeO(n)
SpaceO(1)
Problem 02 · LC 11
Container With Most Water
Medium Opposite Ends Google · Amazon · Meta · Bloomberg
▶
Problem

Given heights of vertical lines, find two that together with the x-axis hold the most water.

Input: [1,8,6,2,5,4,8,3,7] → Output: 49
Hints
▶Hint 1 — a nudge

Area is width × the shorter of the two walls. Start as wide as possible — then every move you make loses width.

▶Hint 2 — the key idea

Since width only shrinks, the only way to win is a taller wall. Always move the pointer at the shorter wall; moving the taller one can never help.

Solution

Greedy converging pointers. The proof: whichever wall is shorter caps the area, so keeping it and moving the tall one strictly loses.

▶Full solution
📐 Pseudocode · Container With Most Water 
function maxArea(h):
      lo ← 0;  hi ← length(h) - 1;  best ← 0
      while lo < hi:
          best ← max(best, (hi - lo) × min(h[lo], h[hi]))
          if h[lo] < h[hi]: lo ← lo + 1       // move the shorter wall — it caps the area
          else: hi ← hi - 1
      return best
TimeO(n)
SpaceO(1)
Problem 03 · LC 15
3Sum
Medium Anchor + Converging Pair Amazon · Meta · Google · Adobe
▶
Problem

Return all unique triplets that sum to zero. The answer must contain no duplicate triplets.

Input: [-1,0,1,2,-1,-4] → Output: [[-1,-1,2],[-1,0,1]]
Hints
▶Hint 1 — a nudge

Fix one number and the problem collapses to Two Sum on the rest. What must you do first to make that inner search O(n)?

▶Hint 2 — the key idea

Sort, then for each anchor i run converging pointers on i+1 .. n-1. The hard part is duplicates: skip repeated anchors, and after recording a hit skip repeated lo/hi values.

Solution

Sorting costs O(n log n) but buys both the pointer walk and cheap deduplication. Total O(n²).

▶Full solution
📐 Pseudocode · 3Sum 
function threeSum(a):
      sort a
      out ← empty list
      for i from 0 to length(a) - 3:
          if i > 0 and a[i] = a[i - 1]: continue       // duplicate anchor
          lo ← i + 1;  hi ← length(a) - 1
          while lo < hi:
              s ← a[i] + a[lo] + a[hi]
              if s = 0:
                  append [a[i], a[lo], a[hi]] to out
                  while lo < hi and a[lo] = a[lo + 1]: lo ← lo + 1   // skip duplicates
                  while lo < hi and a[hi] = a[hi - 1]: hi ← hi - 1
                  lo ← lo + 1;  hi ← hi - 1
              else if s < 0: lo ← lo + 1
              else: hi ← hi - 1
      return out
TimeO(n²)
SpaceO(1) beyond the output
Problem 04 · LC 3
Longest Substring Without Repeating Characters
Medium Variable Window Amazon · Google · Meta · Bloomberg
▶
Problem

Find the length of the longest substring with no repeated characters.

Input: "abcabcbb" → Output: 3 ("abc")
Hints
▶Hint 1 — a nudge

Walk the right edge forward one character at a time. When does the window stop being valid, and which pointer must move to fix it?

▶Hint 2 — the key idea

Keep the last index of every character. On a repeat, jump left to just past that previous copy — never backwards, or you will double-count.

Solution

The Math.max on left is what keeps it correct: a stale duplicate from before the current window must not drag left backwards.

▶Full solution
📐 Pseudocode · LC 3 
function lengthOfLongestSubstring(s):
      last ← map char → last index + 1, default 0
      left ← 0;  best ← 0
      for r from 0 to length(s) - 1:
          left ← max(left, last[s[r]])
          best ← max(best, r - left + 1)
          last[s[r]] ← r + 1
      return best
TimeO(n)
SpaceO(1)
Problem 05 · LC 424
Longest Repeating Character Replacement
Medium Variable Window Google · Amazon · Meta
▶
Problem

You may change at most k characters. Find the longest substring of one repeated letter you can produce.

Input: s="AABABBA", k=1 → Output: 4
Hints
▶Hint 1 — a nudge

A window is valid when the characters you would have to replace fit inside k. How do you compute “replacements needed” from the window's letter counts?

▶Hint 2 — the key idea

Replacements needed = window length − count of the most frequent letter. Shrink while that exceeds k.

Solution

You do not need to recompute the max frequency when shrinking — letting it go stale only ever under-estimates the window, which never produces a wrong maximum.

▶Full solution
📐 Pseudocode · LC 424 
function characterReplacement(s, k):
      cnt ← count per letter, all 0
      left ← 0;  most ← 0;  best ← 0
      for r from 0 to length(s) - 1:
          cnt[s[r]] ← cnt[s[r]] + 1
          most ← max(most, cnt[s[r]])
          while (r - left + 1) - most > k:        // too many chars to replace
              cnt[s[left]] ← cnt[s[left]] - 1
              left ← left + 1
          best ← max(best, r - left + 1)
      return best
TimeO(n)
SpaceO(1)
Problem 06 · LC 76
Minimum Window Substring
Hard Variable Window (shortest) Meta · Amazon · Google · Uber
▶
Problem

Find the smallest substring of s containing every character of t, including duplicates.

Input: s="ADOBECODEBANC", t="ABC" → Output: "BANC"
Hints
▶Hint 1 — a nudge

This asks for the shortest valid window, not the longest. That flips where you record the answer relative to the shrink loop.

▶Hint 2 — the key idea

Keep a need map and one missing counter. When missing hits 0 the window is valid — record it, then shrink from the left and keep recording while it stays valid.

Solution

The single counter makes validity O(1). Characters outside t go negative in the map, so the > 0 guards naturally ignore them.

▶Full solution
📐 Pseudocode · LC 76 
function minWindow(s, t):
      need ← count of each char in t, default 0
      missing ← length(t)
      left ← 0;  bestStart ← 0;  bestLen ← ∞
      for r from 0 to length(s) - 1:
          if need[s[r]] > 0: missing ← missing - 1   // this char was still needed
          need[s[r]] ← need[s[r]] - 1                // extras go negative

          while missing = 0:                         // window is valid — shrink it
              if r - left + 1 < bestLen:
                  bestLen ← r - left + 1
                  bestStart ← left
              need[s[left]] ← need[s[left]] + 1
              if need[s[left]] > 0: missing ← missing + 1   // dropped a needed char
              left ← left + 1
      if bestLen = ∞: return ""
      return s[bestStart .. bestStart + bestLen - 1]
TimeO(|s| + |t|)
SpaceO(|t|)
Problem 07 · LC 992
Subarrays with K Different Integers
Hard At-Most Trick Google · Amazon · Meta
▶
Problem

Count the subarrays containing exactly k distinct integers.

Input: [1,2,1,2,3], k=2 → Output: 7
Hints
▶Hint 1 — a nudge

A window can answer “at most k distinct” easily, because shrinking always keeps that true. “Exactly k” is not monotonic — so don't try to window it directly.

▶Hint 2 — the key idea

exactly(k) = atMost(k) − atMost(k−1). Write the at-most window once and call it twice.

Solution

Inside atMost, every valid window ending at right contributes right - left + 1 subarrays, counted in O(1).

▶Full solution
📐 Pseudocode · LC 992 
function subarraysWithKDistinct(a, k):
      return atMost(a, k) - atMost(a, k - 1)      // "exactly k" = "at most k" − "at most k−1"

  function atMost(a, k):
      freq ← empty map, default 0
      left ← 0;  count ← 0
      for r from 0 to length(a) - 1:
          freq[a[r]] ← freq[a[r]] + 1
          if freq[a[r]] = 1: k ← k - 1          // a new distinct value
          while k < 0:
              freq[a[left]] ← freq[a[left]] - 1
              if freq[a[left]] = 0: k ← k + 1   // a value left the window entirely
              left ← left + 1
          count ← count + (r - left + 1)         // every subarray ending at r
      return count
TimeO(n)
SpaceO(k)
Problem 08 · LC 42
Trapping Rain Water
Hard Opposite Ends Google · Amazon · Meta · Microsoft
▶
Problem

Given an elevation map, compute how much rain water it can trap.

Input: [0,1,0,2,1,0,1,3,2,1,2,1] → Output: 6
Hints
▶Hint 1 — a nudge

Water above any single bar is min(tallestLeft, tallestRight) - height. The O(n)-space answer precomputes both. Can you avoid storing them?

▶Hint 2 — the key idea

Walk from both ends keeping leftMax and rightMax. Whichever side is shorter is the binding constraint, so that side's water is already decided — settle it and step inwards.

Solution

The insight is that you never need the exact other-side maximum, only the knowledge that it is at least as tall as the side you are settling.

▶Full solution
📐 Pseudocode · LC 42 
function trap(h):
      lo ← 0;  hi ← length(h) - 1
      leftMax ← 0;  rightMax ← 0;  water ← 0
      while lo < hi:
          if h[lo] < h[hi]:                      // left side is the bottleneck
              leftMax ← max(leftMax, h[lo])
              water ← water + leftMax - h[lo]
              lo ← lo + 1
          else:
              rightMax ← max(rightMax, h[hi])
              water ← water + rightMax - h[hi]
              hi ← hi - 1
      return water
TimeO(n)
SpaceO(1)
