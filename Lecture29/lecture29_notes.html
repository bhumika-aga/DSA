Greedy Algorithms

“Take the best-looking step and never look back. The hard part is not the code — it is knowing that you are allowed to.”

📚 Lecture 29 of 45 Phase 3 — Core Patterns ⏱ 5 days 🎯 25 problems 💼 Google · Amazon · Meta · Microsoft
🌍
Why does this topic matter?
You have already written greedy algorithms without calling them that: sorting by end time in Lecture 28, Kadane's reset in Lecture 11, the heap that always took the most frequent task in Lecture 20. What those have in common is a decision made once and never revisited. This lecture is about the hard half — knowing which rule to be greedy about, and being able to say why it cannot go wrong.
By the end of this lecture you can
  • State the greedy-choice property and the exchange argument
  • Test a candidate rule against the inputs designed to break it
  • Recognise the three shapes: sort-then-take, reach, and regret
  • Say when a problem needs DP instead, and why greedy fails there
  • Write each pattern in a few lines, because the code is never the hard part
🧠
The picture to keep in your head: Making change. To give 63 cents in as few coins as possible, you take the biggest coin that fits, again and again — quarters, then a dime, then pennies. That is greedy, and for real currencies it is perfect. With coins of 1, 3 and 4, it gives 4 + 1 + 1 for 6 instead of 3 + 3. That is why every greedy solution needs a reason, not just a good feeling.

💡 What Greedy Actually Means

A greedy algorithm builds an answer one step at a time. At each step it applies a fixed rule — take the cheapest, the earliest, the largest — and it never undoes a step. That is the whole definition, and also the whole risk.

📐 Pseudocode · The Shape of Every Greedy Solution 
order the items by the rule           // the only creative step
answer ← empty

for item in items:
    if item still fits the constraints:
        take it                       // irrevocably

return answer

// The code is five lines. Choosing the rule — and proving it — is the work.
🧠
Two properties have to hold. Greedy choice: some optimal answer contains the choice your rule makes first. Optimal substructure: after making it, what remains is the same problem on a smaller input. Interval scheduling has both. Making change with coins {1, 3, 4} has neither — which is why 6 becomes 4+1+1 instead of 3+3.

⚖️ Proving It Works

In an interview you will not write a formal proof, but you will be asked “why does that work?” There is one answer that fits almost every greedy problem.

The Exchange Argument

🔎
The argument in three sentences. Suppose an optimal answer disagrees with your first greedy choice. Swap your choice into it, in place of whatever it used. Show the result is still valid and no worse — so an optimal answer containing your choice exists, and by repeating the argument, the whole greedy answer is optimal.

For interval scheduling it reads: the optimal set's first meeting ends no earlier than the earliest-ending meeting, so swapping yours in cannot clash with anything that followed. Same size, still valid, done.

When Greedy Fails

Before trusting a rule, throw the standard counter-examples at it. Most wrong greedy rules die to one of these four:

Trap Example What breaks
A big item blocks two small ones intervals [1, 10], [2, 3], [4, 5] “take the longest” keeps 1 instead of 2
A cheap step now costs more later coins {1, 3, 4}, target 6 largest-first gives 3 coins, best is 2
Negative or zero values weights that can reduce a total “always add” stops being safe
A choice that must be undone 0/1 knapsack with tight capacity needs DP: items interact
🛑
The two-minute test. Write your rule down, then spend two minutes trying to build a five-element input that beats it. If you cannot, sketch the exchange argument and commit. If you can, you have just saved yourself a wrong solution — and the counter-example usually points straight at DP.

📊 Shape 1 — Sort, Then Take

The most common shape. Put the items in the right order and a single pass is the whole algorithm. Everything depends on the sort key.

📐 Pseudocode · Two-Pointer Matching (Assign Cookies) 
function findContentChildren(greed, cookies):
    sort greed ascending;  sort cookies ascending
    i ← 0;  j ← 0;  fed ← 0

    while i < length(greed) and j < length(cookies):
        if cookies[j] ≥ greed[i]:       // smallest cookie that satisfies the least greedy child
            fed ← fed + 1;  i ← i + 1
        j ← j + 1                       // a cookie too small is wasted on everyone
    return fed

// Exchange argument: giving a child a bigger cookie than needed can only
// hurt, since that cookie might have been the only one for someone else.
Sort key Problem shape Why that key
end time ascending keep the most non-overlapping items finishing early leaves the most room
value per unit, descending fractional knapsack, units on a truck every unit of capacity should carry the most
both arrays ascending matching two sets (cookies, boats) spend the smallest resource that still works
tallest first, then insert by index queue reconstruction shorter people do not disturb taller ones

🏎 Shape 2 — Track the Reach

No sorting at all: scan left to right, keeping the furthest point you could get to. The greedy choice is invisible — it is the decision to only ever extend the frontier.

📐 Pseudocode · Minimum Jumps 
function jump(nums):
    jumps ← 0
    currentEnd ← 0        // the last index reachable with the jumps taken
    farthest ← 0          // the best we could reach with one more

    for i from 0 to length(nums) - 2:
        farthest ← max(farthest, i + nums[i])
        if i = currentEnd:            // the current jump is used up
            jumps ← jumps + 1
            currentEnd ← farthest      // commit to the best frontier we saw
    return jumps

// [2,3,1,1,4]: frontier 0→2, then 2→4 → 2 jumps.
// You never choose WHICH index to jump to — only how far the level reaches.
🧠
It is BFS in disguise. Each “level” is the set of indices reachable with one more jump, and currentEnd marks the end of the level — exactly the ring-by-ring sweep from Lecture 21, done with two integers instead of a queue.

The same frontier idea, differently dressed: Gas Station asks where a circular tour can start. If the total gas is at least the total cost a solution exists, and the only possible start is just after the point where the running tank hits its lowest value.

📐 Pseudocode · Gas Station — Start at the Valley 
function canCompleteCircuit(gas, cost):
    total ← 0;  tank ← 0;  start ← 0

    for i from 0 to length(gas) - 1:
        gain ← gas[i] - cost[i]
        total ← total + gain
        tank ← tank + gain
        if tank < 0:                 // cannot reach i + 1 from the current start
            start ← i + 1              // so no station in between works either
            tank ← 0
    if total < 0: return -1
    return start

🔄 Shape 3 — Greedy with Regret

Sometimes you must take things as they arrive, and only later discover you cannot afford them all. The fix is a heap: take everything, and when a constraint breaks, give back the worst thing you have taken. The decision is still never re-examined — only the worst item is ever dropped.

📐 Pseudocode · Course Schedule III 
function scheduleCourse(courses):
    sort courses by deadline ascending      // handle the most urgent first
    heap ← empty max-heap of durations
    time ← 0

    for (duration, deadline) in courses:
        heap.push(duration);  time ← time + duration    // take it first

        if time > deadline:                 // over budget — regret the longest course
            time ← time - heap.popMax()
    return heap.size

// Dropping the longest course taken so far never reduces the count,
// and always frees the most time. Same trick as Minimum Refueling Stops.

🧮 Greedy vs Dynamic Programming

Greedy Dynamic programming
Decisions one rule, never revisited every option explored, best kept
Cost usually O(n log n), often O(n) states × transitions
Needs greedy choice + optimal substructure optimal substructure alone
Fails when a local best blocks a better global answer rarely — but may be too slow or too big
Example pair fractional knapsack 0/1 knapsack (Lecture 34)
⚠️
The tell. If taking an item can make a later, better item unaffordable — and you cannot fix that by sorting — greedy is wrong and DP is right. If the items never interact except through one running quantity (time, capacity, reach), greedy usually wins.

⚠️ Complexity & The Classic Bugs

Shape Time Space Typical problems
Sort, then one pass O(n log n) O(1) Assign Cookies, Boats, Non-overlapping Intervals
Track the reach O(n) O(1) Jump Game I / II, Gas Station
Greedy with regret (heap) O(n log n) O(n) Course Schedule III, Refueling Stops
Counting greedy O(n) O(1) Lemonade Change, Valid Parenthesis String
Bug Symptom Fix
Guessing the sort key Passes the samples, fails hidden tests Sketch the exchange argument before coding
Sorting by start for a “keep the most” question One long item blocks two short ones Sort by end
Greedy where items interact Answer is close but never optimal Switch to DP — the counter-example shows why
No feasibility check Returns an answer where none exists Test the total first (Gas Station, Taps)
Regret heap keyed on the wrong field Drops an item that was not the costly one The heap orders by what you want back, not by arrival
Ties left to the default order Unstable results on equal keys Make the tie-break explicit in the comparator
💡
How to spot it in an interview. “Maximum number of…”, “minimum steps to…”, “can you finish…” — with no requirement to report the actual arrangement, and items that only interact through one running quantity. Say the rule out loud, test it against two adversarial inputs, then write the five lines.

Problem 01 · Sort, Then Match
Assign Cookies
🔗 LC 455 - Assign Cookies
Easy Two-Pointer Matching Amazon · Google
›
Problem

Each child has a greed factor and each cookie a size. A child is content if the cookie is at least their greed. Maximise the number of content children.

greed = [1, 2, 3], cookies = [1, 1] → 1   |   greed = [1, 2], cookies = [1, 2, 3] → 2
Hints
▶Hint 1 — a nudge

Which cookie should go to the least greedy child? The smallest that works, or the largest?

▶Hint 2 — the key idea

Sort both. Walk them with two pointers, giving the smallest cookie that satisfies the current child and skipping cookies that satisfy nobody.

Solution

The exchange argument: if an optimal solution gives a child a larger cookie than needed, swapping in the smallest sufficient one keeps everyone content and frees the larger cookie for someone else. So the greedy match is never worse. Both pointers only move forward, so after the sort it is one linear pass.

▶Full solution
📐 Pseudocode · Smallest Sufficient Cookie 
function findContentChildren(greed, cookies):
    sort greed ascending
    sort cookies ascending
    i ← 0;  j ← 0;  fed ← 0

    while i < length(greed) and j < length(cookies):
        if cookies[j] ≥ greed[i]:
            fed ← fed + 1
            i ← i + 1                 // this child is done
        j ← j + 1                     // the cookie is used or useless either way
    return fed

// greed [1,2,3], cookies [1,1]: cookie 1 feeds child 1; the second
// cookie satisfies nobody → 1 ✓
TimeO(n log n + m log m)
SpaceO(1)
Problem 02 · Counting Greedy
Lemonade Change
🔗 LC 860 - Lemonade Change
Easy Spend the Largest First Amazon · Google
›
Problem

Customers pay with $5, $10 or $20 bills for a $5 drink. You start with no change. Return true if you can serve everyone in order.

bills = [5, 5, 5, 10, 20] → true   |   bills = [5, 5, 10, 10, 20] → false
Hints
▶Hint 1 — a nudge

For a $20 you owe $15. Two ways to make it — which do you use?

▶Hint 2 — the key idea

Prefer a $10 plus a $5. Fives are useful for every kind of change, so keep as many as you can.

Solution

Only two counters are needed; twenties are never given as change, so they are not worth tracking. The greedy rule is to spend the least flexible bill first: a $10 can only ever be part of $15, while a $5 can pay change for a $10 or a $20. Giving away three fives when a ten was available is the classic failure.

▶Full solution
📐 Pseudocode · Two Counters 
function lemonadeChange(bills):
    fives ← 0;  tens ← 0

    for bill in bills:
        if bill = 5: fives ← fives + 1
        else if bill = 10:
            if fives = 0: return false
            fives ← fives - 1;  tens ← tens + 1
        else:                              // a 20 needs 15 back
            if tens > 0 and fives > 0:
                tens ← tens - 1;  fives ← fives - 1   // prefer 10 + 5
            else if fives ≥ 3:
                fives ← fives - 3
            else: return false
    return true
TimeO(n)
SpaceO(1)
Problem 03 · Track the Reach
Jump Game II
🔗 LC 45 - Jump Game II
Medium Frontier / Implicit BFS Amazon · Google · Meta
›
Problem

Each nums[i] is the maximum jump length from index i. Return the minimum number of jumps to reach the last index (always possible).

nums = [2, 3, 1, 1, 4] → 2  (index 0 → 1 → 4)
Hints
▶Hint 1 — a nudge

You never need to decide which index to land on. What do you actually need to track?

▶Hint 2 — the key idea

Keep the end of the current jump’s range and the furthest index reachable with one more. When you hit the end of the range, take a jump and move the frontier out.

Solution

This is breadth-first search with two integers instead of a queue: each jump is one BFS level, and currentEnd marks where that level stops. Because you only ever extend the frontier, no backtracking is possible — the greedy choice is to always jump to the level that reaches furthest. Stop the loop at n - 2 so arriving exactly at the last index does not count an extra jump.

▶Full solution
📐 Pseudocode · Level by Level 
function jump(nums):
    jumps ← 0;  currentEnd ← 0;  farthest ← 0

    for i from 0 to length(nums) - 2:
        farthest ← max(farthest, i + nums[i])
        if i = currentEnd:          // this jump can go no further
            jumps ← jumps + 1
            currentEnd ← farthest
    return jumps

// [2,3,1,1,4]: i=0 farthest=2, i=currentEnd → jump 1, end=2
// i=1 farthest=4; i=2 = end → jump 2, end=4 → answer 2 ✓
TimeO(n)
SpaceO(1)
Problem 04 · Start at the Valley
Gas Station
🔗 LC 134 - Gas Station
Medium Running Total + Restart Amazon · Google · Microsoft
›
Problem

Around a circular route, station i gives gas[i] and driving to the next costs cost[i]. Return the starting station that lets you complete the circuit, or −1.

gas = [1,2,3,4,5], cost = [3,4,5,1,2] → 3
Hints
▶Hint 1 — a nudge

First, when is the trip impossible at all? That question has nothing to do with the starting point.

▶Hint 2 — the key idea

If the tank goes negative somewhere, no station between the old start and that point can work either — so restart from the next station and reset the tank.

Solution

Two separate facts. Feasibility is global: if total gas is at least total cost, some start works. Location is local: whenever the running tank dips below zero, every station in the failed stretch is also a failure, so the search can jump past all of them. That is what makes it one pass instead of n simulations.

▶Full solution
📐 Pseudocode · Total + Restart Point 
function canCompleteCircuit(gas, cost):
    total ← 0;  tank ← 0;  start ← 0

    for i from 0 to length(gas) - 1:
        gain ← gas[i] - cost[i]
        total ← total + gain
        tank ← tank + gain
        if tank < 0:
            start ← i + 1              // skip the whole failed stretch
            tank ← 0
    if total < 0: return -1
    return start

// gains: -2, -2, -2, +3, +3 → total 0; tank dips at 0,1,2 → start = 3 ✓
TimeO(n)
SpaceO(1)
Problem 05 · Sort by Height
Queue Reconstruction by Height
🔗 LC 406 - Queue Reconstruction by Height
Medium Insert in the Right Order Amazon · Google · Meta
›
Problem

Each person is [h, k]: height h, with exactly k people of height at least h in front of them. Rebuild the queue.

people = [[7,0],[4,4],[7,1],[5,0],[6,1],[5,2]] → [[5,0],[7,0],[5,2],[6,1],[4,4],[7,1]]
Hints
▶Hint 1 — a nudge

Whose position can you be certain about before placing anyone else?

▶Hint 2 — the key idea

Place the tallest first: for them, k is literally the index. Shorter people inserted later are invisible to them, so earlier placements never break.

Solution

Sort by height descending, and by k ascending within the same height. Then insert each person at index k. The invariant is what makes it work: everyone already placed is at least as tall, so the count in front of them is unaffected by a later, shorter insertion. It is a greedy order plus a list insert, not a rearrangement.

▶Full solution
📐 Pseudocode · Tallest First, Insert at k 
function reconstructQueue(people):
    sort people by height DESCENDING, and by k ASCENDING on ties

    queue ← empty list
    for (h, k) in people:
        insert (h, k) into queue at index k     // everyone already there is ≥ h
    return queue

// [7,0] [7,1] [6,1] [5,0] [5,2] [4,4]
// → [7,0]; [7,0][7,1]; [7,0][6,1][7,1]; [5,0] at 0; [5,2] at 2; [4,4] at 4
TimeO(n²)
SpaceO(n)
Problem 06 · Greedy with Regret
Course Schedule III
🔗 LC 630 - Course Schedule III
Hard Sort by Deadline + Max-Heap Google · Amazon · Meta
›
Problem

Each course takes duration days and must finish by deadline. Starting at day 1 and taking courses one at a time, return the maximum number you can complete.

courses = [[100,200],[200,1300],[1000,1250],[2000,3200]] → 3
Hints
▶Hint 1 — a nudge

Process the courses in deadline order. What do you do when the next course pushes you past its deadline?

▶Hint 2 — the key idea

Take it anyway, then give back the longest course taken so far. Swapping a longer course for a shorter one keeps the count and frees time.

Solution

The regret heap is the key idea. Sorting by deadline means every course you have taken is still valid so far; when the total time exceeds the current deadline, dropping the longest course taken restores feasibility with the same number of courses and the most time reclaimed. The count never decreases, so the final heap size is the answer.

▶Full solution
📐 Pseudocode · Take, Then Regret 
function scheduleCourse(courses):
    sort courses by deadline ascending
    heap ← empty max-heap of durations
    time ← 0

    for (duration, deadline) in courses:
        heap.push(duration)
        time ← time + duration                 // optimistically take it

        if time > deadline:
            time ← time - heap.popMax()        // undo the costliest choice
    return heap.size

// [100,200] ok; [1000,1250] ok (1100); [200,1300]: 1300 ≤ 1300 ok;
// [2000,3200]: 3300 > 3200 → drop 2000 → 3 courses ✓
TimeO(n log n)
SpaceO(n)
